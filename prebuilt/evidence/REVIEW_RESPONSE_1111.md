## 一、本轮新增的实质性结果

### 1. `[0x92007DAC]` 全部读写已闭合（评审 P0 第 1 项）

工具：`scripts\trace_flag_92007dac.py` → `evidence\flag_92007dac_trace.txt`。
方法：对 8.19.16 aboot 的 PT_LOAD（`vaddr=0x91D00000, off=0x8000, filesz=0x2FED40, memsz=0x331814`）逐 4 字节对齐点单独解码，避开线性反汇编遇数据块失步；找 `movw #0x7DAC / movt #0x9200` 配对与 pc 相对 literal。

| 类型 | 地址 | 指令 | 语义 |
|---|---|---|---|
| **写（唯一）** | `0x91D39DB4` | `str r1, [r2]` | `r1 = 1`（`mov r1,#1` @`0x91D39DA8`），非验签结果 |
| 读 1 | `0x91D3AD40` | `ldr r3,[r3]` `cmp r3,#0` `bne 0x91D3B710` | 命中后打印日志，最终 `b 0x91D3AD4C` 继续执行，**不是阻断** |
| 读 2 | `0x91D3C864` | `ldr r3,[r3]` `cmp r3,#0` `bne 0x91D3C58C` | 条件早退 |

- raw 32-bit literal 出现 0 次、pc 相对加载 0 次 ⇒ 只有这 1 写 2 读，无隐藏 alias（在直接寻址范围内）。
- 地址 `0x92007DAC` 落在 `.bss`（`0x91FFED40..0x92031814`），crt0 清零，故初值 0。
- **`r1` 的答案**：常量 `1`，不是 RSA 结果也不是状态码。G 函数 `0x91D39CB4`：
  - `0x91D39CE8 str r2(=1),[r4,#0x14]` 无条件置 `is_tampered=1`
  - `0x91D39D1C bl 0x91D12DD0` 验签 → `0x91D39D28 cmp r7,#0` / `bne 0x91D39D9C`
  - 失败分支 `0x91D39D9C..0x91D39DC8`：`str r1(=1),[0x92007DAC]` + `str r2(=0),[r4,#0x14]`（**is_tampered 清零**）→ `b 0x91D39D50` 公共状态处理
  - ⇒ 评审「`is_tampered` 被清零、`Device tampered:false` 不能作验签成功证据」**成立且已定位到具体指令**。

### 2. 发现 G 调用者之后存在「第二次门控」（比评审预期更关键）

`0x91D3C84C bl G` 之后：

```
91D3C850  bl      0x91D445E8        ; 读 [0x92013AC0] / [0x920157DC]
91D3C854  cmp     r0, #0
91D3C858  beq     0x91D3C870        ; r0==0 → 继续镜像识别/装载
91D3C85C  movw/movt r3, 0x92007DAC
91D3C864  ldr     r3, [r3]
91D3C868  cmp     r3, #0
91D3C86C  bne     0x91D3C58C        ; flag!=0 → 早退
91D3C870  bl      0x91D131E8        ; 正常路径继续
```

`0x91D3C58C` 早退分支：`mov sb,#4` → 校验栈保护 → `pop {...,pc}` 带返回值 4 返回，**不是 ASSERT / reboot 循环**，但会提前退出该启动流程。

- `0x91D445E8` 快速路径返回 `r0 = [0x92013AC0]`；对该地址扫描只有 1 处读取、**0 处写入**，属 `.bss` ⇒ 常规情况下为 0 ⇒ 走 `beq 0x91D3C870` 继续装载。
- 慢路径（两个全局变量不等时）会调用 `0x91D516C4` 等并可能返回 `mvn r0,#0`（-1），此时才启用 flag 检查。
- **结论收紧**：项目里「G 返回后调用者继续装载」的表述要限定为「在 `0x91D445E8` 返回 0 的常规路径下继续」；`0x91D3C58C` 早退的触发条件（何时 `[0x92013AC0] != [0x920157DC]`）**尚未闭合**，列 P0 后续。这正好印证评审「不要再说『函数返回了所以后面一定能启动』」的警告。
- 边界：`/recovery` 验签路径是否同样处理**未验证**（评审要求区分，仍开放）。

## 四、可直接追加到日志的评审补充（按评审第十节要求，已按实测收紧）

> 本日研究已完成 PD1610 8.19.16 aboot 验签失败路径的指令级复核，确认其与 7.x 不同：验签失败不再进入 tampered ASSERT 重启链，G 函数置 `[0x92007DAC]=1`、清 `is_tampered=0` 后返回。但 11-11 静态追踪发现 G 的调用者在 `0x91D3C850` 调用 `0x91D445E8` 且其返回非 0 时会检查该标志并可能从 `0x91D3C58C` 提前返回，故「失败后继续装载」只在常规路径成立，不等于已证明所有签名无效镜像均能启动。
>
> 后续必须区分三类镜像：原厂签名有效、保留签名尾部但摘要失效、完全缺失 BootSignature 尾部。当前 `boot_81_unsigned_test.img` 与 `boot_81_noverify.img` 均属第二类（DER `30 82 04 FC` / 1276 B 完整保留）。`Device tampered:false` 与 `verifiedbootstate=green` 不能单独作为 RSA 验签成功的证据。
>
> 目标 B 已具备较完整的原厂基线，但 DTS 未完成往返编译验证（本机缺 dtc），compatible 命中率不等于驱动覆盖率，90 个 ext4 提取文件不能直接视为完整系统可复建素材。`restore_81_all.xml` 47 条参数已核验无误，其 `size_in_KB` 浮点格式经 `restore_601` 实测为 Firehose 接受。
>
> 在这些工作完成前，不将项目状态写成「已成功启动自编译 boot」或「已完成 Android 10 移植」。实机写入实验保持单变量；恢复通道与按键排线未修复前不进行新的启动分区写入。主报告 v7.4 继续封存。
