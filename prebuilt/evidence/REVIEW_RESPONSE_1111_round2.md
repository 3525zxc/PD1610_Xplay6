# 第二轮复评落实：`0x91D445E8 → 0x92013AC0 → 0x91D3C58C` 链条闭合

日期：2026-11-11　纯离线静态分析，**零设备操作、零刷写**
复评边界：评审员明确声明未重跑本地反汇编，仅依据指令摘录做逻辑复核。本文件为实际重跑结果。

## 结论速览

| 评审 P0 项 | 结果 |
|---|---|
| P0-1 `0x91D445E8` 何时返回非零 | **已闭合**：3 个出口（0 / `-1` / `[0x92013AC0]`），常规快路径返回 0；另有**第 2 个调用者** `0x91D3CC68` |
| P0-2 `0x91D3C58C` 与上层行为 | **已闭合**：是 `0x91D3C3F0` 的正常返回出口，返回值 4 被 `0x91D412AC` 接收后**进入重试循环**，不是启动终止 |
| P0-3 `/boot` vs `/recovery` | **部分闭合**：G 有 **3 个调用者**，且 G 内部自带 `/recovery` 分区选择分支；三条路径是否全经过第二门控仍开放 |
| P1 D 类 footerless 镜像 | **已离线生成**（`boot_81_D_footerless.img`），未刷设备 |
| 恢复 XML 独立审计 | **全过**：47/47 与 GPT 吻合、0 重叠、0 越界 |

**最重要的修正**：评审提出的「条件式提前退出」确实存在，但**它不是启动失败终点**——上层会重新调用 boot 加载函数。因此「未签名 boot 一定进不了内核」和「函数返回了所以一定继续启动」两种说法都不成立；准确表述应为「验签失败后 G 返回，但调用者存在依赖辅助状态的条件式提前退出，该提前退出会回到上层重试循环，最终效果取决于重试能否收敛」。

## 一、P0-1：helper `0x91D445E8` 完整出口与调用者

### 出口（3 个）

| 出口 | 地址 | 返回 r0 | 条件 |
|---|---|---|---|
| 快路径 | `0x91D44620 pop {pc}` | **`[0x92013AC0]`** | `[0x920157DC]` 前后值相等（`0x91D44614 cmp` / `beq`）|
| 慢路径成功 | `0x91D446F4 pop {r4,r5,r6,r7,pc}` | `r0 = r4 = 0`（`0x91D446DC mov r0,r4`，r4 来自 `subs r4,r0,#0` 且 `bne` 未跳） | `0x91D20C80` 返回 0 |
| 慢路径失败 | `0x91D44704 mvn r0,#0` → `b 0x91D446E0` → `0x91D446F4` | **`-1`** | `0x91D20C80` 返回非 0（先打印 `0x91D8632C`）|

- `[0x92013AC0]`：**1 处直接读（`0x91D44608`）、0 处直接写**，属 `.bss`（`0x91FFED40..0x92031814`），crt0 清零 ⇒ 常规为 0。
- `[0x920157DC]` 是栈保护 canary：扫描到 1,653 处材料化、**4 处直接写**（`0x91D19050`、`0x91D190E4`、`0x91D2098C`、`0x91D47E2C`），说明 helper 快/慢路径的分流本质是**并发/重入一致性检查**，不是专门的验签状态机。
- ⇒ 评审「没有找到直接写入指令 ≠ 变量永远为零」的保留意见成立，但**快路径返回 0 有结构性依据**：`0x91D3C854 cmp r0,#0 / beq 0x91D3C870` 常规走继续装载，不读 `verify_failure_flag`。**间接写入（指针/结构体偏移/批量内存操作）仍未 100% 排除**，保留为证据边界。

### 调用者（2 个，评审特别要求补查）

| 调用点 | 后续判断 | 语义 |
|---|---|---|
| `0x91D3C850` | `cmp r0,#0 / beq 0x91D3C870`；r0≠0 才读 `[0x92007DAC]` | 主启动路径的第二门控 |
| **`0x91D3CC68`** | `subs r3,r0,#0 / bne 0x91D3C7F4` | **同一大函数内的另一处**，r0≠0 跳去做边界检查（`0x91D3C7F4` 起比较长度/地址），不直接失败 |

⇒ 评审「只研究当前调用点可能漏掉真正的状态初始化来源」的提醒正确：helper 有第二个调用者，但两者都在 `0x91D3C3F0` 启动函数内，**没有找到启动入口之外的初始化调用者**。

### 门控精确触发条件

```
0x91D3C84C  bl G(0x91D39CB4)
0x91D3C850  bl helper(0x91D445E8)
0x91D3C854  cmp r0,#0 ; beq 0x91D3C870   ← r0==0 → 继续装载（常规）
0x91D3C85C  materialise 0x92007DAC
0x91D3C864  ldr r3,[r3]
0x91D3C868  cmp r3,#0
0x91D3C86C  bne 0x91D3C58C             ← helper≠0 且 flag≠0 才早退
```

**两个条件必须同时成立**：helper 返回非零（其自身慢路径失败 `-1`，或 `[0x92013AC0]` 被写成非 0）**且** `verify_failure_flag=1`（验签失败）。这不是第二次 RSA 验签——采纳评审的措辞，记作**辅助门控**。

## 二、P0-2：`0x91D3C58C` 与上层接收者（决定性结果）

- **函数边界确认**：`0x91D3C3F0 push {r4,r5,r6,r7,r8,sb,sl,fp,lr}` + `sub sp,#0x64` ↔ `0x91D3C5A0 add sp,#0x64` + `0x91D3C5A4 pop {r4..fp,pc}`，栈帧完全对应 ⇒ `0x91D3C58C` 是 **`0x91D3C3F0` 这个启动主函数的正常返回出口之一**，不是异常跳出。
- 返回值：`0x91D3C588 mov sb,#4` → `0x91D3C590 mov r0,sb` ⇒ **r0 = 4**。
- 上层接收者：`0x91D412AC bl 0x91D3C3F0`（枚举到 **1 个**直接调用者），紧随：

```
91D412B0  sub  r0, r0, #4        ; 4 -> 0
91D412B4  cmp  r0, #5
91D412B8  bhi  0x91D4141C        ; 返回值不在 4..9 才跳出
91D412BC  lsl  r3, r5, r0        ; r5=1
91D412C0  tst  r3, #0x27         ; 4 命中 bit0
91D412C4  beq  0x91D4141C
91D412C8  bl   0x91D0AED4        ; 读 [0x92002738]（.bss）
91D412D4  mov  r0, r4 ; bl 0x91D0A4E4
91D412DC  bl   0x91D0AED4
91D412E4  beq  0x91D412AC        ; ★ 重新调用启动主函数
...
91D4141C  movw/movt r0,0x91D856E4 ; 打印后 b 0x91D411B8
```

⇒ **返回值 4 被接受为合法结果并触发一次重试**，不是回退 Fastboot、不是重启、不是停机。评审问的「是否存在再次调用 boot 加载器的机会」——**有，且是显式循环**。

⚠️ 但**不能因此说「早退无害」**：如果每次重试都得到相同的 `verify_failure_flag=1` 与同样的 helper 状态，循环可能不收敛（表现为卡 logo/无 USB），也可能在 `0x91D0AED4`（读 `[0x92002738]`，另一个 .bss 变量）条件变化后退出到 `0x91D4141C` 打印并跳 `0x91D411B8`。**重试是否收敛仍未闭合**，这正是需要 UART/实机观测的地方。

## 三、P0-3：`/boot` 与 `/recovery` 对照（部分闭合）

- **G 有 3 个调用者**（不是 1 个）：`0x91D3C84C`（`0x91D3C3F0` 主启动函数）、`0x91D3D764`（`0x91D3D27C`）、`0x91D3E380`（`0x91D3E000`）。
- **G 内部自带 `/recovery` 分支**：`0x91D39E08 movw r2,#0x3808 / movt r2,#0x91d8` = 字符串 VA `0x91D83808` = **`"/recovery"`**；由 `0x91D39DF8 bl 0x91D0AED4` 的返回决定：`bne 0x91D39CF4`（走 boot 分支）否则用 `/recovery` 串跳回 `0x91D39D18` 重新验签。同区域还有 `boot_linux_from_flash` 字符串 `0x91D837E4`。
- ⇒ 两条分区路径**共用同一个 G（同一个 `verify_failure_flag` 写入点）**，但**分区选择由 `0x91D0AED4` 的状态决定**，且 G 有 3 个调用点。
- **仍未闭合**：另外两个 G 调用者（`0x91D3D764` / `0x91D3E380`）之后**是否也经过 `0x91D445E8` + flag 检查**，以及同一全局标志在一次启动中被多次设置后是否有清零/状态残留。评审「不要把一个调用点的结果泛化到另一个」的意见保留。
- 佐证：`0x91D3D6FC` 引用 `"ERROR: No recovery partition found"`，`0x91D438F0` 引用 `"boot-recovery"`，说明 recovery 路径确实在这片代码区。

**D 采用「等长清零」而非截断**：A/B/C/D 保持相同 header、kernel、ramdisk、DTB、文件长度与分区写入范围，只有签名尾部这一个变量不同，符合评审「只有目标变量不同才有比较价值」。截断版会同时改变文件长度，不作为实验组。

命名纠正已落实：`noverify` 指 **DTB 里 system 挂载的 `verify` 标志**，不是 BootSignature 尾部；B/C 统一称「签名摘要失配镜像」；`[0x92007DAC]` 暂定名 **`verify_failure_flag`**（不叫 `rsa_invalid_flag`，因为 `verify_image_with_sig` 的失败还可能来自签名块缺失、DER 错误、镜像读取失败）。

**`threshold_test_unsigned.zip` 明确标注：打包流程烟雾测试，skip 掉 system/radio/oem 行，禁止作为完整 ROM 刷入。**

## 六、目标 B 的三处乐观偏差（评审第六节）——全部采纳

1. **DTB 反编译 ≠ DTS 可编译**：16,797 行 DTS 未经 `dtc` 往返；本机 `dtc` 与 `pylibfdt` 均未安装。定点等长修改原始 DTB 与全量重编译 DTS 是两个不同工程步骤。
2. **252 个 compatible 命中 ≠ 252 个驱动可用**：字符串命中只是初筛；vivo 私有功能可能依附在 `qcom,...` 标准驱动上。后续按 `DT 节点 → compatible → of_match_table → 驱动初始化 → 固件/blob` 链验证，优先屏幕/触摸/UFS/电源/音频/Wi-Fi/蓝牙/相机。
3. **Android 10 参考案例 ≠ 3.18.71 可跑**：OnePlus 3（MSM8996/3.18/LOS17.1）只证明平台代际可行。Binder、system-as-root first-stage init、VINTF manifest、linker namespace、SELinux、fstab/dm-verity/FDE 都还需逐项验证。

正确状态表述：**系统移植路线已建立，原厂硬件配置资料已取得，ROM 构建与启动尚未验证。**
