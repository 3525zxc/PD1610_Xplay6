我认为这次发现的矛盾有一个非常值得优先检查的解释：你可能已经正确找到了 boot 缓冲区的起始地址，却还没有完全证明传入 verify_image 的长度，以及该缓冲区和磁盘文件逐字节一致。

尤其是这两条指令：
0x9183E24C: strb ip, [r4, #0x23F]
...
0x9183E2B4: add sl, r3, ip


我认为它们之间可能存在一个此前被忽略的寄存器复用关系。

先说结论：
1. 0x92000000 很可能确实是 boot 镜像的内存缓冲区起点，但它不能证明缓冲区内容等于下载的 boot.img。
2. strb ip 只能证明写入内存的是 ip 的最低 8 位，不能证明整个 ip=0。而后面的 add sl,r3,ip 使用的是完整 32 位寄存器。
3. 我认为应该先检查 ip 和 sl 的完整寄存器数据流，再调查 UFS 读取路径。暂时不建议继续穷举 SHA-256。
4. 如果需要确定设备实际分区内容，优先采用 EDL/Firehose 只读回读。
下面逐项展开。
一、问题 1：为什么正确的缓冲区和长度仍然算不出签名摘要？
1.1 先区分三个长度
这次我建议在分析中明确区分：
名称	含义
partition_size	UFS 上 boot 分区的实际容量
image_size	boot 镜像实际需要的数据长度
hash_len	最终传入 SHA-256 更新函数的实际字节数

目前你的材料支持：
- 内存基址可能是 0x92000000。
- 签名参数中包含 /boot 和 0x03257000。
- Loader 计算了一个页对齐长度。
- verify_image 接收 r0=r7、r1=sl。
但是，只有确认 sl 的最终值，并确认 0x91839B18 没有再次修改这两个参数，才能把 hash_len=0x03257000 定为已确认。

这里有一个非常重要的汇编细节。
1.2 最大疑点：你可能误判了 ip=0
看这条：
0x9183E24C: strb ip, [r4, #0x23F]


ARM 的 STRB 指令只保存寄存器最低 8 位。

例如：
ip = 0x00000000


和：
ip = 0xFFFFF000


执行：
strb ip, [r4, #0x23F]


写入结果完全相同：
[r4 + 0x23F] = 0x00


但这两个寄存器值在后面的计算中完全不同：
0x9183E2B4: add sl, r3, ip


假设 ip=0xFFFFF000，它在这里实际相当于减去 0x1000。
这是本轮最值得核查的疑点
你之前可能根据 0x23F 最终是零，反推了 ip=0。但这只有在前面的反汇编明确显示：
mov ip, #0


或者等价的清零指令时才能成立。

单独一条 strb 不足以证明这一点。
为什么我怀疑 ip 可能是 -page_size？
看页对齐计算：
add r0, r3, r0
add r3, r3, r1
and r3, r2, r3
and r0, r0, r2


如果：
- r3 表示 page_size + kernel_size；
- r0 表示 page_size + ramdisk_size；
- r2 是页对齐掩码；
那么两个结果各自都带有一个 page_size。

而标准 Legacy Android boot image 的数据布局是：
Header       1 page
Kernel       ALIGN(kernel_size, page_size)
Ramdisk      ALIGN(ramdisk_size, page_size)
Second       ALIGN(second_size, page_size)  [可选]


这是 Android 官方定义的布局。

Android Open Source Project+2

因此，假如两个中间结果分别为：
\[
A=P+\operatorname{ALIGN}(K,P)
\]

\[
B=P+\operatorname{ALIGN}(R,P)
\]

最终总长度就应当是：
\[
L=A+B-P
\]

也就是说，后面的 ip 有可能正好承担：
\[
ip=-P
\]

这个修正作用。

这只是根据代码形态提出的假设，尚不是已经确认的实现。但它解释了为什么同一个寄存器既能给 cmdline[511] 写零，又能参与后面的地址计算。

不要再单纯根据 0x23F 写入零，就认定 ip 的完整值是零。
1.3 还有一个问题：你没有展示 E2B0 到 E2B4 之间所有寄存器变化
目前的片段：
0x9183E250: add r0, r3, r0
0x9183E254: add r3, r3, r1
0x9183E258: and r3, r2, r3
0x9183E25C: and r0, r0, r2

...

0x9183E2B0: add r3, r0, r1
0x9183E2B4: add sl, r3, ip


中间存在一段没有展示的指令。

你需要确认：
- r0 有没有被重新加载？
- r1 有没有被重新加载？
- r2 是否仍然是对齐掩码？
- ip 是否被赋值？
- r4 是不是仍然指向 boot header？
- r3 是不是前面计算的对齐结果？
尤其不能因为 E250 的 r0 是 ramdisk_size，就认定 E2B0 的 r0 仍然代表那个值。
我建议你直接整理这张寄存器表
地址	r0	r1	r2	r3	ip	sl
E204	?	?	?	page_size	?	?
E23C	?	kernel_size	?	?	?	?
E244	ramdisk_size	?	?	?	?	?
E24C	?	?	?	?	完整值待确认	?
E258	?	?	mask	对齐结果	?	?
E2B0	完整值待确认	完整值待确认	?	求和结果	完整值待确认	?
E2B4	?	?	?	?	完整值待确认	最终值
E388	0x92000000	sl	—	—	—	—

这个表补齐后，我们才能判断 0x03257000 是不是实际传入的长度。
1.4 还要检查 second_size
Android Legacy Boot Header 还有：
second_size @ 0x18
second_addr @ 0x1C


如果 second_size 不为零，那么计算整份传统 boot image 的长度时，也需要考虑 Second Stage。

你目前展示的代码主要读取 kernel_size 和 ramdisk_size，没有展示对 second_size 的处理。

请确认：
boot.img[0x18:0x1C]


是不是全零。

如果为零，这个疑点可以排除；如果不为零，就需要检查对应的数据段有没有进入验证范围。

二、问题 3：0x92000000 的数据会不会经过转换？
会存在这种可能，但我认为应该把“数据读取方式”和“数据读取后的内存处理”分开调查。

你现在发现：
0x918011F0:
    mov r0, #0x92000000
    ...
    pop {pc}


这只是告诉我们：
boot buffer base = 0x92000000


并没有告诉我们：
0x92000000 起的内容 = UFS boot 分区从偏移 0 开始的原始字节


这两件事不是同一个命题。
2.1 我认为最值得调查的三个位置
第一优先级
0x9180FF90：镜像实际读取过程

这是目前最重要的地方。

你需要追踪它究竟调用哪个 UFS 读取函数，以及：
- 读取的分区名称；
- UFS LUN；
- 起始 LBA；
- 读取长度；
- 目的地址；
- 是否存在 memcpy；
- 是否有 MBN 头处理；
- 是否跳过分区开头的某个区域。


第二优先级
0x91839B18：验签入口参数处理

虽然调用点是：
mov r0, r7
mov r1, sl
bl  0x91839B18


但需要进一步确认 0x91839B18 如何传给 0x9181167C、0x91810CB0。

重点是有没有：
- 数据基址偏移；
- 长度减法；
- 结构体转换；
- 临时缓冲区；
- 再次规范化。


第三优先级
0x9183E05C：读取结束至验签之前的写操作

搜索所有通过 r7、r4 或其别名访问 0x92000000 缓冲区的写入。

你已经发现：
strb ip, [r4, #0x23F]


这至少说明缓冲区在验签前可能被修改。


2.2 最值得关注：0x23F 的清零
我认为它的目的很可能是确保 cmdline 字符串结束。

Android Legacy Header 中：
uint8_t cmdline[512];


起始偏移为 0x40，结束位置是 0x23F。

Android Open Source Project

这意味着：
cmdline[0]   = offset 0x40
cmdline[511] = offset 0x23F


如果厂商后续把这个字段作为 C 字符串操作，就必须保证存在 NUL 终止符。

因此：
strb ip, [r4, #0x23F]


很可能是在强制确保 cmdline 最后一个字节为零。

但是这也产生一个重要影响：

验签输入可能不是原始磁盘数据，而是经过至少一次字段规范化的内存数据。

对于你当前的 1.15.1 镜像，因为原始文件该字节本来就是零，这一次修改不会导致哈希差异。

不过，如果设备实际分区中的这个字节不是零，那么它就会影响离线复现。
2.3 我目前最怀疑的内存布局问题
我认为应该重点调查：
UFS boot partition
       │
       ▼
0x9180FF90
       │
       ├── 读取原始数据
       ├── 可能执行对齐
       ├── 可能使用其他暂存地址
       └── 可能进行内存拷贝
       │
       ▼
0x92000000
       │
       ├── 清零 header + 0x23F
       ├── 其他字段处理？
       │
       ▼
0x91839B18
       │
       ▼
0x9181167C
       │
       ▼
0x91810CB0
       │
       ▼
SHA-256


这里有一个很重要的判断：

UFS 普通分区读取本身通常只是将存储数据搬运到内存，不会像解压或重新封装那样自动改变每个字节。

因此，如果 0x92000000 与离线文件不一致，我会优先寻找：
1. 读取的实际分区或起始偏移不同；
2. 读取函数经过了数据复制或跳段；
3. Loader 在验签前修改了缓冲区；
4. 传入的实际长度或基址与我们假设不同。
我暂时不会把 UFS 透明加密、特殊解码当成第一嫌疑。
2.4 目前可以进行一个很有价值的静态判断
你可以先确认：
[0x92000000, 0x92000008)


在读取完成后是不是：
41 4E 44 52 4F 49 44 21


即：
ANDROID!


如果是，说明缓冲区至少从文件结构的开头开始。

然后继续检查：
0x92000000 + 0x30
0x92000000 + 0x800
0x92000000 + kernel_offset
0x92000000 + ramdisk_offset
0x92000000 + 0x3257000


这些位置与磁盘文件应当具有怎样的对应关系。

四、问题 4：不使用 adb root，还有什么办法读取设备实际 boot 分区？
有，而且按照你当前设备条件，我最推荐 EDL/Firehose 只读回读。

4.1 EDL / Firehose：最推荐
你已经有 9008 和 QFIL 维护经验，这正好可以利用。

如果手中有与 MSM8996 和 UFS 兼容、能够执行读取操作的 Firehose programmer，就可以在 EDL 状态下直接读出 boot 分区。

Qualcomm 的 qdl-rs 工具公开支持：
- UFS 存储；
- 按分区读取；
- 整个 LUN dump；
- 分区信息读取。
其中有 dump-part 操作。

GitHub+1

我的建议是：
进入 9008
   ↓
加载匹配的 Firehose programmer
   ↓
读取 GPT
   ↓

   ↓
只读回读整个 boot 分区
   ↓

   ↓

注意这里必须是读取操作，不要误选 program、write、erase 或全盘覆盖功能。

尤其 UFS 有多个 LUN，必须确认 boot 分区属于哪个 LUN。
比对时不要只看 SHA-256

- 尾部内容；
- SHA-256。

4.2 Fastboot fetch：值得先检查，但不保证支持
Android 新版 Fastboot 有 fetch 读取分区的命令。

可以先进行只读查询：
fastboot getvar max-fetch-size


如果设备明确返回有效的最大 fetch 长度，再尝试：
fastboot fetch boot boot_partition_dump.img


但这里要提醒：Android 官方说明，bootloader 本身不一定实现 fetch；该功能还需要设备端明确支持。

Android Open Source Project+2

你这台设备的 aboot 年代较早，我不会假设它支持。

不过，查询 max-fetch-size 不会修改分区，可以作为一个低风险检查。
4.3 Stock Recovery ADB
也可以先检查：
adb shell id
adb shell ls -l /dev/block/bootdevice/by-name/boot
adb shell ls -lZ /dev/block/bootdevice/by-name/boot

五、我建议这轮先做的三件事
我不建议立即进行新的 boot.img 刷写实验。

现在最有价值的是把已有的证据链从“汇编推算”提升到“真实运行参数”。

静态分析 + 只读验证

1. 补齐 0x9183E204–0x9183E2B8 完整反汇编

3. 只读回读设备 boot 分区

最后，我想特别指出一个容易被忽略的矛盾
你目前的推理是：
固定 buffer = 0x92000000
len = 0x3257000
所以应该计算：

SHA256(file[0:0x3257000])


但目前实际能成立的只有：
调用点传入：
r0 = 0x92000000
r1 = sl


这还不足以证明：
sl = 0x3257000


也不足以证明：
memory[0x92000000:0x92000000+sl]
==
file[0:sl]


这是两个独立条件。

我现在最想先确认的是 0x9183E2B4 执行时 ip 的完整 32 位值，以及 0x9183E388 执行时 sl 的最终值。

这两个数字一旦拿到，我们就能判断你目前使用的 SHA-256 长度究竟有没有算错。然后再用 Firehose 回读确认内存数据是否对应原始分区。

这比再尝试几十种 SHA-256 拼接方式更有价值。
