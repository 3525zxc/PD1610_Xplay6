## 0. 结论速览

| 判据 | PD1619 / X9 Plus | PD1610 / Xplay6 |
|---|---|---|
| SoC / 内核 | **MSM8976** 家族 / Linux **3.10.84** | **MSM8996** / Linux **3.18** |
| 信任根标识 | `securebootkey=alpha`、`keyver=1`、hash `60ba997f…` | `securebootkey=beta`、`keyver=2`、hash `da758fd5…`（4/4 份镜像一致） |
| 官方 boot 验证 | `sigtype=AVBv1`（**仅第三方工具元数据，未取得镜像验证**） | **AOSP `AndroidVerifiedBootSignature` 标准封装**（5 份镜像字节级确认）+ vivo 自有证书/信任配置 |
| 自编译 boot 能否直接 `fastboot flash boot` 启动 | **能**（release 安装指南明确） | **不能**（T1/T2 单字节实验卡 logo） |
| 自编译 boot 是否带签名尾部 | **完全不带**（本次字节级实测） | 必须带（本机构成 `L+0x400` 起的 DER + 256B 签名） |

**一句话（2026-11-10 修订）**：真正可确认的差异不是「两套签名架构」，而是 **解锁态下的验证策略** —— 两者封装同属 AOSP BootSignature 体系（PD1610 侧已字节级确认，PD1619 侧仅工具元数据未验证），但 PD1619 解锁后允许无签名 boot，PD1610 `is_unlocked=1` 仍对 `boot[0:L]` 逐字节验签。`alpha/beta`、`keyver` 只是信任根标识（aboot 中 `securebootkey`/`keyver` 字符串 **0 命中**），不是验签策略开关。它**解释了差异，但没有提供 PD1610 的新启动入口**。

## 1. 硬证据 A：PD1619 自编译 boot 没有任何签名结构

解析脚本 `C:\qfilx\exp\pd1619_boot_probe.py`，输出 `C:\qfilx\compare\pd1619\boot_probe_result.txt`。

`boot.img` 来源：release `lineage-16.0-20260711` 的 `boot.img`
大小 35,121,152 B（0x217E800），SHA256 `3be27977e7dc4f21791c2484e4c3c8c59690676b04dca8e0b5c40ebb15a54695`

| 项 | PD1619 自编译 boot | PD1610 1.15.1 基线（对照） |
|---|---|---|
| `page_size` | 2048 | 4096 |
| `kernel_size` / `ramdisk_size` | 33,236,693 / 1,880,398 | 45,194,492 / 7,585,303 |
| `second_size` / `dt_size` | 0 / 0 | 0 / 0 |
| `L = page + ALIGN(kernel) + ALIGN(ramdisk)` | **35,121,152 = 文件大小** | 52,785,152（文件 52,790,528，尾部多 0x1500） |
| `L` 处内容 | **OUT OF RANGE（无尾部）** | `30 82 04 fc 02 01 01 30 82 03 d5 …`（DER SEQUENCE + 证书，serial `F2EC2903803243F0`） |
| `/boot` 字符串 | **0 命中** | 1（`0x32573F1`） |
| `sha256WithRSA` OID | **0 命中** | 1（`0x32573E2`） |
| `scm_beta` | **0 命中** | 4 |
| `AVB0` / `SEANDROIDENFORCE` | 0 / 0 | 0 / 0 |
| 末 4 KB 非零字节 | 2,373（属 ramdisk 内容） | 256（正好是 RSA 签名） |
| FDT magic / `qcom,msm-id` | 106 / 106 | 106 / 106 |

> 注：PD1619 镜像里 `30 82` 出现 130 次、`vivo` 699 次，均为 kernel/DTB 区内的普通二进制/字符串，不构成签名结构；判定依据是 `L` 处无尾部 + `/boot`、OID、`scm_beta` 三项全部 0 命中。两份镜像 kernel 区都有 106 处 FDT magic，说明 QCDT 风格 DTB 链在同厂不同 SoC 上同构（与本项目已提取 PD1610 的 106/122 份 DTB 链一致）。

**推论（2026-11-10 降为「较强推断」）**：PD1619 的自编译 boot 不含任何签名/footer，release 安装指南第 1 条原文为「**Unlock your Bootloader first using the viQOO Tool**」、第 2 条要求官方 8.1 底包，随后才 `fastboot flash boot boot.img` → 该机 aboot 在**已解锁态下不校验 boot 分区内容**。但本轮**未**取得 PD1619 官方 aboot / stock boot、未做反汇编、未追踪解锁状态变量，故不作「已确认」。这与此前 X9 系列教程「刷 Magisk 修补 boot 能进系统」一致，且与 PD1610「改一个字节就卡 logo」形成直接对照。

## 2. 硬证据 B：两代信任根的 cmdline 字段

从 boot header `cmdline @0x40` 直接读取（非推测）：

| 镜像 | `androidboot.securebootkey` | `keyver` | `securebootkeyhash` |
|---|---|---|---|
| PD1619 LOS16 自编译 | `alpha` | `1` | `60ba997fef6da9f05885fa11f1dd6d2a90d052a257a09c2075d7246cc73c0d43` |
| PD1610 1.15.1 | `beta` | `2` | `da758fd52632ba6649d61830a88bbe76a616e4b083b9358b3e98e13772dc139d` |
| PD1610 8.19.16 | `beta` | `2` | 同上 |
| PD1610 stock 7.13.15 | `beta` | `2` | 同上 |

本项目既有记录（`2026-11-09.md:137`、v7.4 第 529/538 行）已确认：PD1610 的 `securebootkeyhash` **等于 aboot 内 `@0x1A2F` 证书的 SHA256**，即该字段是「SBL 认证 aboot 所用信任根」的标识，随 cmdline 传给内核。

因此这里是**两代不同的 vivo 信任根**：`alpha/keyver=1`（X9 Plus 一代）与 `beta/keyver=2`（Xplay6 一代）。X9 教程原文「初步推测原因是 X9/X9i 与 X9 Plus/X9s/X9s Plus 对于 `androidboot.securebootkeyver` 的配置不同」与此吻合。

**边界（重要，2026-11-10 补上静态硬证据）**：这是**相关性，不是机制证明**。本轮检索三份 PD1610 aboot（1.15.1 / 8.19.16 / 16 MB dump）：`securebootkey`、`keyver` **均 0 命中**；`beta` 15 处全部是 `vivo attestation beta CA` / `vivo root beta CA` 证书主题串，`alpha` 2 处全部是 `alpha_pll` 时钟驱动日志 → aboot 不按 cmdline 的 `securebootkey`/`keyver` 字符串切换验签策略，`securebootkey*` 只被确认为信任根标识。字符串 0 命中没有排除间接形式的策略判断（见 v7.4 U1）。改 cmdline 需要改 boot（会被验签），改 aboot 又要过 SBL 认证（本机 11-08 实测改 aboot 变砖、拆机短接救回）。故**不构成新入口**，只作为 v7.4 8.3「同代机型是否存在解锁即关验签」的补充数据点。

## 3. 硬证据 C（**原结论已撤销**）：PD1619 官方 boot 的验证形态未验证

`PD1619_PORTING_NOTES.md` 原文记录 stock boot 解包元数据：

> `sigtype=AVBv1`, `avbtype=boot`, `hashtype=sha1`, `imgtype=AOSP`；用 stock kernel + ramdisk + offsets 重打包成功，但哈希不匹配，「because the AVBv1 signing/footer data is not reproduced」。

**2026-11-10 修正**：`sigtype=AVBv1` 是解包工具对**旧式 Verified Boot / BootSignature footer** 的标注，不是 Android 8 的 AVB 2.0 `vbmeta` 体系；而 AOSP `BootSignature.java` 的 ASN.1 定义与 PD1610 尾部 DER 字段顺序/标签/类型**逐字段对应**。所以「vivo 自有 DER/RSA」这一措辞错误，应为「**AOSP 标准 BootSignature 封装 + vivo 自有证书（`OU/CN=scm_beta`）、RSA-2048 + SHA-256 + PKCS#1 v1.5、公钥编译在 aboot 内 `0x91878F28`**」。PD1619 官方 boot 仅有工具元数据、未取得镜像做字节级验证，故「两套不同代码路径/不同验证对象」的判断**撤销**；能确认的差异是解锁态验证策略。

这解释了 DeepSeek 那句「为什么 vivo 放行了这个 8.1 的 aboot」的概念混淆：**aboot 被 SBL 放行 = vivo 签名有效**，与「aboot 内部是否校验 boot」是两件事。X9 Plus 的 8.1 是官方全量包 + 官方文件管理器升级，教程/release 从头到尾没有替换 aboot、没有重签 boot。

## 4. `wuxianlin` / `suu` / 32 位 magiskinit：三件不同的事

酷安帖 `feed/72735509` 标题「[非官方 自编译] Lineage OS 16.0 For Vivo X9 Plus」，作者 **やえみこ**（= ShionKanagawa，即 X9 解锁教程与 GitHub 仓库作者），发布于 2026-07-11。正文 Credits 与三点技术说明：

| 名词 | 真实身份 | 与 PD1610 的关系 |
|---|---|---|
| `@wuxianlin` | **「反 System 挂载」内核补丁方案贡献者** | 本地此前无记录；与验签、root 提权机制无关 |
| `@酷狗贼` | **「反 su 检测」内核补丁方案贡献者** | 对应 vivo 内核拦截 `su` 二进制 |
| `@某贼` | **viQOO 工具箱**（解锁 BL） | 写 `devinfo`/`frp`，PD1610 已解锁 |
| `suu` | vivo 内核拦截 `su` → Magisk 变体把 `su` 改名 `suu`（Magisk Issue #5148，`vivo-Magisk-suu`） | 仅 root 域 |
| 32-bit `magiskinit` | PD1619 底层环境无法执行 64 位 `magiskinit`，会 bootloop；必须强制 32 位 early init（PID 1 / ramdisk 阶段），64 位 runtime 仍可用 | 帖子自注「同样适用于其他 Vivo Linux 3.x 设备」，PD1610 内核 3.18 属此列，但**只影响 root，不影响启动链** |

**修正本会话 08:20/08:28 的判定**：`wuxianlin` 本地全库 0 命中属实，但外部原文证实确有其人，语义是 anti-System-mount bypass，不是「编造」。DeepSeek 把「32/64 位兼容」当 `suu` 的解释也确有出处（32-bit magiskinit），但那是 PD1619 的 ramdisk 阶段问题，与 `suu`、与 PD1610 验签均无关——三件事被混成了一件。

## 6. 对两个目标的价值判定

| 目标 | 价值 | 说明 |
|---|---|---|
| **A：找到可行启动入口** | **无增量** | 仍是「解释差异，不提供入口」。2026-11-10 补：签名哈希输入已按 AOSP 标准模型 5/5 闭合，验签侧不再有私有格式歧义可利用，反而**加强**此判定。PD1610 的 `beta/keyver=2` 信任根、aboot 内嵌公钥、验签调用点两处、`devinfo is_unlocked` 不被读取，全部未被触动；13.4 四条重启条件一条都不满足 |
| **B：准备可运行的系统** | **有方法论价值** | 该仓库（756 文件，`lineage-16.0` 分支）是一份完整的「**不依赖内核源码、用 prebuilt kernel + 私有 blobs 做类原生**」工程模板：`TARGET_PREBUILT_KERNEL`、`BOARD_KERNEL_IMAGE_NAME := Image.gz-dtb`、`BOARD_KERNEL_CMDLINE`/BASE/PAGESIZE/OFFSETS、`proprietary-files.txt` + `extract-files.sh`、`PD1619_PORTING_NOTES.md` 记录 adb 采集项、`tools/patch-magisk-boot-pd1619.sh` 处理 `skip_initramfs→want_initramfs` 内核补丁与去除 DT fstab verity flags。与本项目「基于原厂 3.18 内核移植 Android」思路一致 |

**但设备树源码本身不可复用**：README 明写基于 `LeEco s2 (MSM8976)` 设备树，内核 3.10.84，非 Treble，`/vendor` 是 `/system/vendor` 软链接；全树 756 个路径中，命中 `pd1610|xplay6|msm8996|sign|verif|unlock|aboot|bootloader` 的只有 `prebuilt/kernel` 一个（且是二进制内核），**没有任何 PD1610 或 MSM8996 内容**。

PD1610 自己的设备树材料反而更齐：已从 8.19.16 boot 的 122 份 DTB 链中定位第 79 份为 `vivo MSM 8996 v3 + PMI8996 PD1610`（409,557 B），并解析出 `qcom,msm-id=<0xf6 0x30001>`、`board-id=<0x1 0xa 0x1000001 0x0>`、`pmic-id=<0x20009 0x10013 0 0>`（见 `PD1610_非传统启动路径与MSM8996内核移植可行性研究.md`）。
