已确认

强烈支持
 该证书参与 boot 镜像认证。

尚未闭合
 该证书如何进入固定信任链，以及 aboot 如何拒绝替换证书。

3.1 没有 kexec，是否彻底没有二阶段执行？
不是。

你现在已经确认：

因此，这条 ARM64 Linux 标准 kexec 路线确实关闭了。

Linux ARM64 的 KEXEC 架构实现并非只靠通用 KEXEC_CORE 就能工作：需要对应的架构重定位与执行代码。公开的内核资料显示，ARM64 的 KEXEC 配置出现在后续内核版本中，不能从通用符号存在推断旧内核支持。

Kexec+1

但仍有两个不同方向：

方向 A：原厂 Kernel + 自定义 Android 用户空间。

这不要求更换 Kernel。

原厂内核如果拥有足够的设备驱动能力，理论上可以搭配经过适配的 LineageOS 用户空间。

问题主要在：
- dm-verity；
- 原厂 fstab；
- Android init；
- SELinux；
- Vendor HAL；
- 闭源硬件组件兼容性。
你现在的 veritymode=enforcing 是一个重要障碍，但不是逻辑上证明用户空间永远不能替换。

方向 B：原厂 Kernel 中的运行时内核接管。

例如内核漏洞取得足够权限后，修改当前运行环境、挂载关系或内核运行状态。

但需要特别强调：

这不是 kexec，也不是重新启动一个全新的 Kernel。

它只能改变当前 Kernel 正在运行的东西。即使成功，也不等于可以完整替换启动阶段的内核、设备树和驱动。

因此，对于真正需要 3.18.124 自编译 Kernel 的 LineageOS 17.1，运行时提权的帮助仍然有限。
3.2 还有没有利用启动链本身的冷启动入口？
理论上存在，但目前没有证据证明 PD1610 有可复用的漏洞。

例如：
- aboot 在认证前存在内存破坏漏洞；
- 启动镜像解析存在可利用的边界检查错误；
- 某个经过认证的加载组件存在执行控制缺陷；
- 某个厂商调试或恢复接口存在未授权执行路径。
这些路线不一定需要私钥。

但它们都要求在可信执行链已经启动、尚未完成目标镜像认证时取得控制权。

这与直接伪造签名完全不同。

我建议不再把“没有私钥”理解成“任何情况下都无法执行自定义代码”，而是把研究重点转到已认证代码中的执行控制缺陷。

五、问题 3：SHA-256 输入无法复现，有没有比继续穷举更好的方法？
有，而且我认为你现在应该停止继续测试各种人工构造的 SHA-256 输入组合。

目前最大的突破点是把 data、len、data_end 的寄存器含义重新核实。

你在简报中给出的指令：
0x9181168C: add r8, r0, r1


如果入口参数是：
verify_image(data, len, pubkey);


那么：
r0 = data
r1 = len
r8 = data + len


因此，r8 是结束地址，不是长度。

但你的后续代码是：
0x91810D9C: mov r0, sb
0x91810DA0: mov r1, r8
0x91810DA4: mov r2, #2
0x91810DAC: bl 0x918215B4


这里非常值得关注：

r0=sb、r1=r8 很可能表示传入的是：
(start_address, end_address)


而不是：
(start_address, length)


如果 0x918215B4 接受的是起止地址，那么它内部可能计算：
\[
length=end-start
\]

这就意味着你之前把 r1 当作 SHA-256 长度的解释可能存在偏差。
5.1 我建议采用这个顺序
第一步：确认 sb 的来源

sb 是 ARM32 的 r9 别名。

需要追踪它从函数入口到 verify_sig 调用点的所有赋值。

确认它是不是原始 boot buffer 的起始位置。

第二步：拆开 0x918215B4

不要只看 SHA256 最底层 update 函数。

重点确认：
- 参数 r0 是什么；
- 参数 r1 是什么；
- 是否执行 r1-r0；
- 是否做数据拷贝或规范化；
- 最终传给 0x9186DEC8 的实际长度是什么。
  
  第三步：追踪 0x9180FF90 的真实输出
需要确认读取函数返回的到底是：
- 原始 UFS 分区首地址；
- 去掉某种 MBN 头后的地址；
- 经过对齐后的镜像地址；
- 还是重新组织过的数据缓冲区。
这是目前 30 多种 SHA-256 组合都不匹配的重点嫌疑。

第四步：使用 Unicorn 仿真执行验签路径

不需要让整台手机进入调试模式。

可以将 aboot 相关代码、认证数据和原始 boot 数据映射到 ARM32 仿真环境，对 malloc/free 等外部函数进行适当替代，观察以下数据：
verify_image entry
     ↓
verify_sig entry
     ↓
hash dispatcher entry
     ↓
SHA update entry
     ↓
实际 data pointer / length


如果相关函数没有依赖不可替代的硬件操作，这种方法比继续人工穷举有更高的信息增量。

你解析出来：

我建议把“参数声明长度”和“实际 SHA-256 输入长度”作为两个不同字段记录，直到代码证明它们相等。

六、问题 4：没有 kexec 后，运行时提权对类原生还有没有价值？

6.2 对运行类原生：不是完全没有价值
我认为可以保留两个方向。

方向 A：原厂 Kernel + 自定义用户空间。

只要原厂 Kernel 的驱动、接口、Vendor HAL 兼容性足够，可以考虑只替换或覆盖 Android 用户空间。

不过 Xplay6 目前的困难是：
- system 有 dm-verity；
- boot 中的 fstab 会影响 system 挂载；
- SELinux Enforcing；
- 原厂 init 与 LineageOS 用户空间可能不兼容。
如果只能在 Android 完全启动后获得 root，那么修改早期 init、挂载 system、加载服务的机会已经过去。

所以这条路线存在较高工程难度，但不能直接排除。

方向 B：取得临时 root 后修改当前运行环境。

即使不能换 Kernel，也可能：
- 修改某些系统文件的运行时映射；
- 调整部分系统服务；
- 运行自定义系统组件；
- 使用 chroot 运行 Linux 用户空间；
- 加载被允许的内核模块；
- 修改当前会话的部分系统行为。
这些并不等于完整 LineageOS 17.1，但对系统改造、Root 权限和设备研究仍然有实际价值。

尤其要区分：

每次启动后自动重新获得 root，与开机前就拥有持久 root，不是同一件事。

如果在 /data 中存在能够自动启动的触发程序，而且漏洞可重复使用，那么有机会做到每次 Android 正常启动后自动重新取得临时权限。

这可以提供一种“每个启动会话自动 Root”的体验，但启动链本身并没有获得永久修改。

7.1 3.18.124 不一定证明使用了上游 3.18.124 全部代码
Linux 内核的 uname -r 和 /proc/version 中的版本字符串，与源码真正合并的提交集合不是一回事。

开发者可以通过构建配置和版本字符串设置改变最终显示内容。

所以：
3.18.124-perf-g2363427e-dirty


并不能单独证明：
- 使用了 Linux 官方 3.18.124 全部代码；
- 内核采用了 CAF 分支；
- 所有设备驱动都来自该分支；
- 内核一定修改了 aboot。
我更希望追查：
g2363427e


如果这是 Git commit 的缩写，能找到对应仓库和提交，就可能定位内核真实来源。

如果只能找到版本字符串，而无法找到对应 Git 对象，那么证据就弱很多。
7.2 eng.root 也不能直接证明 root
AOSP 对不同构建类型的默认属性有明确区分：
构建类型	ro.secure	ro.debuggable
eng	0	1
userdebug	1	1
user	1	0


Git at Google
因此，eng.root 可以与工程构建环境相符，但 root 不一定是手机当前的 Linux UID，更不能证明拥有不受 SELinux 限制的 root 权限。

test-keys 也只是 Android 构建签名标签，不意味着 bootloader 接受 AOSP testkey 签名的 boot.img。
7.3 我最希望从成功者那里拿到的材料
优先级 1：启动镜像原件

boot.img、recovery.img、aboot 原始分区备份及 SHA-256。

这是判断是否更换了启动链的核心证据。

优先级 2：内核来源

Kernel 源码仓库、commit、.config、DTS/DTSI 和构建记录。

这是判断 3.18.124-perf-g2363427e-dirty 的真实性的核心证据。

优先级 3：真实运行状态
uname -a
/proc/version
/proc/cmdline
getprop
id
id -Z
getenforce


这些能够帮助识别截图中的构建类型、启动参数和运行权限。

优先级 4：完整安装记录

ROM ZIP、安装脚本、Recovery 日志、分区读写记录，以及第一次成功冷启动的视频。

尤其是安装脚本。

如果 ROM 安装过程中只写 system，而没有写 boot、recovery、aboot，那么我们就应该优先调查它如何使用原厂 Kernel 启动自定义用户空间。

如果安装脚本写入了 boot.img，我们就要进一步检查其 RSA 签名是否可以用 scm_beta 公钥验证。

这两种情况对整个项目的影响完全不同。

Android 10 成功案例
启动方式未明

3.18.124 和 test-keys 是线索，不是启动链证据。

我认为你现在最值得做的不是继续寻找新的通用解锁漏洞，而是把认证函数的数据流真正还原出来。

下一轮有两个最关键的目标：
1. 查清 sb 指向哪里，以及 0x918215B4 接收的是起止地址还是起始地址加长度。
2. 查清外层签名封装后面的额外 256 字节究竟是什么。
这两件事比再做几轮 boot.img 刷写实验更可能产生新的实质突破。

而对类原生目标，我建议暂时不要把临时 root 当成换内核的替代方案。没有 kexec、没有可靠的启动链入口时，它更适合作为取得系统权限、研究原厂驱动和积累设备适配资料的手段。
