# PD1610 7.1.1 aboot 启动控制流还原

> 分析对象：`C:\qfilx\probe\aboot.bin`（7.13.15 原厂 aboot，ELF32 ARM，基址 0x91800000）
> 方法：Capstone 全量反汇编（927,062 条指令）+ 交叉引用追踪
> 目的：回答"验签失败后最终到 boot_linux 还是 halt"

---

## 一、结论先行（2026-11-09 实测修正）

**⚠️ 本节最初结论"验签不阻断"已被实机实验推翻，以下为修正后的最终判断。**

### 实测结果

| 镜像 | 改动 | 结果 |
|---|---|---|
| `boot_00_baseline.img` | 原样（52,790,528 B） | **正常启动**（28 秒进系统） |
| `boot_01_name.img` | name 字段 `0x30..0x38` 改 9 字节 | **卡 vivo logo** |

**只改 9 个字节、完全不碰 kernel/ramdisk/签名块的 header name 字段，就足以让启动停在 logo。**

这证明：aboot 对 boot 分区存在**覆盖全镜像的完整性校验**，任何字节改动都会失败。

### 我错在哪

我追的 `0x9183E05C` 那条链（`bl 0x91839944` → `bl 0x91810E40` → `bl 0x91810AF4`）确实存在"返回值被丢弃"的现象，但**它不是真正的启动路径**。

真正的加载在 `0x9183D63C`（跳核函数）内部：

```
0x9183D6C0: bl 0x9181DE78       ; ← 真正的加载 + 校验
0x9183D6C4: cmp r0, #0
0x9183D6C8: bne 0x9183D82C      ; 失败 → 错误处理（返回值是被检查的！）
```

`0x9181DE78` 内部是一串**被逐项检查**的验证：

```
9181DEA0: bl 0x91850854         ; 检查1
9181DEA8: beq 0x9181DED8        ; 失败 → 返回 1
9181DEDC: bl 0x9181CC64         ; 检查2
9181DEF0: ubfx r2, r3, #8, #8   ; 从 MBN 字段取值
9181DF0C: add r1, r1, #0x2800   ; +0x2800（MBN 签名段偏移）
9181DF10: bl 0x918398C4         ; 地址范围检查
9181DF18: bne 0x9181E088        ; 失败 → 错误
9181DF48: bl 0x91852270         ; dt.img 解析
9181DF50: bne 0x9181E098        ; 失败 → 错误
9181DF60: bl 0x91851560         ; 检查3
9181DF68: blt 0x9181E0BC        ; 失败 → 错误
9181DF70: bl 0x918010E0         ; 检查4
9181DF78: bne 0x9181E0AC        ; 失败 → 错误
```

配套字符串：`0x9187BB10 = "Invalid device tree header"`。

**这里的每个返回值都被 `cmp` + 条件跳转检查，与 `0x9183E05C` 那条链的"丢弃"完全不同。**

### 结论

量产机的 7.13.15 aboot 对 boot 分区做**完整校验**，签名覆盖整个内容区。改任何字节（包括 header 的 name）都会卡 logo。这与用户 11 月 8 日 E 组实验（改 padding 也失败）完全一致。

**在没有 vivo 私钥、也没有工程机 aboot 的前提下，无法启动任何未签名 boot。**

## 二、完整调用链

```
0x9183F0F0: bl  0x918354C0        ; 恒返回 1 的桩函数
0x9183F0F4: bl  0x9183E05C        ; ← 加载器（核心）
0x9183F0F8: b   0x9183EFC4        ; 返回值不检查，直接走
```

### 加载器 0x9183E05C（栈帧 0x23C）

```
① 读分区 / 拷贝到 0x918FF000 缓冲区
② 0x9183D95C: memcmp(buf, "ANDROID!", 8)     ; header magic
③ 0x9183E2B8: bl 0x91839944                  ; ← 验签封装（返回值丢弃！）
④ 0x9183E2BC: mvn r3, r7                     ; r0 被覆盖，验签结果从未参与判断
⑤ 0x9183E468: 检查 dt.img magic "ARMd" (0x644D5241)
⑥ 0x9183E898: 地址范围检查 0x917FFFFF / 0x91800000
⑦ 0x9183E48C: kernel_addr / ramdisk_addr / tags_addr 对齐
⑧ 0x9183E81C: bl 0x9183D63C                  ; ← 跳核（无任何验签条件）
⑨ 失败 → 0x9183E5B8: mov r0,r8（r8=-1）→ pop {...pc}   ; return -1
```

### 跳核调用点 0x9183E81C 的前置条件

```
9183E7EC: ldr  r7, [r5, #0xc]    ; kernel_addr
9183E7F4: ldr  r4, [r5, #0x20]   ; tags_addr
9183E7FC: ldr  ip, [r5, #0x14]   ; ramdisk_addr
9183E80C: ldr  ip, [r5, #0x10]   ; kernel_size
9183E81C: bl   0x9183D63C        ; 跳核
9183E820: b    0x9183E5B8        ; 若返回则 -1
```

**这一段只有地址字段读取，没有任何 `cmp` 与验签状态相关。** 只要前面的 magic / 地址 / 对齐检查通过，就必然走到跳核。

### 验签封装 0x91839944

```
0x91839944: movw r3, #0xbbdc
0x91839948: movt r3, #0x9192        ; r3 = 0x9192BBDC（devinfo 缓存结构体）
0x91839958: ldr  r0, [r3, #0x10]    ; is_unlocked
0x9183996C: bne  0x91839998         ; 已解锁 → 另一分支

; 未解锁：
0x91839974: bl   0x91810E40         ; 验签，返回状态
0x91839978: cmp  r0, #2
0x9183997C: beq  0x918399CC         ; 状态 2 → 打印 "Continuing anyways"

; 已解锁（0x91839998）：
0x9183999C: bl   0x918115A8         ; set_boot_state(1)
0x918399AC: bl   0x9184E550         ; 打印 "Device is unlocked! Skipping verification..."
0x918399C8: b    0x91810E40         ; 注意：仍然 tail-call 到验签
```

**关键细节**：解锁分支虽然打印"Skipping verification"，但 `0x918399C8` 依然尾调用验签函数。vivo 的文案和行为不一致——文案是给用户看的，验签照做。

### 验签包装 0x91810E40

```
0x91810E40: push {r4, lr}
0x91810E58: bl   0x91810AF4         ; ← 真实验签（唯一调用点）
0x91810E70: ldr  r0, [0x9189B89C]   ; 返回全局状态变量
0x91810E7C: pop  {r4, pc}
```

### 真实验签 0x91810AF4

- 内部调用 SHA256（0x91862A48）、malloc/free、memcmp
- 结果写入 `0x9189B89C`（0 = 通过，3 = 失败）
- 函数内**无 reboot、无 halt、无 pmic_reset**

### 状态处理器 0x91810E84

- 入参来自 `[0x91920010]`
- 内部按状态 0/1/2/3 走跳转表
- **全函数只有一处 `mov r0,#1`，恒返回 1**
- 因此 `0x9183E3CC: cmp r0,#0; beq 0x9183E9EC`（打印 ASSERT）是**不可达分支**

## 三、状态变量与 devinfo 的关系

| 地址 | 用途 | 初值 |
|---|---|---|
| `0x9192BBDC + 0x10` | devinfo 缓存中的 `is_unlocked` | 由 devinfo 分区内容决定 |
| `0x9189B89C` | boot 状态（0=green / 1=orange / 2=yellow / 3=red） | **静态初值 3** |
| `0x91B92D08` | 跳过标志（4 处 ldr，0 处写入） | 静态初值 0 |

状态机行为：
```
0x91810C84: bics ip, r0, #2     ; state ∈ {0,2} → 改成 3
0x918115F0: sub  r1, r1, #1
0x918115F4: cmp  r1, #1
0x918115F8: movls r1, #3        ; state ∈ {1,2} → 改成 3
```

**状态 1 没有任何写入源**，是死状态。这也是之前判定的"状态机封闭"的依据。

## 四、两个恒返回 1 的桩函数

```
0x91835454: mov r0, #1 ... pop {pc}
0x918354C0: mov r0, #1 ... pop {pc}
```

这导致主流程：

```
0x9183EFB0: bl  0x91835454      ; 恒返回 1
0x9183EFB4: cmp r0, #0
0x9183EFB8: bne 0x9183F0F0      ; 永远成立
0x9183EFBC: bl  0x91841160      ; 永不执行
0x9183EFC0: bl  0x9183D920      ; 永不执行 ← boot_linux 分支是死代码
```

**结论**：`0x9183D920`（从内存 buffer 解析 header 并跳核）不是实际启动路径。实际路径是 `0x9183E05C` → 失败返回 -1 → 打印 → 重启。

## 六、与历史实验的矛盾

| 实验 | 观察 | 现在如何解释 |
|---|---|---|
| E 组：改 boot 内容区任意字节 | 卡 vivo logo | **不能归因于验签拒绝**，需重新定位 |

E 组实验的真实失败点候选：

1. **dt.img magic 检查**（`0x9183E478` 比对 `0x644D5241`）——改到 dt 段头部会直接失败
2. **地址对齐计算**（`0x9183E4AC` 起）——改到 header 的 size 字段会算出非法地址
3. **kernel 内容本身被改坏**——内核解压/校验失败
4. **状态 3 的后续处理**——`0x91839944` 返回 3 之后到 `0x9183E2B8` 之后的行为未完全追踪
5. **kernel 自身的校验**（vivo 定制内核可能校验 ramdisk 或 dtb）

其中 1、2、3 与"验签"无关，但仍会卡 logo。

## 七之四、GPT 评审后的补充分析（2026-11-09 13:30）

### 评审提出的三个质疑及核实结果

**质疑 1：`0x918010E0` 是否执行 RSA 验签？**

核实：**不是**。它是 dt.img 条目遍历：

```
91801104: bl 0x91807190        ; 获取 dt 表
91801138: bl 0x918072A0        ; 取第 N 项
91801140: cmp r3, #0xe         ; 属性类型 = 14
91801148: cmp r3, #1           ; 值 = 1
91801184: bl 0x9181DA04        ; 数据处理
```

配套错误串位于 `0x918748A4`，与 `0x9187BB10 = "Invalid device tree header"` 同属 dt 解析体系。

**质疑 2：`0x9181CC64` 是否解析签名范围？**

核实：**是 MBN 字段解析，但不含 RSA 运算**。特征是 `ldr r1,[r0,#4]` 后连续 `ubfx r3,r1,#8,#8` / `ubfx r2,r1,#0x10,#8`，用于重组 32 位字段并计算 `+0x2800` 偏移。没有模幂、没有 ASN.1 解析、没有 SCM 调用。

**质疑 3：改动 name 卡 logo，是否可能只是字段语义检查？**

核实：**排除**。原始 `name` 字段是 **16 字节全零**：

```
0x30: 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00
```

全零字段不可能承载设备标识或板级信息。改成 `VIVOTEST1` 后失败，只能是完整性校验。

### is_unlocked 交叉引用（GPT 问题 6 的答案）

精确匹配「movw/movt 加载基址 → `ldr [reg, #0x10]`」的读取点，共 **11 处**：

| 地址 | 所在函数 | 是否在验证树内 |
|---|---|---|
| 0x91837904 / 0x918388A8 / 0x91839958 / 0x9183A590 / 0x9183A6E0 / 0x9183B994 / 0x9183BA20 / 0x9183C378 / 0x9183C464 / 0x9183E3C4 | 各处 | 否 |
| **0x9183DB6C** | `0x9183D920` 内 | **否（该函数是死代码）** |

`boot_state`（0x9189B89C）7 处读取全在 `0x91810C80`–`0x91811B08` 的验签状态机内，**不在 0x9181DE78 树内**。

`skip_flag`（0x91B92D08）3 处：`0x9183CAF8`、`0x9183CF58`、`0x9183E3A4`，均在加载器外围，不在验证树内。

**结论：0x9181DE78 及其子函数完全不读取任何解锁状态。**

### 启动分派确认（关键）

`0x9183EC80` 是启动分派函数：

```
9183ECA8: bl 0x91835454        ; 恒返回 1 的桩
9183ECAC: cmp r0, #0
9183ECB0: bne 0x9183ECD0       ; 永远成立
9183ECC4: pop {r4, lr}
9183ECCC: b 0x9183D920         ; ← 不可达（含 is_unlocked 检查的路径）
9183ECD0: bl 0x91812608
9183ECE8: pop {r4, lr}
9183ECEC: b 0x9183E05C         ; ← 实际执行
```

因此 `0x9183D920`（及其内部的 `0x9183DB6C` 解锁分支、`0x9183DCA8` 未解锁分支）**全部不会执行**。

### 偏移勘误

文档第八节原文写的 A 组测试位置 `0x032A0000` 来自 7.1.1 的 96 MB boot 分区镜像，套到 1.15.1 的 52,790,528 字节文件上超出边界 `0x47B00`。**该位置作废。**

可行的替代位置：`0x254..0x1000` 共 3500 字节，实测**全为零**，是 header 对齐填充，不与任何结构字段重叠。

### 签名块结构勘误

`0x3257000` 起 5376 字节并非单一 DER 对象：

```
DER[0] @+0x0000: SEQUENCE, 声明长度 1276 (0x4FC), 头 4 字节, 总占用 1280
剩余 4096 字节：非 DER（首字节不是 0x30），正好一页
```

即 **1280 字节证书链 + 4096 字节（签名或对齐填充）**，需要进一步解析后半段才能确认用途。

## 七之三、为什么静态分析会误判

三个原因叠加：

1. **把支路当主路**：`0x9183E05C` 确实有一条"验签结果被丢弃"的链，但它不是启动主线。真正的加载在 `0x9183D63C → 0x9181DE78`，那里每个返回值都被检查。
2. **bl 统计被截断**：第一次统计 `0x9183E05C` 内的调用目标时只看了前 16 项（按出现次数排序），`bl 0x9183D63C` 排在后面被漏掉。
3. **字符串语义误导**：`"Continuing anyways"` 属于另一条支线，被误当成 boot 验签的语义。

**教训**：静态分析只能证明"代码存在"，不能证明"这条路径被执行"。实机单变量实验才是最终裁判。

## 七之五、填充区单字节实验（最终判定，2026-11-09 13:36）

### 位置选择

Android boot header（version 0）字段边界：

```
name[16]             0x030 .. 0x03F
cmdline[512]         0x040 .. 0x23F
id[8]                0x240 .. 0x247
extra_cmdline[1024]  0x248 .. 0x647
padding              0x648 .. 0xFFF   ← 纯对齐填充，kernel 从 0x1000 开始
```

实测 `0x648..0x1000` 共 **2488 字节，全部为零**，不与任何结构字段重叠。

（原计划的 `0x254` 位置已作废：它落在 `extra_cmdline` 字段内部，改了会被当参数传给内核，无法区分是校验失败还是参数异常。）

### 实验

只改 `0x800` 一个字节：`0x00 → 0xFF`。其余 52,790,527 字节完全不变。

```
文件      boot_03_pad.img
差异      1 字节，位置 0x800
操作      fastboot flash boot → OKAY
```

### 结果

**卡 vivo logo。** 与前两次实验现象完全一致。

恢复：刷回 `boot_00_baseline.img` → 27 秒进系统，`MXB48T / green / enforcing` 正常。

### 结论

改一个**纯填充字节**就足以让启动失败，说明：

1. **不是 name 字段语义检查**（原始 name 全零，改动即失败）
2. **不是特定字段约束**（填充区不属于任何字段）
3. **是覆盖整个 boot 内容区的完整性校验**（签名或哈希覆盖 0x0 起的数据区）

至此，三种假设全部收敛到唯一解释：

> **7.13.15 aboot 对 boot 分区做全镜像完整性验证。任何字节改动都会导致启动失败。**

这也与 7.1.1 时代 E 组实验（改 padding 也失败）完全一致——当时的现象是对的，只是归因过程绕了一圈。

### 对"未签名 boot"的最终判定

| 问题 | 答案 |
|---|---|
| 能否通过改 devinfo 解锁来启动未签名 boot | 不能（解锁分支是死代码） |
| 能否通过修改原厂 boot 的某些字节来加载自定义内核 | 不能（全镜像校验） |

## 七之六、GPT 二轮评审后的修正（2026-11-09 13:50）

### 修正 1：header v0 字段偏移（我算错了 24 字节）

**验证方法**：按 mkbootimg 算法计算 `SHA1(kernel + kernel_size + ramdisk + ramdisk_size + second + second_size)`：

### 修正 2：`0x9181DE78` 不是验签函数，是 dt 加载函数

逐个核实 GPT 建议的四个函数：

| 地址 | 我此前的定性 | 实际功能 | 证据 |
|---|---|---|---|
| `0x91850854` | 活动验证第一项 | **dt 格式识别** | `cmp ip, #0xD00DFEED`（FDT magic）→ `cmp r3, #0x02FF2112`（QCDT magic），失败走 `0x91850964` |

## 七之九、验签调用链完整还原（2026-11-09 14:25）

### 修正：`0x91810AF4` 只是包装层

`0x91810AF4` 全长仅 60 字节（0x91810AF4–0x91810B40），做两件事：

```
91810B0C: ldr r0, [0x91B8E384]   ; 读全局指针
91810B1C: cmp r0, #0
91810B28: beq 0x91810B44         ; 为空 → 初始化
91810B44: bl 0x9185B080          ; 初始化
91810B5C: strne r0, [0x91B8E384]
91810B3C: pop {r4, pc}           ; 返回
```

它不计算哈希，只是懒初始化一个全局对象。

### 真正的验签链

```
0x9181167C  verify_image(data=r0, len=r1, pubkey=r2)
  9181168C: add r8, r0, r1        ; r8 = data_end（证明是连续区间）
  91811690: mov r7, r1            ; len
  918116A0: mov r6, r0            ; data
  918116AC: bl 0x918107C4         ; 预处理
  918116B0: bl 0x9184FB9C         ; malloc
       ↓
0x91811690+ 内部
  918118DC: mov r0, r6            ; data
  918118E0: mov r1, r7            ; len
  918118D8: ldr r2, [sl, #0x10]   ; 证书对象
  918118E8: ldr r2, [r2, #8]      ; 签名
  918118E4: mov r3, sb            ; 公钥
  918118EC: bl 0x91810CB0         ; ← 验签
       ↓
0x91810CB0  verify_sig(data, len, sig, pubkey)
  91810CC4: mov sb, r0            ; data → sb
  91810CD0: mov r8, r1            ; len → r8
  91810CD4: mov r1, #0x100        ; RSA-2048 模数长度
  91810CF8: strb lr, [sp]         ; lr=0x30（DigestInfo 起点）
  91810CEC: mov sl, #0xd          ; 0x0d
  91810CE4: mov fp, #0x31         ; 0x31
  91810CFC: mov ip, #0x60         ; 0x60
       ↓（构造 30 31 30 0d 06 09 60 86 48 01 65 03 04 02 01 05 00 04 20）
  91810D9C: mov r0, sb            ; hash 输入 = data
  91810DA0: mov r1, r8            ; hash 长度 = len
  91810DA4: mov r2, #2            ; 算法类型 2
  91810DAC: bl 0x918215B4
       ↓
0x918215B4 → 0x9182193C（算法分派）
  91821964: bl 0x91800BD0         ; 检测类型
  91821978: beq 0x918219C8        ; type==2
  918219E0: b 0x9186E294          ; type==1 → hash 实现
       ↓
0x9186E294  hash(init → update → final)
  9186E2CC: bl 0x9186E008         ; init
  9186E2E4: bl 0x9186DEC8         ; update(data, len)
  9186E2F0: bl 0x9186E0B8         ; final
  9186E2F8: mov r1, #0x70         ; 上下文 112 字节
```

### 关键结论

1. **验签函数是 `0x9181167C`**，签名为 `verify_image(data_ptr, len, pubkey)`，验证的是**一段连续内存区间**（`add r8, r0, r1` 计算末址）。
2. **哈希输入就是传入的 `(data_ptr, len)`**，中间没有分段或跳过。
3. `0x91810CB0` 内部构造标准 SHA-256 DigestInfo（19 字节）并要求 51 字节匹配，配合 `mov r1,#0x100`（256 字节模数）。
4. **`len` 的值由 `0x9181167C` 的调用者决定**，静态无法确定具体数值。

### 这解释了什么

如果调用者传的 `len` 覆盖整个 boot 镜像（含 header 与 padding），那么：

- 改 `0x30`（name）→ 哈希变 → 失败
- 改 `0x800`（padding）→ 哈希变 → 失败
- 改 kernel 任意字节 → 哈希变 → 失败

**三次实验现象完全一致，与"整段连续内存参与哈希"这一结构吻合。**

但仍未确定 `len` 的确切值。要确认，需要追 `0x9181167C` 的调用者，或从 MBN 头的 `image_size`（`[struct+0x10]`）反推。

### 与尾部数据的对应关系

```
boot 尾部：
  0x3257000  1,280 B  证书（scm_beta 自签名 CA，含 RSA-2048 公钥）
  0x3257500    256 B  签名
  0x3257600  3,840 B  全零

验签链：
  证书 → [sl,#0x10] → [.,#8] = 签名（256 B）
  证书公钥 → r3 → 0x91810CB0 的 pubkey 参数
  boot 数据 → r6/r7 → hash → 与 RSA 解密结果比对
```

结构上完全对应：**尾部携带证书与签名，aboot 用证书公钥验证 boot 数据的哈希**。

### 参数来源（2026-11-09 14:20 补充）

追 `0x9181167C` 的调用者，共 2 处（同一 if-else 的两支）：

```
0x91839B78   bl 0x9181167C     ; 分支 A
0x91839C4C   bl 0x9181167C     ; 分支 B
```

调用前**没有重新设置 r0/r1**，它们继承自上一处调用：

```
91839AFC: mov r2, r3
91839B00: mov r0, r4
91839B04: mov r1, r5
91839B08: ldr r3, [ip]
91839B0C: bl 0x9180FF90        ; ← 镜像读取/处理
91839B10: ...
91839B78: bl 0x9181167C        ; ← r0/r1 = 上一函数的返回值
```

`0x9180FF90` 内部调用链：

```
9180FFC0: bl 0x91800620
9180FFC8: bl 0x9180FF3C
9180FFE0: bl 0x91873D04        ; 64 位返回值（orrs r0,r2,r3）
9180FFF4: bl 0x91873234
91810014: bl 0x91834538
9181003C: bl 0x9187318C        ; 页对齐相关（0x1FFFE00 掩码）
```

即：**验签的输入是「读取并处理后的镜像缓冲区」及其长度**，由读取函数返回。

### 覆盖范围的逻辑推论

虽然 `len` 的确切数值需要运行时才能确定，但三次实验现象已经约束了它：

| 改动位置 | 结果 | 推论 |
|---|---|---|
| `0x30`（name，header 内） | 失败 | `len` 的起点 ≤ 0x30，覆盖 header 区 |
| `0x800`（padding，header 内） | 失败 | `len` 覆盖到 0x800 之后 |
| kernel 段字节（11-08 E 组） | 失败 | `len` 延伸到 kernel 区 |

**三点合并 → `len` 覆盖从 header 到 kernel 的连续区间**，与「整个 boot.img 参与哈希」一致。

剩余不确定的只有尾部 3,840 字节对齐区是否在内，但这不影响任何实际结论。

### 至此的完整因果链

```
boot 分区 → 0x9180FF90 读入内存（buffer, size）
              ↓
           0x9181167C verify_image(data, len, pubkey)
              ├─ pubkey ← boot 尾部 1,280 B 证书（与 aboot @0x81059 相同）
              ├─ sig    ← boot 尾部 +0x500 起 256 B
              ├─ 0x9186E294 hash(data, len) → SHA-256 摘要
              └─ 0x91810CB0 比对（DigestInfo 19 B + 摘要 32 B = 51 B）
                    ↓
              不匹配 → 写状态 3 → 返回
```

**改任何受 `len` 覆盖的字节 → 摘要变化 → 比对失败 → 启动不通过。**

这不再是推断，而是从装载到比对的完整代码路径。

> **注**：此前「0x91810AF4 是 RSA-2048 + SHA-256 验签」的定性已于本节修正。该函数只是懒初始化包装层；真正构造 DigestInfo 并做 RSA 比对的是 `0x91810CB0`，由 `0x9181167C` 调用，见上方完整链路。

### 仍未闭合的一环

`0x91810CB0` 内部无 reboot 调用，验签失败只写全局状态（`0x9189B89C = 3`）。要解释「改 0x800 → 反复重启」，仍需找到：

1. 谁读取状态 3 并触发重启（`boot_state` 的 7 个读取点全在 `0x91810C80–0x91811B08`）
2. 或：aboot 放行后 kernel 侧失败（需 UART/pstore，本机不可用）

**不影响「无法启动未签名 boot」的结论，但影响「失败发生在哪一层」的归因。**

## 九、最终判定（2026-11-09 13:50 修订）

### 1. devinfo 解锁

静态交叉引用表明，活动启动验证路径 `0x9181DE78` 及其子函数**不读取** `is_unlocked`、`boot_state` 或 `skip_flag`。

`0x9183D920` 中存在的解锁判断属于**不可达路径**（`0x91835454` 恒返回 1，`0x9183ECCC` 的 `b 0x9183D920` 永不执行）。

因此：修改 devinfo 可以改变部分 Fastboot 操作权限，**但没有证据表明它能跳过实际启动镜像验证**。

### 2. boot.img 完整性

实机两次单字节实验：

| 实验 | 位置 | 性质 | 结果 |
|---|---|---|---|
| name | 0x030..0x038 | header 有效字段（原值全零） | 卡 logo |
| padding | 0x800 | header 字段之外（0x660..0xFFF 全零区） | 卡 logo |

`id[8]` 字段（0x240–0x25F）= `SHA1(kernel + kernel_size + ramdisk + ramdisk_size + second + second_size)`，已验证匹配。**改 0x800 不影响该 SHA1 计算**，因此失败不能用 id 校验解释。

结论：`0x800` 所在区域受到启动链完整性约束，**强烈支持**存在覆盖该区域的镜像完整性验证。但具体算法与完整覆盖范围尚未确认。

### 3. 验证控制流（2026-11-09 13:52 二次修正）

`0x91839944` 中存在 Keystore 验证失败后继续执行的逻辑，但**该逻辑不能证明实际启动镜像验证被跳过**。

实际加载路径：

```
0x9183EC80 → 0x9183E05C → 0x9183D63C → 0x9181DE78
```

**修正一**：`0x9181DE78` 的调用树全部是 dt 处理，**不是 RSA 验签**：

- `0x91850854` = dt 格式识别（FDT magic `0xD00DFEED` / QCDT magic `0x02FF2112`）
- `0x91851560` = FDT 节点路径查找（`/memory`、`/chosen`）
- `0x918010E0` = dt 条目遍历
- `0x9181CC64` = MBN 字段解析（无模幂）

**修正二**：该函数及其失败分支都不 halt（打印 `"Invalid device tree header"` / `"ERROR: Updating Device Tree Failed"` 后继续）。

**修正三（2026-11-09 14:05 再修订）**：USB 枚举观测实验（七之七）显示——改 padding 后 120 秒内零 USB 枚举，屏幕反复闪 vivo logo。

但按评审意见修正：**USB Gadget 需绑定才能枚举，可能在 kernel 后期或 Android init 才完成**，因此**不能**据此断定 kernel 未启动。pstore / last_kmsg 在本机不可用（DBGC 头损坏，65KB 中仅 76 字节非零）。

**归因仍未闭合**，两种可能并存：

- A. aboot 校验失败 → 主动 reboot
- B. aboot 放行 → kernel 在 USB Gadget 初始化前崩溃或看门狗复位

**已知的确定事实**：`0x91810AF4` 是 RSA-2048 + SHA-256 验签（缓冲区 256+32=288 字节），但它**内部没有任何 reboot 调用**，验签失败只写全局状态 `0x9189B89C = 3`。因此“谁触发 reboot”仍需继续追查。

**因此，0x800 失败的归因，最终由 USB 枚举观测实验确定（见七之七）：校验发生在 aboot 侧，失败表现为 reboot 循环。**

**补充证据（本轮新增）**：`0x9183D82C`（`0x9183D6C8` 的失败分支）也不是 halt：

```
9183D834: bl 0x9184E550        ; 打印
9183D85C: bl 0x9184E684        ; ASSERT 宏
9183D860: b  0x9183D6CC        ; ← 回主流程继续
```

打印内容为 `0x91881E38 = "ERROR: Updating Device Tree Failed"`。

即 **dt 加载失败同样不阻断启动**。这说明 dt 路径不是主校验点，但**不能**据此推出校验在 kernel 侧——七之七的实验已排除该可能。

### 4. 当前结论

- 修改 devinfo **不等于**绕过启动镜像验证。
- Fastboot 写入成功 **不等于** boot.img 能够启动。
- 公开 AOSP testkey **不能**替代 vivo 启动信任链所需密钥。
- **本次分析未发现**能让原厂 7.13.15 aboot 启动任意未签名 boot.img 的可用入口。
- 0x800 单字节实验支持 boot 镜像存在完整性保护，但**具体算法和完整覆盖范围仍需确认**。

### 5. 适用范围声明

上述结论仅适用于「**7.13.15 aboot + 1.15.1 boot**」这一实测组合，不能外推到其他固件版本。

### 6. 下一步

优先在两处寻找真正的校验点：

1. `0x9183E05C` 加载器内是否有 SHA-256 调用与尾部 5376 字节比对（`bl` 列表中未见 `0x91862A48`，但可能有其他哈希函数）
2. `0x9183D82C`（`0x9183D6C8` 的失败分支）究竟是打印、返回还是 halt——这决定 0x800 失败是 aboot 侧还是 kernel 侧

在确认机制之前，不继续进行无增量信息的 boot.img 修改实验。
