## 二、硬事实（无需推断）

1. **内核是自定义的**：`3.18.124` 是 Linux stable 分支版本（2018-09 发布），**vivo 原厂 PD1610 从未使用**——6.0.1=3.18.20、7.1.1=3.18.31、8.1=3.18.71（8.1 原厂 config 已由 tmproot 仓库 `ota8/config.txt` 独立证实）。`-perf` 为 vivo 配置的 LOCALVERSION，`g2363427e` 为其 git 描述，`-dirty` 表示构建时工作树有未提交修改，`#11` 为第 11 次构建。
2. **ROM 是自编译的 LineageOS 17.1**：`lineage_pd1610-eng` + `QQ3A.200805.001`（LineageOS 17.1 使用的 Android 10 build id）+ `test-keys`（自签名）+ `eng`（工程构建，adbd 默认 root）。ROM 编译于 2026-10-14 10:30，内核编译于前一日 02:28。
3. **Hi-Fi/DSD 已工作**：DSD 标记 = ES9038 DAC 的 DSD 直通路径被驱动起来——这是 Xplay6 移植里最难的部分，与 tmproot 仓库 `art/PORT-RUNBOOK-7.md`（DAC/ES9038、TFA9890、ACDB、DAPM、DSD 全量核对表）主题**高度吻合**。
4. 基带为完整可用状态（有信号、有版本号），说明 modem 分区保留原厂。

## 三、与本地静态分析的交叉（关键推论）

- 自定义内核 ⇒ boot.img 不可能是 vivo 签名（vivo 没有 3.18.124 的构建）。
- 本项目的静态结论（已确认）：**1.15.1 与 7.13.15 两代 aboot 同属"新架构"**——解锁分支只设 `boot_state=1` + 打印，验签无条件执行，失败走 `tampered assert → platform_halt(reboot)` 重启循环（1.15.1 的 F=`0x91637028`、调用者 `0x9163BFB8`；字符串 `Device is tampered`/`Security Error`/`boot_verifier.c`/`HALT: platform_halt reboot` 全齐）。
- ⇒ **零售 PD1610 + 上述任一原厂 aboot 不可能启动这颗内核**。与该现象一致的唯一解释仍是：**该机为工程机 / 内部放宽验签的 aboot**（v7.4 §8.2 判断），或存在我们尚未找到的第三方 bypass（无证据）。
- 另一条待验证假设：若存在**更早期（2016 年）PD1610 aboot**属"旧架构"（解锁即结构性跳过验签，如 PD1516A 3.8.5），则该机可能靠"老 aboot + 解锁"启动。本地无该版本文件，无法证伪；需取得 2016 年 PD1610 官方 aboot 才能排除。

## 四、与 tmproot 仓库的交叉

- `PORT-RUNBOOK-7.md` 的音频核对表（ES9038/DSD/ACDB）与本截图的 DSD 演示**指向同一目标**；该 runbook 基线为 1.15.1/PD1610 6.0.1。
- 因此：tmproot 作者与该 ROM 项目**至少共享技术圈/资料**，是否同一人无法从公开材料判定（用户称是另一位博主）。

## 五、下一步（信息增益最大 → 最小）

1. **要 `getprop ro.boot.*`**（若博主愿提供，一条命令即可定案）：
   `adb shell getprop | grep -E "ro.boot.(verifiedbootstate|flash.locked|veritymode|secure|hardware|serialno)"`
   - `verifiedbootstate=green` + `flash.locked=0` → 解锁但验签仍执行（需解释）；
   - `verifiedbootstate=orange` → 解锁放宽模式；
   - 缺失/异常值 → 工程引导层。
2. **要一张 fastboot 界面照**（`fastboot getvar all` 或 bootloader 界面）——看 `secure`、`unlocked`、aboot 版本号。
3. 问三个客观问题：aboot 是否原版/是否刷过；设备背面是否有工程标记；boot 分区是否 vivo 签名。
4. 离线：若有渠道取得 **2016 年早期 PD1610 aboot**，用本项目方法（movw/movt 配对 + F/G 结构比对）判断其是否属旧架构——这决定"零售机 + 老 aboot"假设能否成立。

- 用户尝试联系案例博主（酷安 UID 3298502 / GitHub `xiaocheng20`），对方**拒绝提供任何信息**（明确表态仅将询问视为消遣）。

- `xplay6-tmproot` 台账同向确认：该工程全程**不碰引导链**（README 原话 "without unlocking the bootloader and without writing any partition"），其 `UNLOCK-ADB-INPUT.md` 中的 "unlock" 指「USB 模拟点击」权限，与 bootloader 无关。⇒ 该信源在引导链上**零增量**。

### 7.2 这不改变任何工程结论

案例博主的机器**是哪台、什么状态，我们永远不会知道**——正因如此，它从始至终无法作为证据使用。本项目全部结论建立在**自有镜像的静态分析**上：

- 零售 1.15.1 / 7.13.15 / 8.19.16 的 aboot 均为新架构（CAF `boot_verifier.c`，验签无条件执行，失败 → tampered ASSERT → 重启循环）；
- ⇒ **零售 PD1610 + 这三版 aboot 无法启动自编译 kernel**（静态已确认，与任何人的案例无关）。

他的截图只能证明「存在一台 Xplay6 跑着自编译 LOS 17.1」，**不能证明该机是零售机**。这一判断不因他拒绝配合而改变。

### 7.3 唯一余下的、"零售机也可能成立"的假设

| 假设 | 内容 | 状态 |
|---|---|---|
| A | 该机为工程机 / 内部放宽验签 aboot | 无法证伪；但不可复制，对项目无用 |
| B | **2016 年早期 PD1610 aboot 属旧架构**（解锁 → 结构性跳过验签，同 PD1516A 3.8.5） | **已排除**（2026-11-10 13:35，见补充记录 §14） |
| C | 存在未知第三方 bypass | 无任何证据 |

**假设 B 已排除的依据**：`1.15.1` 的内核构建于 **2016-12-02**，即上市首发世代，是已知最早的零售 6.0.1 版本；其 aboot 验签包装 `0x916371FC` 入口无条件置 `is_tampered=1`，两个调用点（`0x9163B8D8` /boot、`0x9163C08C` /recovery）**前无任何解锁分支**——新架构从首发起就存在。剩余未验证空间仅剩上市前原型（1.13.x 之类，无任何可得文件），不构成零售路径。

**假设 B 为什么重要**：若成立，则「零售机 + 降级到早期官方 aboot + 解锁 + 自编译 boot」就是一条真实入口——而且早期 aboot 是 vivo 自己签的，SBL 加密校验会通过（与"改版 aboot 必黑砖"是两件事，v7.4 那张表把两者混在一起了）。

**假设 B 的判据（纯离线，不需要设备）**：
1. 取得 2016—2017 年 PD1610 官方固件包，抽出 `emmc_appsboot.mbn`；
2. 用本项目现成方法比对：① `Device is unlocked! Skipping verification...` 字符串是否有活 xref；② 验签包装函数是否"无条件调用"（新架构）还是"解锁分支绕过"（旧架构）；③ 是否存在 `boot_verifier.c` / `Security Error` / tampered ASSERT 全套字符串。
3. 三判据中任一为"旧架构特征"即成立。

**假设 B 若成立后的第二道关卡（需设备，未执行）**：SBL 是否对 aboot 施加版本回滚校验。PD1610 报告 `securebootkey=beta (keyver 2)`；`keyver` 是密钥版本而非镜像版本，2016 年 MSM8996 平台普遍**不对 aboot 做 rollback index 检查**——但这是平台惯例推断，**未验证**。风险：刷入后 SBL 拒签 → 黑砖 → 9008 恢复（本机已实测可用）。
