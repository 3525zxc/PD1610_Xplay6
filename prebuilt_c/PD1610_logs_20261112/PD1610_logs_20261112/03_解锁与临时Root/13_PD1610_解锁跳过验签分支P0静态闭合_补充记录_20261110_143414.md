## 0. 一句话结论

## 1. 方法修正（为什么此前 xref 是 0）

先前的 `trace_unlock_log.py` 用「字面量池 + 相邻 movw/movt 对」找交叉引用，全部 0 命中，甚至必然被引用的字符串（`reboot-bootloader`、`fastboot.c`）的 VA 在全文件也 0 次出现。原因：

- 本批 aboot（较新 GCC，ARM A32）字符串引用采用**寄存器构址**：`movw rX,#低16` + `movt rX,#高16`，且 **movw/movt 交错出现**（如 `movw r3; movw r1; movt r3; movt r1`），不要求相邻；
- 需按**寄存器**跟踪配对，而非相邻指令对；
- 条件执行变体（`movweq/movwne/movteq/...`）也必须纳入。

修正后脚本：`C:\qfilx\aboot\p0_trace_unlock.py`（线性 A32 + skipdata，按寄存器配对）。

## 3. 函数 F（7.13.15：`0x91839944`）——解锁检查与日志（已确认）

```
F:  r3 = 0x9192BBDC            ; 全局 devinfo 缓存指针
    r0 = [r3+0x10]             ; is_unlocked
    cmp r0,#0
    bne UNLOCKED
    ; 锁定：boot_state_set(0) → 取 keystore 状态 H()
    ;   若 H()==2：打印 "Keystore verification failed! Continuing anyways..."
    ;   返回 H()
UNLOCKED:
    boot_state_set(1)          ; 0x918115A8(1) → [0x9189B89C] = 1
    打印 "Device is unlocked! Skipping verification..."
    尾调 H()（返回 keystore 状态）
```

- devinfo 布局核对：`+0x10 = is_unlocked`（与 11-08 实验一致）；`+0x14 = is_tampered` 由验签函数 G 读写（§4）。
- `cmp r0,#0`：**任意非零都判解锁** → `0x01`（PD1610 实验）与 `0xFF`（X9s devinfo）在此判定点等价（P2 的 boot 判定点闭合）。
- F 的唯一调用者：`0x9183E2B8`，位于 boot 装载主函数内（`/boot` 验签调用点 `0x9183E38C` 之前）——**在实际 boot 装载路径上（已确认）**。
- F 返回值在调用处**未被检查**：其作用是副作用（设 boot_state、打日志、触发 keystore 状态缓存）。

## 4. 验签包装函数 G（`0x91839B18`）与 boot_verifier 全链（已确认）

字符串 `platform/msm_shared/boot_verifier.c`（`0x918796B8`）确认本模块即 CAF LK boot_verifier。

```
G(r0=镜像, r1=长度):
    [devinfo+0x14] = 1                       ; is_tampered 先置 1
    r6 = verify_image_with_sig(img, len, pname, ...)   ; 0x9181167C，无条件调用
        ; pname ∈ "/boot"(0x91880C14) / "/survival"(0x91880C08) / "/recovery"(0x91880BFC)
        ; 内部两次 RSA（0x91810CB0）：主密钥成功→boot_state=0；
        ; 两次都失败→0x91810C64：仅当 boot_state∈{0,2} 时升级为 3（RED）
        ; ★ boot_state==1（解锁）时不升级 → RED 被绕过
    if r6≠0: [0x91B92D08]=1（验签成功标志）; [devinfo+0x14]=0（清 tampered）
    s = boot_state_get()                     ; 0x91811AB0
    s==2 → 0x91812EEC(0)+0x918125D0          ; 黄锁警告显示
    s==3 → 0x91812EEC(2) + msleep(30000) + shutdown_device(0x91833148)
           ; shutdown 打印 "Going down for shutdown."、写 0 到 0x4AB000、msleep(5000)、
           ; 失败才打印 "Shutdown failed" 返回（reboot.c）
    [devinfo+0x14]≠0 → devinfo_update(0x918399F8) + "Device is tampered. Asserting.."
```

- `verify_image_with_sig` 全库**仅 2 个调用点**（`0x91839B78` / `0x91839C4C`，均在 G 内）→ /boot、/recovery 验签调用无条件，不存在「解锁就跳过验签调用」的分支。
- boot_verifier 日志族、内嵌 `scm_beta` 证书本体（`SHENZHEN1/scm_beta1/vivo@vivo.com`）、`VERIFIED_BOOT_SIG`/`AUTH_ATTR`/`KEYSTORE_INNER` 字段名均已在 `.rodata` 指认。

## 5. U1 主干闭合：验签结果如何决定是否进内核（已确认，7.13.15）

## 10. 第二轮复核（2026-11-10 10:44，评审驱动）：tampered 尾部 = assert 重启循环

评审要求补齐三件事：① `devinfo_update(0x918399F8)` 完整返回路径；② `"Device is tampered. Asserting.."` 之后的控制流；③ G 返回值在调用者处的失败判断。复核结果**推翻本记录第 5 节"失败+解锁→警告后继续启动"的表述**。

### 10.1 三项补齐结果（全部已确认，7.13.15）

**① devinfo_update（0x918399F8）完整返回路径**：函数体 0x918399F8–0x91839B14，两个出口均为干净的 canary+pop 返回，永不阻塞：

- 分区缺失（`0x918099CC` 返回 64 位大小为 0）→ `0x91839A50` 直接返回；
- 写入失败 → `dprintf("ERROR: Cannot write device info\n")`（`0x91880BD8`）+ assert 日志宏 → `0x91839AF8 → 0x91839A50` 返回；
- 写入目标按全局 `[0x9192BBD8]` 选择："devinfo"（`0x91880BD0`）或 "aboot"（`0x91876BA0`）分区；
- 返回值在 G 内立即被覆盖（`0x91839BD0` 重新装 r0），无消费。

**② "Device is tampered. Asserting.." 之后 = ASSERT(0) → 重启循环**：

打印后以 r0=返回地址、r1=`"ASSERT FAILED at (%s:%d): %s\n"`（`0x918746C8`）、r2=`"app/aboot/aboot.c"`（`0x91880688`）、r3=1224（行号）、[sp]=`"0"`（`0x9187F4A0`，断言表达式字面量）调用 `0x9184E684`（LK assert）。assert 链：

```
0x9184E684: 打印 "ASSERT FAILED at (app/aboot/aboot.c:1224): 0"
  → 0x9184E614（格式化断言表达式）
  → 0x9184E410: [0x9192B37C] 计数 +1；首次调用先 bl 0x918345B0
      （0x918345B0 = mrs cpsr / orr #0x80 / msr cpsr_c = 关中断）
  → 尾调 0x91806BAC:
      bl 0x9184E2F0
      dprintf("HALT: platform_halt reboot...\n")   ; 0x918769A4
      r0=0; bl 0x91833068                           ; reboot_device(0)：
          PMIC 寄存器写重启原因 → PSHOLD 0x4AB000 写 0 → msleep(5000)
      dprintf("HALT: spinning forever...\n")        ; 0x918769C4，仅重启失败可达
      b 0x91806BE8 → b 0x91806BE8                   ; 自跳死循环
```

assert 函数内 `0x9184E6F8` 的"正常返回"是**死代码**（halt 函数未标 noreturn，编译器照常生成后续；`verify_image.asm` 中 `0x91811714` 等 assert 调用点之后的代码同理不可达）。`__stack_chk_fail`（`0x9184E70C`）尾部同样是打印+自跳死循环。

**③ G 返回值在调用者处无失败判断——且失败时 G 根本不返回**：

G 的唯一返回路径是验签成功（r6≠0 → `[0x91B92D08]=1` + `is_tampered=0` → 状态显示 → `0x91839C04` 正常返回）。两个调用点（`0x9183E38C` /boot、`0x9183DDE8` /recovery）的返回值 r0 均被下一条指令立即覆盖（`bl 0x91843B58` / memcpy 参数准备），无任何检查。

### 10.2 修正后的完整模型（7.13.15，已确认）

```
F(0x91839944): is_unlocked(≠0) → boot_state=1 + "Device is unlocked! Skipping verification..."
G(0x91839B18): is_tampered=1（无条件）→ verify_image_with_sig（无条件执行）
  ├─ 验签成功: [0x91B92D08]=1, is_tampered=0
  │     state==2 → 黄锁警告显示
  │     → G 正常返回 → 调用侧 E398: [0x91B944B0]≠0 且 [0x91B92D08]≠0 → E5B8（→下游跳核路径）
  │        [0x91B944B0]==0 → E3B0 state 检查（state==1 → EAC0 警告显示 → E3BC → 0x91810E84 分派）
  └─ 验签失败: is_tampered 保持 1 → G 不再返回
        state==3（锁定，0x91810C64 升级）→ Security Error 显示 + 30s + shutdown 尝试（reboot.c）
        state==1（解锁）→ 无任何显示
        → devinfo_update（回写 tampered）→ "Device is tampered. Asserting.."
        → ASSERT(0) → 关中断 → "HALT: platform_halt reboot..." → reboot_device(0)
        → 重启循环（重启失败则 "HALT: spinning forever..." 死循环）
```

### 10.3 对既有结论的修正

- **第 5 节"验签失败+解锁→EAC0 警告→回 E3BC 继续启动"不成立**：验签失败时 G 永不返回；E398/EAC0/E3BC 分支只在验签成功后可达（state==1 场景 = 解锁态下以第二把密钥验签成功且 state 未被主密钥成功路径改写为 0）。
- **11-08「改 1 字节 → 5s 卡 logo」归因修正**：由"内核早期崩溃/复位循环（推断）"修正为"**aboot 内 tampered assert → platform_halt(reboot) → 重启循环**"（静态已确认）。**内核从未执行**——单字节实验从此不能评估内核好坏；任何被改动的 boot 都会被这条链拦截在内核跳转之前。
- **失败拦截层更新（替代 v7.4 三层表述的第 ③ 层）**：① RSA 验签失败；② RED 升级（仅锁定态：Security Error + 30s + 关机尝试）；③ **tampered assert 重启循环（锁定/解锁一视同仁的最终拦截）**。解锁绕过的只是 ② 的表现层（无错误屏、无 30s 等待、无关机尝试），**绕不过 ③**。
- **跨机型推论（推断）**：X9s 解锁 + 无签名 boot 能正常启动 → 其 aboot 必然缺少/改写这条 `is_tampered=1 → assert` 链（或解锁态不置 tampered、或失败处理改为日志继续）。P3（取得 X9s/PD1619 官方 aboot）的价值从"验证机制推断"升级为"**定位真正的行为分叉点**"。

### 10.4 两层结论（按评审框架）

- **已确定**：解锁不会跳过 BootSignature 验签调用；在 PD1610 7.13.15 中验签失败的最终拦截是 tampered assert 重启循环，**与解锁状态无关**；"解锁 + 验签失败 = 一定继续启动"**不成立**，不予写入任何结论。
- **仍开放**：`[0x91B944B0]` 的写入者与语义（==0 时绕过验签结果检查直达 state 检查）；`E3BC → 0x91810E84(boot_state 四路分派) → 下游函数 0x9183E5D4 → 候选跳核 0x9183E81C` 完整链的逐条精读（现仅验签成功路径可达）；PD1516A / PD1616B 侧行为分叉点（P3，需官方 aboot）。
- 本轮新增分析对象均为本地已有文件，零设备操作、零刷写；13.4 四条重启条件仍一条不满足。

## 11. P1（2026-11-10 11:20，评审驱动）：PD1516A 两份 aboot 的 tampered/ASSERT 路径比对 —— 跨机型分叉点确认

评审复评采纳 P0/§10 全部结论并提出新优先级（P1=PD1516A 比对，判据为函数级而非字符串级）。执行结果如下。分析对象：`compare\pd1516a_385\emmc_appsboot.mbn`（3.8.5，基址 0x91600000）、`compare\pd1516a_776\emmc_appsboot.mbn`（7.7.6，基址 0x91800000）。

### 11.1 模块级差异（已确认）

| 比较点 | PD1610 7.13.15 | PD1516A 3.8.5 | PD1516A 7.7.6 |
|---|---|---|---|
| 验签实现 | CAF `boot_verifier.c`（模块字符串/内嵌证书/keystore 标签全套） | 旧实现：无 `boot_verifier.c`/`KEYSTORE`/`QSEEcom` 字符串；错误码风格（`"ERROR: Cannot read boot image signature"` 活跃，xref 2 处） | 同 385（验签函数 `0x91837EB4`，错误点打印→`mvn r0,#0` 返回 -1） |

### 11.2 结论（已确认，静态）

1. **跨机型分叉点是验签架构代际差，不是单点参数**：PD1516A（3.8.5/7.7.6 两版一致）为旧架构——**解锁=结构性跳过验签（无日志），锁定+验签失败=打印提示后继续（无 assert、无 RED）**；PD1610 7.13.15 为新架构（CAF boot_verifier）——**验签无条件执行，解锁只抑制 RED 表现层，最终拦截是 tampered assert 重启循环**。
2. `"Device is unlocked! Skipping verification..."` 在 PD1516A 两版中为死数据的机制解释：旧架构用**分支结构**实现解锁跳过，不需要该日志；该串属于共用源码中新架构 F 函数的残留（或未接线的编译产物）。
3. X9s（PD1616B）教程行为「解锁+无签名 boot 可启动」与 PD1516A 旧架构行为同构；X9s 属于哪一代需 P2（取得官方 aboot）确认。若 X9s 也是旧架构，则「解锁跳过验签」是 vivo 旧世代全系行为，PD1610 是**换新架构并加死 assert 的机型**。
4. 术语按评审建议统一：PD1610 表述为「**解锁态抑制 RED 升级，但保留 tampered 致命断言**」；PD1516A 表述为「解锁态结构性跳过验签」。

### 11.3 本轮方法备注

- PD1516A 的 movw/movt xref 需按各自基址（385=0x91600000，776=0x91800000）加载，不能用 `adis.py`（硬编码 7.13.15 文件与基址）；skipdata 线性扫描的 xref 命中需用字编码校验（movt 高 12 位=0xE34/条件码）排除错位伪命中。

## 12. P2-a（2026-11-10 12:30，评审驱动）：PD1516A 7.7.6 门控上下文闭合 —— 修正 §11 的"验签编译期关闭"表述

### 12.1 四问答案

1. **门控存根恒返常数** ✓：`0x91831AA4`/`0x91831B10`（及 385 的 `0x9162DA4C`）均为无条件装载常数返回的存根，非运行时开关。
2. **调用门控的函数始终可达** ✓：主启动决策函数 `0x91839210` 在数据段被指针引用（文件偏移对应 VA `0x91888934`），即 **LK app 入口（aboot_init，APP_START 结构体）**，每次启动必然执行。

### 12.2 结构修正（撤回 §11"776 验签编译期关闭"）

- 门控≠0 的分支进入 **`0x918385F0` = normal-boot 主体**（帧 0x23C）：读 boot/recovery 分区（`0x9180EE2C`）→ 签名处理（共享辅助函数 `0x91833E24`/`0x9183C4BC`，与新旧两实现共用同一批 crypto/mmc 辅助：`0x918478D0`/`0x91847E00`/`0x91847AC8` 等）→ 跳核；**成功不返回**，返回则打印 `"ERROR: Could not do normal boot. Reverting to fastboot mode."` → fastboot。
- 其内部 `"ERROR: Cannot read boot image signature"`（`0x918390F8`）由分区**读取失败**（`0x9183890C`）触发，不等于 RSA 验证失败路径。
- 旧验签入口 `0x91837EB4` 与其 wrapper `0x918391A8`（wrapper 自身无任何调用者）为**死代码**；门==0 分支引用旧入口但门恒为常数，该分支不可达。

- **遗留（新）**：`0x918385F0` 内部验签的深度（是否执行 RSA 验证、验签失败后的处置）尚未逐条闭合；跳板表 `[0x91B721E0]`（.bss，运行时经 `0x9183AE54` 等写入）为服务分派表（PLT 风格，多处 blx +0x0C/+0x20/+0x24），其具体服务项未逐一识别。

### 12.3 对三机型表的最终修正（按评审措辞）

| 比较项目 | PD1610 7.13.15 | PD1516A 3.8.5 | PD1516A 7.7.6 |
|---|---|---|---|
| 验签调用 | 无条件执行 | 锁定分支执行 | 受恒返常数门控选择，活动路径为新实现 |
| 解锁态处理 | 仍执行验签 | 结构性跳过验签 | 活动路径无 is_unlocked 读取，门控与锁定无关 |
| tampered 标志 | 有 | 有（+0x14，入口置 1 成功清 0） | 未发现同等机制 |
| 验签失败 ASSERT | 有，ASSERT(0)→重启循环 | 当前路径未发现（尾调 dprintf 后返回） | 未闭合（新实现内部深度未逐条精读） |
| RED / boot_state | 完整状态机 | 未发现 | 未发现 |
| 失败后处理 | halt/reboot | 打印错误后返回继续 | 返回→回退 fastboot（normal-boot 失败路径） |

**修正后的代际差表述**：PD1610 7.13.15 与 PD1516A 两个 build 存在不同的 Boot 验签执行及失败处理架构。PD1610 使用 CAF boot_verifier，验签失败后通过 tampered ASSERT 阻止启动；PD1516A 3.8.5 在解锁分支结构性跳过验签（失败仅打印继续）；7.7.6 活动路径为新实现 `0x918385F0`，其验签深度与失败处置尚未逐条闭合。证书（`scm` 同族）与验签策略是独立的两层，不能互推。

### 15.2 恒零性证明（已确认）

- `0x91843B58` = getter：`ldr r1,[0x91B951AC](canary)` → `ldr r0,[0x91B944B0]` → canary 校验 → `pop {pc}`，返回 `[0x91B944B0]`。

- **⇒ 每次启动 .bss 被清零，且镜像内无写入路径 ⇒ getter 恒返回 0。**

### 15.3 对控制流的后果（修正此前表述）

`0x9183E38C`（验签）之后：

```
0x9183e390: bl getter(0x91843b58)     ; 恒返回 0
0x9183e394: cmp r0, #0
0x9183e398: beq 0x9183e3b0            ; ← 永远走这里
0x9183e39c: (r3 = 0x91B92D08; cmp #0; bne 0x9183e5b8)   ← 永不执行
0x9183e3b0: bl boot_state_get(0x91811ab0)

  1. `0x9183E5B8` 不是跳核路径，而是**本函数的收尾返回**（`ldr canary; add sp,#0x23c; pop {r4..fp,pc}`）；
  2. 该分支被恒零标志锁死，**是死代码**，正常启动永不经过。

- **结论：`[0x91B944B0]` 是一个在本 build 中既无写入者、也无有效分支的残留全局**（很可能是被裁掉的旧策略开关）。它既不能解释"两条不同启动路径"，也不是任何入口。

## 16. P4（2026-11-10 13:45）：真实跳核路径闭合 —— **arm64 不做 `blx`，由 TZ 经 `smc #0` 完成**

### 16.1 两个验签调用者的真实身份（已确认）

### 16.2 `boot_linux_from_flash` 的成功路径（已确认，7.13.15）

```
0x9183DDE8  bl G(0x91839B18)              验签（无条件）

### 16.3 `boot_linux`（`0x9183D63C`）与真正的跳转点（已确认）

```
0x9183D770  ldr r2,[r7,#0x38]             读 Image header +0x38

0x9183D794  blx r3                         ← **全库唯一的直接跳核指令**（仅 arm32）
0x9183D904  mov r0,r6 (kernel); mov r1,r8 (tags); bl 0x9181EEF8
```

### 16.4 arm64 分支（`0x9181EEF8`）→ SCM → `smc #0`（已确认）

```
0x9181EF54/0x9181EF74  kernel 地址写入 0x91B8F000 与 [0x91B8F048]
0x9181EF78  bl 0x9181EC3C
   ==0 → 0x9181E5F4（a64 参数块：1 / 0xF）
   !=0 → 0x9181E840（参数块：0x2000010F / 0x12 / 0x91B8F000 / 0x50）
0x9181E840  bl 0x9181E774
0x9181E774  ... smc #0 @ **0x9181E7D4**   ← 真正的跳核（进 TZ）
            返回 1 时循环重试
0x9181F004  dprintf("Failed to jump to kernel")   ; 0x9187BD04
0x9181F030  ASSERT FAILED at (platform/msm_shared/scm.c:1076)  ; 0x9187BB50 / 0x9187BB30
```

全库 `smc #0` 仅 4 处，全部在 `0x9181E4xx–0x9181E7xx` 这一段（SCM 封装层）。

### 16.5 结论

1. **arm64 内核的入口切换与跳转由 TZ（secure monitor）执行**：aboot 只把 kernel 地址写入 `0x91B8F000` 并发出 SCM 调用；跳转本身不在 aboot 的指令流里。这是"改 aboot 让它跳自定义内核"在 MSM8996 上比预想更复杂的原因——即使改了参数，仍要经 TZ，而改过的 aboot 又过不了 SBL。
2. **arm32 分支是唯一直接 `blx`**（`0x9183D794`），本机不适用（内核为 arm64）。
3. **此前 P4 的起点 `0x9183E5D4` 是错的**：那是 `0x9183E05C` 函数 epilogue 之后的下一个函数，与跳核无关。P4 已于本轮按正确路径完成。
4. 验签在跳核之前、无条件执行；`G` 失败即 tampered assert（§10），故**跳核路径只有在验签成功时可达**——与 4.2 / 13.1 层 2 结论一致。

### 17.3 解锁签名校验的实现（已确认）

`0x9184065C`（`vivo_bsp unlock_vivo` 的验签）：

```
push; sub sp,#0x130
cmp r5(r0=数据), #0 ; beq fail
ldrb r3,[r5] ; cmp #0 ; beq fail
r3=[0x91B93378]; cmp r3,#1 ; beq 0x9184070C    ; ← 跳过标志（见 17.4）
cmp r6(r1=长度),#0x200 ; ble fail                ; 长度必须 > 512
r0 = r5 + (len-0x200); r1=sp; r2=0x200
bl 0x91842380                                    ; ← 取末尾 512 字节做 RSA 验签
bl 0x918503C8 / 0x918424E8                       ; strlen + 比较
```

- **签名块 = 数据末尾 0x200（512）字节**，长度必须 > 512。
- 验签公钥**内嵌在 `vivo_bsp unlock_vivo` 字符串之后**（`0x91882F30` 附近）：`30 82 01 22 30 0D 06 09 2A 86 48 86 F7 0D 01 01 01 05 00 03 82 01 0F 00 30 82 01 0A 02 82 01 01 00 DF 10 92 89 FB 54 CB 72 F6 57 38 8E …`，模数 **`DF109289FB54CB72…`**。
- **该公钥与 boot 验签公钥（`E1146086…`）不是同一把**：解锁签名与 boot 签名是**两套独立信任根**。

### 17.4 跳过标志 `[0x91B93378]` 是死代码（已确认）

- 读点：`0x918406A4`（`cmp #1` → `beq 0x9184070C` 跳过验签）。
- 写点：仅 `0x91840398`（`str #1`），所在函数起点 `0x91840338`。
- **`0x91840338` 全库无任何调用者** → 死代码；该标志恒为 0（.bss，`0x91B89558–0x91B9A40C` 内，crt0 清零）。
- ⇒ 不存在"按标志跳过解锁验签"的可用路径。

### 17.5 对项目的四条结论

1. **P2 彻底闭合**：**官方解锁写入 devinfo+0x10 的值就是 `1`**（`str r2,#1`），与我们 11-08 写的 `0x01` **逐位相同**。`bbk unlock_vivo` 更是严格 `cmp #1`——vivo 自己把"已解锁"定义为恰好 1。X9s 的 `0xFF` 属第三方写值，非官方语义；在 boot 路径（`cmp #0`）上二者等价，在 fastboot 命令语义上不等价。
2. **不存在"更深一层的解锁"**：官方通道的终点就是 `is_unlocked=1`，与我们已有的状态一致。签名只保护"写入动作"，不产生额外状态。⇒ **通过官方解锁换取放宽验签，这条路不存在。**
3. **两套独立信任根**：解锁签名（`DF109289…`）≠ boot 验签（`E1146086…`）。即便取得解锁私钥，对启动未签名镜像**无任何帮助**。
4. 第三方工具箱 `unlock.log` 的 `check Signature Fail` 由此得解：它在尝试 `vivo_bsp unlock_vivo`，缺少 vivo 服务器签名。**这条路对所有第三方工具都封死**——也解释了为什么社区对 vivo 新机只能用 9008 写 devinfo。

## 20. H1 离线前置核对（2026-11-10 14:15）：换 aboot 不改变验签结果，且整条链同源

### 20.1 验签公钥跨版本比对（已确认）

按 SubjectPublicKeyInfo 前缀 `30820122300d06092a864886f70d01010105000382010f003082010a0282010100` 全库检索，取模数前 16 字节：

| build | 内嵌公钥（模数前 16 B） |
|---|---|
| PD1610 1.15.1 | `E1146086D08BE59EEF00E460C311BFEE`（boot 验签） + `DF109289FB54CB72F657388E6FB30BB1`（解锁） |
| PD1610 7.13.15 | 同上，**两把完全一致** |
| PD1610 8.19.16 | 同上，**两把完全一致** |
| X9s 1.13.10 | `A5CEEE3D7AA078514AF946405CAF0CBF`（boot 验签） + `DF109289FB54CB72…`（解锁） |

1. **PD1610 的 boot 验签公钥在 1.15.1 / 7.13.15 / 8.19.16 三代中逐字节相同** ⇒ 换 aboot **不改变"什么镜像能通过验签"**；原厂 6.0.1 的 boot 在 8.19.16 aboot 下同样验签通过，自编译 boot 同样验签失败。

## 21. H1 离线核对（二）：XBL 认证面、boot 格式兼容性、SCM 调用面（2026-11-10 14:22）

### 21.1 XBL（`xbl.elf`，1,830,152 B）

- ELF64 / AArch64（e_machine=183），17 个 program header，entry `0x6213C50`，标准高通布局。

### 21.3 arm64 跳核路径保留（已确认）

## 22. H1 隐藏风险排查（2026-11-10 14:50）：`is_tampered=1` 不会被别处消费成拦截

### 22.1 动机

8.19.16 的 G 失败后**会把 `devinfo+0x14`（is_tampered）留在 1**（不清除）。若后续某处读它并阻断，H1 仍会失败。因此必须枚举全部消费者。

### 22.2 枚举结果（已确认）

devinfo 指针 `0x91DA1318` 全库构址 38 处；在其后 12 条指令内出现 `ldr …, #0x14` 的共 5 处，其中 2 处是 `[sp,#0x14]` 栈访问（假阳性）。**真实消费者 3 处**：

| # | 地址 | 逻辑 | 是否阻断 |
|---|---|---|---|
| 1 | `0x91D3A3E0` | `ldr r3,[devinfo+0x14]; cmp #0; moveq r3,0x91D83934("false"); movne r3,0x91D8392C("true")` → 仅取字符串 | **否**（纯显示，即 fastboot `device-info` 的 `tampered: %s`） |
| 2 | `0x91D3CACC` | `ldr [devinfo+0x10]; cmp #0; bne 0x91D3CAD8`（已解锁则跳）→ 否则 `ldr [devinfo+0x14]; cmp #0; beq 0x91D3CDF8` | **否**（路径选择，两条路都继续装载） |
| 3 | `0x91D3D680` | 同上先判 unlocked；tampered≠0 时 `bl 0x91D3D12C` 后 `b 0x91D3D2CC` 继续 | **否**（`0x91D3D12C` 分配 0x1000 并写分区，属"回写 tampered 状态"，写完继续） |

`0x91D3D12C` 头部（确认为状态回写型，非阻断）：
```
push {r4,r5,r6,r7,r8,lr}; sub sp,#0x10
r0=0x1000; bl 0x91D52A94        ; 分配缓冲区
bl 0x91D1D7F0                   ; 取分区/句柄
bl 0x91D5575C / 0x91D52D54      ; 读取/拷贝
```
无 `assert` / `platform_halt` / `reboot` 调用。

### 22.3 结论

- **8.19.16 里 `is_tampered=1` 只影响"显示"和"路径选择"，不产生任何阻断。**
- 结合 §19.2（G 失败不 assert）、§19.2 调用者（失败后继续）、§22（tampered 不阻断），**H1 在 aboot 侧已无已知拦截点**。
- 剩余唯一未知仍是 aboot↔XBL 的加载接口（需实机），与 `is_tampered` 无关。

### 22.4 附：本轮同时确认的其它事实

- 8.19.16 有两个 `device-info` 显示串 `true` / `false`（`0x91D8392C` / `0x91D83934`）。
- 8.19.16 的 `bootselect` 串位于 `0x91D84138`，与 7.13.15 的 bootselect 路径一致。
