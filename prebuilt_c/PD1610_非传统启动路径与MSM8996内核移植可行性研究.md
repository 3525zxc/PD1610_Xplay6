- 日期：2026-11-09
- 性质：**全新研究主题的第一轮**，纯离线静态分析；零设备操作、零刷写、零注入
- `Xplay6_最终报告_v7.md` 保持 v7.4 归档版，**未改动**；本文件独立成篇

## 1. 方向一：Fastboot 内存启动路径 —— 关闭

### 1.1 方法

五个 aboot 全部按 ELF32 ARM 的 PT_LOAD 做精确 VA↔文件映射（各版本基址不同：`0x91600000` / `0x91D00000` / `0x91800000`），另对 7.13.15 的 16 MB 分区 dump 用 `BASE=0x91800000 / FOFF=0x8000`。四层核对：

1. 全量 C 字符串枚举，精确匹配 `boot` 等命令名；
2. 全量 `oem …` / `flashing …` 字符串枚举，排除把内存启动藏在 OEM 子命令下的可能；
3. 对命令字符串 VA 搜索 A32 `movw/movt` 立即数对，定位运行时注册代码；
4. 对 7.13.15 dump 全镜像解码 A32 BL 指令（`(word & 0x0F000000)==0x0B000000`），统计所有指向已知验签/跳核函数的调用点。

### 1.2 五份 aboot 的精确命令字符串

| aboot | `flash:` `erase:` `continue` `reboot` `reboot-bootloader` `getvar:` `download:` | 精确 `"boot"` | OEM 命令数 |
|---|---|---|---|
| PD1610 1.15.1 (`0x91600000`) | 全部存在 | **无** | 9 |
| PD1610 8.19.16 (`0x91D00000`) | 全部存在 | **无** | 16 |
| PD1610 7.13.15 分区 dump (`0x91800000`) | 全部存在 | **无** | 12 |
| PD1516A 7.7.6 (`0x91800000`) | 全部存在 | **无** | 12 |
| PD1516A 3.8.5 (`0x91600000`) | 全部存在 | **无** | 7 |

OEM 表内容全是 `device-id / device-info / device-name / device-imei / product-model / op-entry / optr-flag / get-info / enable-charger-screen / disable-charger-screen / ufs-id / update-app / reboot-edl / reboot-recovery` 一类，**没有任何内存启动或任意地址执行变体**。同平台的 PD1516A 也没有 `boot` → 这不是 vivo 单独裁掉的，同代 LK 基线本身就没有这条命令。

### 1.3 注册点与 BL 交叉引用（7.13.15 dump）

`movw/movt` 引用到 23 处、18 个不同命令字符串，注册代码集中在 `0x9183C3B4–0x9183C5C8`（flash/erase/continue/reboot/oem）与 `0x91840C10`（`getvar:`）、`0x91840C24`（`download:`）。**没有 `"boot"` 的注册点**。

全镜像 BL 解码命中已知函数（v7.4 地址）共 20 处，全部落在 `0x91810DBC–0x9183F0F4`：

| 目标 | 调用点 |
|---|---|
| `verify_image` (`0x9181167C`) | `0x91839B78`、`0x91839C4C`（仅此两处，与 v7.4 一致） |
| `verify_sig` (`0x91810CB0`) | `0x918118EC`、`0x91811930` |
| 验签子过程 `0x91839B18` | `0x9183DDE8`、`0x9183E38C` |
| dt 加载 `0x9181DE78` | `0x9183D6C0` |
| 跳核候选 `0x9183D63C` | `0x9183D99C`、`0x9183E81C` |
| getter `0x91843B58` | `0x9183E390`、`0x9183E9DC` |
| 状态分派 `0x91810E84` | `0x9183E3C8`；加载器主函数 `0x9183E05C` ← `0x9183F0F4` |

即：**验签与跳核都只在重启后的启动加载链里被调用**，fastboot 命令注册/处理区不调用它们。`flash:` 只把镜像写入分区，`download:` 只把数据放进 download buffer；验签发生在下一次启动的加载器中。

### 1.4 回答评审的四个问题

| 问题 | 答案 |
|---|---|
| Xplay6 是否实现独立内存启动命令？ | **否**。五个 aboot 无 `boot` 字符串、无注册点；既有实测 `fastboot boot` → `FAILED (remote: 'unknown command or device is lock')` |
| 内存启动与分区启动是否调用同一验证函数？ | **问题不成立**：只有分区启动一条路径。`flash` 侧不验签，验签在重启后的加载器 |
| 内存启动是否有独立镜像格式 / 启动入口？ | 不适用；未发现任何第二套镜像解析或跳核入口 |
| 若两条路径相同能否关闭？ | 更彻底：**内存启动路径根本不存在**，路线静态 + 实测双证关闭 |

补充：Recovery 也不是独立入口 —— 既有报告确认 `0x91839C4C` 是 `/recovery` 的 `verify_image` 调用点，与 `/boot` 共用同一验签函数。EDL/9008 是写分区通道；`secure:yes` 下 PBL/SBL 认证 aboot，同样不构成运行环境切换。

> 静态边界：命令表不是 `{字符串指针, handler}` 的静态数组（指针引用几乎为空），因此本轮改用「字符串精确枚举 + `movw/movt` 注册点 + BL 解码」三重证据；未逐条反汇编每个 fastboot handler 的完整函数体。

## 2. 方向二：DTB / QCDT —— 本轮最大收获

### 2.1 清点结果

| 检查项 | 结果 |
|---|---|
| boot header（5/5 镜像） | `second_size = 0`、`dt_size = 0`，`page_size = 4096` |
| 独立 `dt.img` / `dtbo` 文件 | 本地固件样本中 **0 个** |
| 分区表 `rawprogram_all_full.xml` | **无** `dtbo` / `dt.img` 分区；只有 `cdt`（4 KB，LUN3，`filename=""` 不刷写）与 `dip`（1 MB，LUN4） |
| `updater-script` | 无 dt 相关写入 |
| aboot 字符串 | PD1610 7.13.15 与 PD1516A aboot 都含 `Invalid device tree header`、`qcom,msm-id`、`qcom,board-id`、`qcom,pmic-id` |
| 既有反汇编 | `0x9181DE78` = dt 加载、`0x91850854` = FDT/QCDT 格式识别（`0xD00DFEED` / `0x02FF2112`）、`0x9183E468` = 检查 `"ARMd"` magic |

### 2.2 新证据：boot.img 内部是连续排列的真实 DTB 链

在 kernel 区域（不是文件尾）发现大量 FDT 头，全部通过合法性校验：`version=17`、`off_dt_struct=56`、`totalsize` 300–410 KB、strings block 含 `model` / `compatible` / `qcom,msm-id` / `qcom,board-id`；且**第一份 DTB 的 `totalsize` 正好等于下一份 FDT magic 的间距**，证明是首尾相接的多份 DTB，而非随机字节。

| 镜像 | FDT magic 命中数 | 备注 |
|---|---|---|
| PD1610 1.15.1 boot | 106 | 链长 ≥105，前几份是高通 CDP/MTP/Liquid 参考板 DTB |
| PD1610 8.19.16 boot | 122 | 链长 ≥121；**第 79 份 = vivo PD1610 专用 DTB** |
| PD1610 stock boot | 3 | 第 1 份 = vivo PD1610，另含 PD1516/PD1516A |
| PD1516A 7.7.6 boot | 3 | 含 PD1516 / PD1516A / PD1610 三份 vivo DTB |
| PD1516A 3.8.5 boot | 59 | 链长 ≥58 |

8.19.16 中 vivo PD1610 专用 DTB：文件偏移 `0x2615836`，大小 409,557 B，SHA256 前缀 `6e919bc1d65e0e73`；stock 中的 PD1610 DTB：`0x8B4ABC`，379,908 B，`83b46b5f8a577817`。

**回答评审的问题**：Xplay6 的设备树**来自 boot.img 内部**（kernel 区附加的多板型 DTB 链），不是从独立分区加载；aboot 按 `qcom,msm-id / board-id / pmic-id` 选择其中一份。分区表里没有 dtbo/dt.img，OTA 也不写 dt 分区。

### 2.3 已提取的原厂硬件描述（可直接对接 mainline DTS）

从导出的 DTB 根节点解析（纯 Python 解析 FDT 结构块，未依赖 dtc）：

| 机型 DTB | model | `qcom,msm-id` | `qcom,board-id` | `qcom,pmic-id` |
|---|---|---|---|---|
| **PD1610**（Xplay6） | `vivo MSM 8996 v3 + PMI8996 PD1610` | `<0xf6 0x30001>` | `<0x1 0xa 0x1000001 0x0>` | `<0x20009 0x10013 0 0>` |
| PD1516A（Xplay5S） | `vivo MSM 8996 v3 + PMI8996 PD1516` | `<0xf6 0x30001>` | `<0x1 0x9 0x1000001 0x0>` | `<0x20009 0x10013 0 0>` |

两者 `msm-id` 相同，`board-id` 第二项 `0xA` vs `0x9` 是 aboot 选板键。`compatible` 均为 `qcom,msm8996-cdp / qcom,msm8996 / qcom,cdp`。这三项属性正是 postmarketOS《MSM8996 Mainlining》要求移植者从 downstream DTS 找出来填进新 DTS 的内容。

已导出样本到 `C:\qfilx\compare\dtb\`：15 份前链 DTB + 5 份 vivo 专用 DTB（`pd1610_81916_VIVO_00.dtb`、`pd1610_stock_VIVO_00/01.dtb`、`pd1516a_776_VIVO_00/01.dtb`）。

### 2.4 本方向未闭合

- **QCDT 表头 / 索引表位置未定位**：`"ARMd"` magic 在五份 boot 镜像中 **0 命中**；`kernel_raw.bin` 偏移 `0x38` 的 `41 52 4d 64` 后面紧跟 `PE\0\0`（MZ/PE 文件），是**伪命中，不是 QCDT 表头**。既有 `0x9183E468` 检查 `"ARMd"` 的输入来源仍不明。
- `dtc` 未安装 → **未反编译为 DTS**。可复现命令：`dtc -I dtb -O dts C:\qfilx\compare\dtb\pd1610_81916_VIVO_00.dtb -o pd1610.dts`。
- 1.15.1（106 份）与 PD1516A 3.8.5（59 份）链中的 vivo 专用 DTB 未定位（model 字符串形式不同或未包含）。
- aboot 选择逻辑（`qcom,*-id` 匹配与 DTB 装载）的完整反汇编未做。

### 3.2 关键限制：lk2nd 不是绕过验签的独立入口

Galaxy Tab S3 项目的 README 明确写着「Samsung's bootloader only accepts lk2nd **when it is packed like a stock boot image**」：lk2nd 自身也打包成 Android boot image，由**原厂 bootloader 按原厂规则加载**。README 里出现的 `fastboot --cmdline … boot boot.img` 是 **lk2nd 自己提供的 fastboot 接口**，不能套到 vivo aboot（第 1 节已证其无 `boot` 命令）。

因此：mainline 内核与设备树研究有长期价值，但**它不解决 PD1610 的启动入口问题**。评审「即使 Fastboot 路线被证伪，内核移植工作也不会白费」在研究层面成立；对「让 Xplay6 跑起来」这个最终目标，启动入口仍是必要条件。

### 3.3 与最终目标的关系

- 若目标是 **LineageOS / 类原生 Android**：沿用评审判断，基于原厂 3.18 内核移植比直接上 mainline 更接近目标；mainline 主要价值是驱动与设备树的参考实现。
- 若目标可放宽为 **移动端 Linux**：MSM8996 社区基础足够，但 PD1610 的 UFS、屏幕、触摸、摄像头、指纹、电源管理都需单独适配，且仍需先解决启动入口。
- **本轮两方向的直接汇合点**：postmarketOS 移植流程第一步所需的 `qcom,msm-id / board-id / pmic-id`，已从原厂 DTB 中离线取出（第 2.3 节），不必等实机临时 Root 去读 `/proc/device-tree`。

## 4. 方向四：临时 Root 信息采集 —— 本轮未执行

需要实机与临时 Root（设备不在电脑旁），本轮**未执行**，仅登记目标：`/proc/config.gz`（原厂内核配置）、`/proc/modules`、`/proc/cmdline`、`/proc/device-tree` 或 `/sys/firmware/fdt`、`dmesg`，用于确认模块加载能力、可复用驱动与板级配置。

本轮离线 DTB 提取已部分替代 `/proc/device-tree` 的作用；但内核配置、模块列表、启动日志仍需实机。边界不变：**临时 Root ≠ 能加载任意内核，也 ≠ 能替换 boot.img**。
