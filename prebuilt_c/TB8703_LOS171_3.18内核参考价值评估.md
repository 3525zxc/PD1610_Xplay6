## 0. 一句话结论

**对目标 A（绕过 PD1610 启动验签）零价值；对目标 B（3.18 内核跑 Android 10）是一份结构同构的可运行参考实现。**
它不是"刷机教程"，而是一个 **非 Treble、只有 system 分区、3.18 内核、arm64、Android 10** 的完整成品——和 Xplay6 的处境在系统结构上完全同类。

## 2. `lineage-17.1-20200906-UNOFFICIAL-TB8703.zip` 解析

zip 内仅 11 个条目，关键 4 个：

| 文件 | 大小 | 说明 |
|---|---|---|
| `system.new.dat.br` | 598,597,853 | 整个 system（Brotli 压缩的 sparse 镜像） |
| **`boot.img`** | **11,167,744** | 内核 + ramdisk（已提取到 `C:\qfilx\compare\tb8703\boot.img`） |
| `system.transfer.list` | 7,847 | 块映射 |
| `updater-script` | 1,770 | 只刷 system + boot，**无 vendor 分区** |

**`updater-script` 关键行**：

```
block_image_update("/dev/block/bootdevice/by-name/system", ...)   ; 只写 system
package_extract_file("boot.img", "/dev/block/bootdevice/by-name/boot")
mount("ext4","EMMC","/dev/block/bootdevice/by-name/system","/system","")
run_program("/tmp/install/bin/deunify.sh", "")
```

⇒ **非 Treble、system-only 部署**（vendor 混在 system 内），与 Xplay6 的"无 vendor/product/odm 分区"处境相同。

## 3. `boot.img` 结构（已确认）

| 项 | 值 |
|---|---|
| magic | `ANDROID!`（legacy header v0） |
| page_size | `0x800` |
| kernel | `0x9E1DF3` = 10,362,355 B（**gzip 压缩**）@ `0x80008000` |
| ramdisk | `0xC3E04` = 802,308 B（gzip）@ `0x81000000` |
| second | 0 |
| tags_addr | `0x80000100` |
| **L 推算** | `0xAA6800` = 11,167,744 |
| **文件大小** | `0xAA6800` = 11,167,744 |
| **差** | **0** |
| **尾部 64 字节** | **全 0** |

**⇒ 这颗 boot.img 完全没有签名尾部**：无 AOSP `BootSignature`、无 AVB footer、无任何填充数据。
与 X9s 那份去加密 + Magisk 修补的 boot 形态一致（`L == 文件大小`）。
**原因**：TB-8703F 解锁 bootloader 后不做 boot 验签；这正是 PD1610 与它的根本分野，也说明**该样本不能用来推理 PD1610 的验签**。

**cmdline**（header 0x40）：
```
console=null androidboot.hardware=qcom msm_rtb.filter=0x237 ehci-hcd.park=3
lpm_levels.sleep_disabled=1 androidboot.bootdevice=7824900.sdhci loop.max_part=7
buildvariant=userdebug
```
无 `androidboot.selinux=permissive`（即 enforcing），无 `skip_initramfs`。

**ramdisk 布局**（cpio，解压后 1,864,192 B，仅 4 个条目）：

```
apex/  debug_ramdisk/  dev/  init (1,863,112 B)
```

**没有 fstab、没有 init.rc**——典型 Android 10 **system-as-root 第一段 init**：内核挂载 system 为根，其余全部来自 system 分区。

## 5. 与 PD1610 原厂 8.1（3.18.71）config 对比

| 选项 | TB8703 LOS17.1（3.18.140） | PD1610 8.1（3.18.71） |
|---|---|---|
| ANDROID_BINDER_IPC | `=y` | `=y` |
| ANDROID_BINDER_DEVICES | `"binder,hwbinder,vndbinder"` | 同 |
| ASHMEM | `=y` | `=y` |
| ION | `=y` | `=y` |
| SW_SYNC | `=y` | `=y` |
| SECURITY_SELINUX | `=y` | `=y` |
| DM_VERITY | `=y` | `=y` |
| BLK_DEV_LOOP | `=y` | `=y` |
| IKCONFIG / KALLSYMS_ALL / DEBUG_INFO | `=y` / `=y` / `=y` | 同 |
| **MODULES** | **`# CONFIG_MODULES is not set`（全内建）** | `=y` + `MODULE_SIG_FORCE=y` |
| KEXEC / DEVMEM | 未设置 / not set | 未设置 / not set |

**⇒ 跑 Android 10 所必需的内核子系统，PD1610 原厂 3.18.71 里一个都不缺。**
从 8.1 到 10 的跨越**不需要新增内核子系统**，差的是：
① linux-stable 3.18.71→3.18.140 的安全补丁（可选）；
② binder/ION 等驱动的 Android 10 兼容补丁；
③ 设备驱动与 DTB；
④ **启动链（目标 A）**——这一条才是真正的墙。

## 6. 对项目三条可直接复用的结论

1. **目标 B 的可行性得到实证**：3.18 内核 + 非 Treble + 仅 system 分区 + arm64 + Android 10 = 真实可运行组合。此前"没有 Treble 分区基础，GSI 路线不成立"只否掉了 GSI，**没有否掉"自行构建 system-only ROM"**。
2. **boot.img 最小形态有现成模板**：legacy v0 header、gzip kernel、4 条目 system-as-root ramdisk、无签名尾部、`loop.max_part=7`。Xplay6 若走到"能启动自编译镜像"那一步，打包形态可照此。
3. **部署方式确认**：只写 system + boot、`deunify.sh` 处理、`backuptool.sh` 保留 GApps——非 Treble 设备的 LOS 17.1 标准做法。

## 7. 边界（必须写清）

- **不解决目标 A**：TB-8703F 的 bootloader 不验 boot 签名（`L == 文件大小`、尾部全零），PD1610 的 aboot 无条件验签 + tampered assert。**样本的可运行性来自"没有验签"，不是"绕过了验签"。**
- **不同 SoC**：TB-8703F = MSM8953（`androidboot.bootdevice=7824900.sdhci`），PD1610 = MSM8996。内核源码树、驱动、DTB 全部不通用，只有"方法"可借鉴。
- **该内核非案例博主编译**（`nobody@android-build`），因此不能用它推断案例机的构建环境。
- 未执行：解包 598 MB 的 system 镜像、比对框架层补丁、任何设备侧操作。
