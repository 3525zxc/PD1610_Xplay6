## 0. 一句话结论

在**已测试的组合**（PD1610 零售版 / aboot 7.13.15 / boot 1.15.1）下：boot 与 recovery 都存在 **RSA-2048 + SHA-256** 验签，验签使用 **aboot 内嵌的密钥对象**；实机改动镜像内容会导致启动失败。指令级可确认验签失败会置阻断标志并使**验签子过程 `0x91839B18` 提前返回**，但**这不等于调用者停止装载，失败后的完整控制流仍未闭合**（4.2）。**目前没有找到能让自编译内核通过该验证的可行路径。** 同时 system 受 dm-verity（`enforcing`）约束，生成可挂载的 system 需要与非 AOSP `verity_key` 匹配的私钥，该私钥不在手，自编译 system 同样不可行。

证据边界（详见 3.5）：

- 签名**结构**与**长度模型**：已确认（4 份不同镜像逐字节吻合）
- 签名的**实际哈希输入**：未确认（5 次观测 / 4 份不同样本的摘要全部对不上）
- 单字节实验：**只覆盖两个位置**（`0x30`、`0x800`），不外推"任意字节"
- aboot 的 SBL 认证、system 的 dm-verity、boot 的 RSA 验签：**三条独立证据链**，各自保留证据边界，不能互相替代
  - SBL 认证：LK 报告「安全启动已启用」+ 平台惯例，**较强**（未实测刷改版 aboot、未追 QFPROM 读码）
  - dm-verity：**保护已启用确认**；**私钥归属为推断**（v7.3 收紧，见 5.5）
- 「缺签名即放行不存在」：**较强推断**，5.2 的 T2 是双变量实验、T1 无只读回读，未闭合
- 内存破坏：**本轮审计未发现可用缺陷**，但广泛栈保护不等于排除所有类型
- 「验签失败必然阻止内核装载」：**尚未完全闭合**（v7.4，4.2）——指令级确认的是「置两个标志 + 验签子过程 `0x91839B18` 提前返回」；上层 `skip_flag` 检查分支可能不可达，且**局部提前返回 ≠ 调用者返回**，上层 `0x9183E05C` 的后续流程未追通

**本报告不标记为「所有结论完全闭合」**，未闭合项见第 6 节与 13.7（重启条件见 13.4）。

## 2. 结论摘要

| # | 结论 | 强度 |
|---|---|---|
| 1 | boot/recovery 镜像尾部带 RSA-2048 + SHA-256 签名块；**签名值在 DER 结构内部（相对偏移 `0x400`）**，不是 DER 之外的另一段 | **确认**（asn1parse + 逐镜像偏移核对） |
| 2 | DER 的 params INTEGER 等于 `page_size + ALIGN(kernel) + ALIGN(ramdisk)` | **确认**（4 份镜像逐字节吻合） |
| 3 | 实测两个位置（`header.name`、header 页填充 `0x800`）各改 1 字节 → 启动失败 | **确认**（仅限这两个位置，不外推"任意字节"） |
| 4 | 「缺签名即放行」不存在 | **较强推断**（未闭合，见 5.2：T2 为双变量实验、T1 无只读回读确认） |
| 5a | 验签失败 → 置 `skip_flag[0x91B92D08]=1` **且**清 `[0x9192BBF0]=0` → 验签子过程 `0x91839B18` **提前返回**（不等于调用者返回） | **确认**（指令级，4.2） |
| 5b | 上述失败路径**必然**阻止内核装载 | **尚未完全闭合**：上层 `skip_flag` 检查分支可能不可达；验签子过程返回后调用者 `0x9183E05C` 仍继续执行，其到最终内核入口的数据流未追通（4.2、13.7 U1） |
| 6 | aboot 自身受 SBL 认证，改 aboot 无法启动 | **较强**（LK 报告 `secure:yes` + 平台惯例；未追 QFPROM 读码、未实测刷改版 aboot） |
| 7 | 已测试命令及二进制静态检查**未发现** `boot` / `oem` 入口 | **较强**（有限测试，不等于完整命令表枚举；见 5.3） |
| 8 | 内核 `CONFIG_KEXEC=n`，二阶段加载不可用 | **确认**（符号表完整但无 kexec 核心符号） |
| 9 | /system、/oem 均挂 dm-verity，veritymode 由引导层下发 | **确认**（`dm-0`/`dm-1` + getprop + fstab + `/verity_key` 指纹） |
| 10 | **RSA 摘要所对应的原始字节范围尚未重构**：5 次观测（4 份不同样本）的摘要都不匹配 | **未确认**（第 6 节） |

> 证据边界说明：
> - 第 2 条证明的是**长度模型**，不等于证明「签名的哈希输入就是这段连续原始字节」。
> - 第 3 条只覆盖两个被实测的位置，不能写成"任意一字节"。
> - **第 4 条（v7.3 降级）**：T2 虽确实清掉了真签名，但同时改了数据，无法单变量归因；T1 的「旧签名残留」只是写入长度推断，未经回读。故不写「确认 / 无条件 / 任何情况」。
> - **第 5b 条（v7.4 降级）**：指令级能确认「置标志 + 验签子过程提前返回」，不能确认「上层必然不装载」；`0x91843B58` 是 getter，若所读全局运行时未被间接写入（静态初值 0），`skip_flag` 检查**很可能**被绕过，但运行时恒零**未完全排除**。故不写「必然 / 无条件阻断」。
> - 第 7 条为**有限观测 + 静态检查**，不是对命令表的完备枚举证明。
> 以上在 3.5、5.2、5.3 单列。

## 3. 镜像签名结构（结构与长度已解开，哈希输入未闭合）

### 3.1 尾部布局（逐镜像实测，2026-11-09 19:55 复核）

| 镜像 | 数据区 L | DER 起点 | DER 总长 | 签名在 DER 内的偏移 | DER 之后 |
|---|---|---|---|---|---|
| 1.15.1 boot 14.9 MB | `0x0E30000` | `= L` | 1280 | `+0x400` | 6912 B（其中 1647 B 非零，为镜像尾部残留数据） |
| 实验 boot 52.8 MB | `0x3257000` | `= L` | 1280 | `+0x400` | 4096 B（前 256 B 非零，后 3840 B 全零） |
| 1.15.1 recovery | `0x3B10000` | `= L` | 1284 | `+0x404` | 4096 B（前 253 B 非零） |
| 8.19.16 boot | `0x3801000` | `= L` | 1280 | `+0x400` | 4096 B（前 255 B 非零） |

> **更正（v7.2）**：v7.1 早期把「DER 1280 B + 签名 256 B」写成两段并列结构，**是错的**。
> 签名（`OCTET STRING` 256 B）在 **DER 内部**，相对偏移 `0x400`；DER 之后那 256 B 是**另一段数据**——
> 用镜像证书公钥做 raw RSA 解签输出为空（非 PKCS#1 结构），**不是第二份签名**，用途未知。
> 各镜像 DER 之后的字节数也不一致（非统一定长块），不能作为布局依据。

### 3.2 DER 逐字段

```
SEQUENCE {                       ; 30 82 04 FC
  INTEGER 1                      ; 版本
  SEQUENCE { … }                 ; 985 B X.509 证书（scm_beta 自签名 CA, RSA-2048, CA:TRUE）
  SEQUENCE { sha256WithRSAEncryption, NULL }
  SEQUENCE { PRINTABLESTRING "/boot", INTEGER <数据区长度> }
  OCTET STRING 256 B             ; RSA 签名值
}
```

命令：`openssl asn1parse -inform DER -in <1280B> -i`

### 3.3 params 里的 INTEGER = DER 声明的数据长度

| 镜像 | 分区名 | params INTEGER | 数据区结束偏移 | 页+ALIGN(k)+ALIGN(r) |
|---|---|---|---|---|
| 1.15.1 boot（14.9 MB） | `/boot` | `0x0E30000` | `0x0E30000` | `0x0E30000` ✓ |
| 实验用 boot（52.8 MB） | `/boot` | `0x3257000` | `0x3257000` | `0x3257000` ✓ |
| 1.15.1 recovery | `/recovery` | `0x3B10000` | `0x3B10000` | `0x3B10000` ✓ |
| 8.19.16 boot | `/boot` | `0x3801000` | `0x3801000` | `0x3801000` ✓ |

**长度模型已闭合**：`len = page_size + ALIGN(kernel) + ALIGN(ramdisk)`，四份独立镜像逐字节吻合，此前"差一页"的争论终结。

**但长度吻合 ≠ 哈希输入已确认。** 5 次观测（4 份不同样本）的 RSA 摘要全部与 `data[0:len]` 的 SHA-256 对不上（第 6 节）。
也就是说：DER 声明"我签了多长"这件事已确认；"aboot 实际拿哪段字节去算哈希"**尚未确认**。

### 3.4 算法

raw RSA 模幂后得到标准 PKCS#1 v1.5 结构：

```
00 01 FF … FF 00 || 30 31 30 0D 06 09 60 86 48 01 65 03 04 02 01 05 00 04 20 || <32B 摘要>
```

→ RSA-2048 / SHA-256 / PKCS#1 v1.5，与 aboot 内手工拼出的 19 字节 DigestInfo 逐字节一致（`0x91810CF0`–`0x91810D8C` 把这段常量写栈）。

### 3.5 证据边界（v7.2 新增，防止把推断写成事实）

| 命题 | 当前证据 |
|---|---|
| DER 声明的长度 = header 页 + ALIGN(kernel) + ALIGN(ramdisk) | **已确认**（4 份镜像逐字节吻合） |
| RSA 签名算法 = SHA-256 + PKCS#1 v1.5 | **已确认**（raw RSA 解出标准 DigestInfo） |
| RSA 摘要来自 `data[0:len]` 这段原始连续字节 | **未确认**（5 次观测 / 4 份样本全部不匹配） |
| aboot 的实际哈希输入 = 磁盘镜像的原始字节 | **未确认** |
| 修改镜像内容会导致启动失败 | **已确认，但仅限两个实测位置**（`0x30`、`0x800`） |
| 「缺签名即放行」不存在 | **较强推断**（T2 双变量、T1 无回读；见 5.2） |
| 栈保护能排除所有类型的内存破坏 | **不成立**（仅覆盖栈上特定越界写；见 12.7） |

因此本报告统一表述为「**DER 声明的长度**」，不再使用"签名覆盖某某区间"这种把长度模型当成哈希模型的写法。

## 4. 验签调用链（代码级）

### 4.1 三个验证目标、两个静态调用点（v7.3 更正）

全二进制静态搜索发现**直接 `bl 0x9181167C` 指令共 2 处**：`0x91839B78`、`0x91839C4C`（反汇编 786432 条指令全扫）。该计数只覆盖直接 BL 引用，**不构成**对间接调用、函数指针调用或其他潜在调用路径的排除性证明。
之前标题写「三个调用点」是错的：**三个是验证目标（`/boot`、`/survival`、`/recovery`），调用点只有两个**；
`/boot` 与 `/survival` 由同一个调用点按全局模式位选择。

```asm
; ① 正常启动调用点（同一处覆盖 /boot 与 /survival）
91839B60  ldr     r3, [r3]
91839B64  cmp     r3, #0
91839B68  movwne  r2, #0xc08      ; 模式位非 0 → "/survival"
91839B6C  movweq  r2, #0xc14      ; 模式位 ==0 → "/boot"
91839B70  movtne  r2, #0x9188
91839B74  movteq  r2, #0x9188
91839B78  bl      0x9181167C      ; verify_image(data, len, name)
91839B7C  mov     r6, r0          ; ★ r6 = 返回值（v7.3 补齐）
91839B80  bl      0x91811AF0      ; ★ 被旧摘录省略的调用
91839B84  cmp     r6, #0
91839B88  beq     0x91839BA4      ; 返回 0 → 走成功路径
91839B8C  movw    r3, #0x2d08
```

> **v7.3 补答评审对 `r6` 的质疑**：旧摘录跳过了 `91839B7C` 与 `91839B80` 两条指令。

### 4.2 验签失败后的状态处理与控制流（v7.4 措辞收敛）

> **v7.4 更正**：v7.3 标题「失败即不装载」把**条件分支**写成了无条件阻断。第三轮评审指出
> `0x9183E398 beq` 会绕过 `skip_flag` 读取；离线反汇编后确认该质疑成立。
> **20:42 收敛**：按复评进一步区分「验签子过程提前返回」与「整个启动流程停止」，全文统一术语——
> **「验签子过程」指 `0x91839B18`，「加载器主函数」指其调用者 `0x9183E05C`**；不把 getter 的静态初值零写成运行时恒零，不把描述符字段清零写成内核启动失败。

**A. 写入侧（验签子过程 `0x91839B18`，指令级确认）**

```asm

91839B4C  str  r2, [r4, #0x14]    ; 验签前置 [0x9192BBF0] = 1（r4=0x9192BBDC）
91839B78  bl   0x9181167C         ; verify_image（/boot | /survival）

91839B80  bl   0x91811AF0
91839B84  cmp  r6, #0
91839B88  beq  0x91839BA4         ; 成功 → 跳到汇合点

91839B94  mov  r1, #1
91839B98  mov  r2, #0
91839B9C  str  r1, [r3]           ; ★ skip_flag[0x91B92D08] = 1
91839BA0  str  r2, [r4, #0x14]    ; ★ [0x9192BBF0] = 0
91839BA4  bl   0x91811AB0         ; ★ 成功/失败汇合：getter return [0x9189B89C]
91839BA8  cmp  r0, #2 / beq 0x91839C34
91839BB0  cmp  r0, #3 / beq 0x91839C1C

91839BC0  beq  0x91839C04         ; ★ ==0 → 函数返回出口
91839C04  … canary 校验 …

```

→ **确认**：验签失败会同时置 `skip_flag=1` 与 `[0x9192BBF0]=0`，并使**验签子过程 `0x91839B18` 自身**提前返回。
这条路径在 `0x91839B18` 内部，**不依赖**上层 `skip_flag` 检查；它**不表示**调用者 `0x9183E05C` 也已返回。

> **21:02 补齐**：旧摘录省略了 `0x91839BA4` 的**成功/失败汇合点**（`bl 0x91811AB0`，该 getter 返回 `[0x9189B89C]`）
> 及其返回 2 / 3 时的两个旁路 `0x91839C34` / `0x91839C1C`。ARM 模式复核：两个旁路执行状态初始化后
> 都 `b 0x91839BB8`，仍回到描述符读回与 `beq 0x91839C04`，**不改变上述结论**。

**B. 上层 `skip_flag` 检查（评审指出的条件分支 —— 可能不可达）**

```asm
9183E38C  bl   0x91839B18         ; 验签子过程（调用者 0x9183E05C）
9183E390  bl   0x91843B58         ; ★ 见下方定性
9183E394  cmp  r0, #0
9183E398  beq  0x9183E3B0         ; r0==0 → 绕过下面的 skip_flag 读取
9183E39C  movw r3, #0x2d08
9183E3A0  movt r3, #0x91b9
9183E3A4  ldr  r3, [r3]           ; 读 skip_flag
9183E3A8  cmp  r3, #0
9183E3AC  bne  0x9183E5B8         ; ≠0 → 失败出口汇合点（15 条分支跳入）
```

调用关系：加载器主函数 `0x9183E05C` 在 `0x9183E38C` 调用 `0x91839B18`，返回后**立即**在 `0x9183E390` 调用 getter。
**`0x91839B18` 提前返回 ≠ `0x9183E05C` 返回**：调用者仍继续执行后续指令，局部提前返回与整个启动流程停止是两件不同的事。

`0x91843B58` 的完整反汇编：

```asm

91843B60  str  lr, [sp, #-4]!
91843B64  sub  sp, sp, #0xc

91843B6C  movw r2, #0x44b0 / movt r2, #0x91b9  ; r2 = 0x91B944B0

91843B78  ldr  r0, [r2]          ; ★ getter 返回值 [0x91B944B0]
91843B7C  ldr  r2, [sp, #4]      ; ★ 取回栈上 canary（r2 被复用，不再是地址）
91843B80  ldr  r3, [r3]          ; ★ r3 从「地址」重载为 canary 值
91843B84  cmp  r2, r3            ; ★ 值 vs 值，正常栈保护比较（不是地址比较）
91843B88  bne  0x91843B94        ; → __stack_chk_fail
91843B8C  add  sp, sp, #0xc
91843B90  pop  {pc}             ; return r0
91843B94  bl   0x9184E70C       ; __stack_chk_fail
```

> **21:02 补齐（复评第二点）**：旧摘录漏了 `91843B74` / `91843B7C` / `91843B80` 三条，
> 并把 `cmp r2,r3` 误注释成地址比较。逐条核对复评提出的四点：canary **确实存栈**（`91843B74`）、
> **确实取回**（`91843B7C`）、比较的是 **canary 值**（`91843B80` 把 r3 重载为值）、
> `r0` 在 `91843B78` 赋值后到 `pop {pc}` 之间**从未被改写**。
> 故「主要功能是返回 `[0x91B944B0]`」的定性成立，且现在可以称为**完整反汇编**。

即它**只是带栈保护的全局变量 getter**，不是条件判断函数。离线统计：`0x91B944B0`
在整份反汇编中**仅此 1 处读引用、0 处写引用**；逐一核对 `0x91B944B4/B8/BC/C0/C4/F8/FC` 等相邻
构造点，写入目标均非 `0x91B944B0`；该地址落在文件数据段内（`file off 0x39C4B0`），静态初值 16 B 全零。

→ **较强推断**：`0x9183E398 beq` **很可能**跳过 `skip_flag` 检查，`0x9183E39C–E3AC` 可能永不可达。
但静态搜索**不能排除**通过指针、结构体拷贝或内存复制等**间接方式写入**，故运行时是否恒零**尚未完全排除**；
不能把该 getter 的静态初值零写成「运行时恒零」，也不能把「`skip_flag` → 失败出口」写成验签失败后的必经路径。

**C. 加载流程中的第二处 `[+0x14]` 检查（不构成独立阻断）**

```asm
9183E984  cmp  r3, #0
```

**C2. 零值分支 `0x9183E3B0` 的实际执行路径（21:02 离线补出）**

> 复评指出：`0x9183E3B0` 不只是普通分支目标，而是 getter 返回零时**很可能实际经过**的路径；
> 报告此前只从 `0x9183E5DC` 开始登记追踪，漏掉了更靠前的控制流。该质疑成立。
> 本轮以 **ARM (A32)** 模式重新反汇编 `aboot_full_orig.bin`（`BASE=0x91800000 / FOFF=0x8000`），补出实际指令。

```asm
9183E390  bl   0x91843B58        ; getter → [0x91B944B0]
9183E394  cmp  r0, #0
9183E398  beq  0x9183E3B0        ; ★ 零值分支

9183E3A8  cmp  r3, #0
```

对 `0x9183E3B0–0x9183E5DC` 共 **140 条指令**的分支提取（底稿 `C:\qfilx\aboot\e3b0_e5dc.asm`）与
全函数 `0x9183E000–0x9183F000`（1024 条指令）扫描显示：

- 该段**没有任何一条指令跳转到 `0x9183E5DC`**；段内是向更早地址回流
  （`0x9183E584 → E0AC`、`E594 → E23C`、`E5A4 → E2EC`）以及 `0x9183E4DC → E5B8`（失败出口）。
- `0x9183E5DC` 在全函数范围内**只有两个前驱**：`0x9183E9B4` 与 `0x9183EBA4`，均来自 C 节那处 `[+0x14]` 检查区。
- `0x9183E5DC` 起始为 `mov r1,#0 / mov r2,#0x100 / add r0,sp,#0x34 / bl 0x9184FE98`
  （清 0x100 字节栈缓冲，连续两次），**不是**「继续正常加载」的简单标签。

  `0x9183E5B8` 是 canary 校验 + `pop {r4,r5,r6,r7,r8,sb,sl,fp,pc}` 的**函数返回出口**。

→ **结构结论（本轮新增，仍非 U1 闭合）**：复评假设的 `0x9183E3B0 → 中间基本块 → 0x9183E5DC`
**线性链条未被证明**；`0x9183E3B0` 段与 `0x9183E5DC` 段是带回流的多个基本块。
二者之间的连接、以及 `0x9183E5DC → 0x9183E81C` 之间是否检查 `[0x9192BBF0]` / `skip_flag`，**本轮未追踪**。
因此 U1 的起点必须前移到 `0x9183E398` 的两个分支，而不是从 `0x9183E5DC` 开始。

**D. 结论边界（v7.4 · 20:42 采纳复评定稿表述）**

静态反汇编确认，`0x91839B18` 调用 `verify_image` 后，会根据返回值处理加载状态。

验签失败时：

1. 设置 `skip_flag[0x91B92D08] = 1`；
2. 将加载描述符的 `[r4+0x14]`（即 `[0x9192BBF0]`）字段清零；
3. 随后读取该字段，零值条件成立时跳转到 `0x91839C04`，执行函数返回。

因此，可以确认验签失败会触发状态修改，并使 `0x91839B18` 提前返回。但调用者 `0x9183E05C` 在
`bl 0x91839B18` 返回后仍会继续执行——**局部提前返回和整个启动流程停止是两件不同的事**。
后续 `0x91843B58` 读取的全局变量 `0x91B944B0`，目前只发现一处直接读取、未发现直接写入、静态初值为零，
因此 `0x9183E398` 的 `beq` 很可能跳过 `skip_flag` 检查，但运行时是否存在间接写入尚未完全排除。
另外，`0x9183E9A0` 对 `[0x9192BBF0]` 的检查，其零值分支最终经过空函数 `0x918354F8` 汇合到
`0x9183E5DC`，目前没有证据证明该分支本身会阻止内核装载。

| 命题 | 当前状态 |
|---|---|
| 验签失败会设置 `skip_flag` | **确认** |
| 验签失败会清零加载描述符字段 `[0x9192BBF0]` | **确认** |
| `0x91839B18` 在失败路径提前返回 | **确认** |
| `0x91843B58` 是返回 `[0x91B944B0]` 的 getter（完整栈保护序列已补齐）；该全局静态初值为零，且未发现直接写入 | **确认（静态范围内）** |
| `0x9183E398` 运行时必然跳过 `skip_flag` 检查 | **较强推断** |
| 验签失败必然阻止最终内核装载 | **尚未完全闭合** |

**结论**：已确认验签失败后的局部状态处理和函数提前返回，但**尚未完全证明调用者后续流程必然停止内核装载**。
需要继续追踪 `0x9183E5DC` 之后的描述符使用、加载函数返回值及最终内核跳转条件；且按 C2 段的结构事实，
追踪起点必须前移到 `0x9183E398` 的两个分支，不能预设 `0x9183E3B0` 会线性汇合到 `0x9183E5DC`。

**闭合所需（登记为待办，本轮未执行）**：见 13.7 的 U1 / U2。**第一优先级是从 `0x9183E398` 两分支出发、
沿真实执行路径追到最终内核入口**，重点证明 `0x9183E3B0` 如何（以及是否）到达 `0x9183E5DC`，
而不是只分析 `0x9183E5DC` 以后、也不是再找另一个 `skip_flag` 检查或重查 DER。
若失败镜像仍有机会到达内核跳转，「失败必然阻断装载」需重新评估；反之，若能证明失败状态沿所有可能分支
都无法到达内核入口，本节才算真正闭合。

### 4.3 公钥来源

`verify_image(data, len, name, desc)` 的入参里**没有证书指针**；公钥由 aboot 内部按 `name` 查表取得（`0x9185B080` 一线）。
镜像尾部自带的那份证书与 aboot 内嵌的 `scm_beta` 证书 SHA256 完全一致，作用是让验证者知道"该用哪把钥匙"，不是钥匙本身。

> 说明：这条是**静态推断**（参数没有证书指针），未经"用自定义证书签名并刷机"的反证实验。该实验对最终结论无影响（见第 6 节）。

### 4.4 解析器实现

DER/X.509 解析走 **LK 版 OpenSSL 1.0.1 移植**（aboot 内含 `lib/openssl/crypto/asn1/tasn_utl.c`、`rsa_eay.c`、`rsa_pk1.c`，以及 `Openssl LK: Removed rand dependency in rsa_eay.c` 等定制日志）。

| T1 | `boot_04_nosig.img` = `baseline[:L]`，`L=0x3257000`，**文件大小恰为 L** | **进系统** |
| T2 | `boot_05_nosig_mod.img`：数据区 `0x800: 00→FF`；从 `L` 起追加 `0x1500` 全零字节（覆盖整个尾部 5376 B） | **卡 logo** |

**v7.3 偏移核对（离线读回镜像文件，非设备操作）**：

```
L = 0x3257000；baseline 大小 0x3258500（= L + 0x1500）
T2 镜像 [0x800]        = ff
T2 镜像 [L : L+0x400]  = 全零（DER 本体，含证书/alg/params）
T2 镜像 [L+0x400 : L+0x500] = 全零  ← 真正的 RSA 签名字段，256/256 B 为零
```

> **更正 v7.2 的歧义写法**：原表「签名区 0x1500 清零」中的 `0x1500` **是追加的清零长度，不是偏移**。
> 生成脚本为 `out = baseline[:L] + b"\x00" * 0x1500`，即把从 `L`（DER 起点）开始的整个 0x1500 尾部清零。
> 因此评审担心的「`0x1500` 落在数据区内部、真签名没被清掉」**实测不成立**：`L+0x400` 起的 256 B 签名字段确为全零。

**但评审的结论仍然成立，理由比原推测更强**：

| 命题 | 实际能证明什么 |
|---|---|
| T1 截断到 L 后进系统 | **不能**证明「缺签名会放行」。`fastboot flash` 只写入 L 字节，L 之后的旧签名是否仍留在分区属于**推断**：依据是写入长度，未做 EDL 只读回读确认 |
| T2 卡 logo | **双变量实验**：同时改了 `0x800` 数据字节 **并**清除了整个尾部（含签名）。无法把「失败」单独归因于「签名缺失」——数据被改动本身已足以导致失败（见 5.1 E2） |
| 「缺签名即放行不存在」 | **未由 T1/T2 闭合**。当前只有「数据改动 + 签名清除 → 失败」这一组合观测，缺少**单变量**对照 |

**闭合该结论所需的实验（v7.4 按评审拆分，本轮不执行，仅记录）**：

| 实验 | 修改内容 | 要验证的问题 | 前置条件 |
|---|---|---|---|
| **T3-A** | 数据区一字节不动，**保留 DER**，仅把 `[L+0x400 : L+0x500]` 的 256 B RSA 签名值清零或改坏 | **无效 RSA 签名**是否被拒绝 | 刷入后只读回读确认该 256 B 确已改变 |
| **T3-B** | 数据区一字节不动，**清除整个 DER / 尾部认证结构**（`[L : L+0x1500]` 全零） | **完全缺失认证结构**时是否被拒绝 | 必须回读确认分区尾部确被覆盖，不能只按镜像文件长度推断写入结果 |
| **EDL 只读回读** | 无写入 | T1 之后 `L` 起始的分区内容是否确为**旧签名残留** | 只读，先备份 |

> **v7.4 区分（评审第三点）**：T3-A 证明的是「DER 结构仍在、签名值无效」，
> **不等价于**「认证结构不存在」；T3-B 才对应后者，且对写入落盘的确认要求更高。两者是不同命题，不能互相替代。

| 命题 | 证伪条件（满足即推翻当前推断） |
|---|---|
| 「无效签名不会被放行」 | T3-A 后设备**正常进系统**（且回读确认签名确已变） |
| 「完全缺失认证结构不会被放行」 | T3-B 后设备**正常进系统**（且回读确认尾部确已清零） |
| 「T1 进系统是因为旧签名残留」 | EDL 回读显示 `L` 起已无有效 DER/签名，而设备仍能进系统 |

上述任一完成前，第 2 节第 4 条与第 7 节「缺签名/签名损坏」一行的强度保持 **较强推断**，不写「确认」「无条件」「任何情况都必须验」。

> 按评审要求：**不为补齐报告再刷入任何未经验证的实验镜像**。以上仅列为待办条件（并入 13.4）。

**v7.3 补充 `/verity_key` 公钥来源与指纹证据**（离线核对固件包内文件）：

| 项 | 实测值 |
|---|---|
| `firmware/boot115/verity_key` | 524 B，SHA256 `f16f3691ce1e667856add1ddb651b24a023de88cb75b686d45309f6dd88cad5c` |
| 头部 32 B | `40000000 a704dbb9 e99cf54b bf4f191d d85a201d d43133ba a6f90432 3ed33f33`（mincrypt RSA 公钥格式，模数开头 `a704dbb9…`） |
| `firmware/81916/verity_key` | 524 B，与 1.15.1 版**字节级完全相同**（同为 `f16f3691…`） |
| `fstab.qcom` | `/system … wait,verify`；`/oem … wait,verify` |

**证据边界（按评审区分两层）**：

- **已确认**：系统完整性保护已启用（fstab `verify` + `dm-0`/`dm-1` + `veritymode=enforcing`）；固件包中存在这份**非 AOSP testkey 格式**的 `verity_key`，且 1.15.1 / 8.19.16 两版文件字节级一致。**当前运行时是否使用了这份文件尚未确认**（见下条 v7.4 边界与 13.7 U9）。
- **未直接确认**：这把公钥对应**私钥的归属**。「私钥由 vivo 掌控」是由「固件由 vivo 发布、密钥非公开 testkey、跨版本固定」得出的**合理推断**，不是密码学或直接证据；本轮也没有实测「用自签 system 刷入」来反证。
- **v7.4 补充边界（评审第五点）**：上表 `verity_key` 来自**固件包内的文件**。固件包中存在该文件，
  **不能单独证明设备运行时实际加载的就是这一份**。按 AOSP dm-verity 标准布局，校验公钥位于 boot 镜像 ramdisk 的
  `/verity_key`；要闭合「运行时使用的公钥 = 本表指纹」，需从**当前设备使用的 boot ramdisk** 中取出该文件比对指纹，
  或追到加载路径。本轮未做，标注为**待确认**（13.7 U9）。
  现有证据（fstab `verify` + `dm-0`/`dm-1` + `veritymode=enforcing`）已足以支持「完整性保护已启用」，该层不依赖此项。
- **可操作结论**（不依赖私钥归属）：无论私钥在谁手里，**它不在我们手里**；而生成能通过 `dm-verity` 校验的 system 需要与该公钥匹配的私钥。因此自编译 system 不可行这一判断成立，但理由应写成「缺少匹配私钥」，而非「已证明私钥归 vivo」。

## 6. 哈希重构失败清单（未闭合项，限制的是结论强度，不是可行性判断）

> 这一项**不影响"没有可行路径"的结论**——因为无论哈希怎么算，都需要 vivo 私钥才能生成匹配签名。
> 但它**确实限制**第 2 条结论的强度：我们能证明"DER 声明了多长"，不能证明"aboot 拿哪段字节算的哈希"。

用**各镜像自带证书里的公钥**做 raw RSA 解签取摘要，再与数据区 SHA-256 对比，**5 次观测全部不匹配**。

> **v7.3 样本口径更正**：这是 **5 次观测、4 份不同样本**。
> 最后一行「96 MB 分区 dump 首镜像」与第一行「1.15.1 boot 14.9 MB」的摘要与哈希**完全相同**
> （`e1aa702e…` / `20b9f66d…`），是同一份镜像的第二次观测，**不是独立样本**。
> 旧版「5 份镜像」夸大了独立样本数，此处更正。

| # | 观测对象 | 摘要（前 16） | SHA256(数据区)（前 16） | 独立样本 |
|---|---|---|---|---|
| 1 | 1.15.1 boot 14.9 MB | `e1aa702eca8ec163` | `20b9f66dd1a618ea` | ✓ S1 |
| 2 | 1.15.1 boot 52.8 MB | `1cf2d759c00f4761` | `3892f158c791be66` | ✓ S2 |
| 3 | 1.15.1 recovery | `fd0c8e3dd6af6ddd` | `b7c037b2216f5260` | ✓ S3 |
| 4 | 8.19.16 boot | `3d36776e08863ac1` | `dc11a0d278776ede` | ✓ S4 |
| 5 | 96 MB 分区 dump 首镜像 | `e1aa702eca8ec163` | `20b9f66dd1a618ea` | ✗ 同 S1 |

已穷举并排除：

- 长度取错（见 3.3，四份镜像逐字节吻合）
- 起点偏移 0 / 0x200 / 0x400 / 0x800 / 0x1000 × 终点 0xE30000±0x2000（512 步长全扫）
- 分块哈希（4 KB / 512 B 逐块摘要再哈希）、双 SHA-256、页旋转、页 0 清零
- header 四类字段（name / cmdline / id / extra_cmdline）**全部 16 种清零组合**，含尾填充清零
- "紧凑拼接"（去掉页对齐填充）、紧凑+补零
- 签名值位置取错（三份样本 raw RSA 结构均正确）
- DER 元数据自身参与哈希（der[:1020]/[:1024]/[4:1020]/data+der 等）

**这说明 aboot 在算哈希前对缓冲区做了某种改写**（或哈希的不是这段连续字节）。
但要注意：**这一条是否查清，不影响「没有可行路径」这一总体判断**——因为无论如何都需要与该公钥匹配的私钥才能生成有效签名，而私钥不可得。
它**确实限制**第 2 节第 10 条（哈希输入）的强度；第 4 条（缺签名即放行）的降级则是**另一回事**，源于 5.2 的实验设计，与哈希无关，两者不要混为一谈。

## 8. 方向评估（审计后状态）

### 8.1 aboot 内存破坏漏洞（**已于 12.7 节审计完毕：无可用缺陷**）

攻击面明确：`verify_image` 会解析镜像尾部这段**完全由刷机者控制的 DER**，实现是 LK 版 OpenSSL 1.0.1。

现实约束：
- 外层长度解析已做 16 MB 上限、越界、溢出三重检查（4.4）
- DER 总长被强制 ≤ 一页（`0x91811848` 处比较）
- `verify_image` 唯一 `memcpy` 的三要素都等于"一页"，长度不由镜像决定
- 栈保护广泛存在：canary 地址构造点 1622 处、`__stack_chk_fail` 调用点 1672 处（核心区 22 / 24）——**均为引用计数，非函数数**
- 无 UART、无串口、`/sys/fs/pstore` 不存在、`/proc/last_kmsg` 仅 76 字节非零
- 通过/失败只有 1 bit 预言机（能进系统 / 卡 logo）

评估（v7.3 收紧）：本轮**未发现可直接利用的边界缺陷**；广泛栈保护会拦下典型连续栈溢出，
但**不能据此排除堆破坏、数据变量覆盖、函数指针篡改**等其他内存破坏类型。
若未来出现候选漏洞，仍需逐项评估漏洞类型、可控程度与可利用条件。
以当前观测条件不具备继续利用的工程条件，**该方向转入"待条件"状态（见 13.4）**，不表述为"已封死"。

### 8.2 工程机 aboot / 泄露私钥

能一次性解决，但无公开渠道。截图里那台 `lineage_pd1610-eng`（内核 `3.18.124-perf-g2363427e-dirty`，比所有官方固件都新）最合理的解释是：**工程机（熔丝未烧）** 或 **换过引导层**。

### 8.3 换目标机型

**待调查方向（v7.3 收紧）**：同代 MSM8996 机型中，是否存在「devinfo 解锁后验签被真正关闭」的型号/固件，本轮**没有**具体机型与固件证据，不能写成「多数国际版/开发版」的既有事实。
若将来要评估换机型，须逐台核对 `getvar secure`、`verifiedbootstate`、`veritymode` 与 aboot 的 `verify_image` 调用情况。Xplay6 零售版已确认**不属于**「解锁即关验签」的情形。

## 10. 可证伪条件

本报告的核心结论「零售版无法引导自编译内核」在下列任一情况下**被推翻**：

1. 有人提供**能通过 SBL 认证**的 aboot（vivo 签名 / 工程机版本），且该 aboot 关闭 boot 验签；
2. 有人提供 **vivo 的 boot 签名私钥**（或能对任意数据生成有效 DER 的签名服务）；
3. 在 aboot 的解析路径上给出**可复现的内存破坏 PoC**，并证明可稳定改写 `verify_image` 返回值；
4. 存在我们未发现的第四条启动路径（不经 `0x9181167C`），且该路径会装载内核。

除这四条外，任何"刷机教程/工具"若要在这台零售机上运行自编译内核，都必须先解决同一组密码学约束。

## 12. 离线补充（19:10–20:00，全程无设备操作）

### 12.1 `0x9186CC54` 定性完成

```asm
9186cc54  push {r4,r5,lr}
9186cc64  ldr  ip, [r3, #8]     ; r3 = 密钥对象
9186cc74  ldr  ip, [ip, #8]     ; 取虚表槽位
9186cc7c  blx  ip
```

它是**密钥对象的虚表分发**（`key->vtbl->method`），真正执行 RSA 验签，**不是**"数据规范化函数"。
调用链：`verify_sig → 0x9182154C → 0x9186CC54 → key->[+8]->[+8]`。
结合字符串 `ERROR: Boot Invalid, RSA_KEY is NULL!`，可确认"密钥是外部传入的对象"。

### 12.2 公钥来源：aboot 内部 keystore（编译进镜像）

```asm
91810b0c  ldr  r0, [0x91B8E384]        ; 已缓存？
91810b50  movw r2, #0x62b              ; key id
91810b54  bl   0x9185B080              ; keystore 查找
91810b5c  strne r0, [0x91B8E384]
91810b68  strne r0, [0x91B8E388]
```

- `0x9185B080(0, &out, 0x62b, 0x91879B80)` → 返回密钥对象，缓存在全局 `0x91B8E388`
- `0x91879B80` 是**静态描述符表**（指向 aboot 数据段里的 DER 块）
- aboot 内嵌的 DER 位于 `0x91878F28`，其模数 `e1146086d08be59e…` **与 boot 镜像尾部证书完全一致**

→ 结论：验签用的是 **aboot 里编译进去的证书**，不是镜像自带的证书。
→ 推论：用自己密钥重签的镜像（`C:/qfilx/exp/boot_06_mykey.img`）**预期卡 logo**，刷机测试只作确认用。

### 12.3 新发现：存在独立的 `keystore` 分区与刷写通道

| 字符串 | VA | 引用点 |
|---|---|---|
| `unlock device to flash keystore` | `0x91880DE4` | `0x9183A81C`（fastboot flash 处理） |
| `image is not a keystore file` | `0x91880E04` | `0x9183A85C` |
| `unlock device to erase keystore` | `0x918805A8` | 擦除处理 |
| `Secret key is invalid, please update the bootloader with …` | `0x91880D84` | 同上 |
| `boot_verifier: keystore length is invalid.` | `0x91879AB4` | `0x91811B88` |

`fastboot flash keystore` 有专门的解析器（`0x91808F18`）：检查长度、`[+0x1C2] == 0xEE`、分段长度，再写入分区。

**但**：`verify_image` 全二进制只有两个调用点（`0x91839B78`、`0x91839C4C`），都用于 boot/recovery/survival，**没有针对 keystore 分区的启动期验签调用**。

→ 该分区是否参与启动期信任根，需要**只读**读回分区内容才能定论（待设备可用）。

### 12.4 两版 aboot 的 boot_verifier 具有高度相似特征（v7.4 收紧）

8 个标记字符串在两版中数量一一对应（`RSA_KEY is NULL`、`image length is different`、`Signature decrypt failed`、`Signature length exceeds`、`keystore`、`Openssl LK`、`scm_beta`、`X509_Certificate is NULL`），均各 1 处（`keystore` 各 7 处）。

> **v7.4 收紧（评审第四点）**：字符串数量一致**不能单独证明函数实现完全相同**。
> 准确表述是：两版 aboot 的 boot_verifier 具有**高度相似的代码与字符串特征，支持其来自同一代码基础**；
> **函数行为是否完全一致仍需确认**。
> 此前已发现两镜像装载基址不同（`0x91800000` vs `0x91600000`），直接比较机器码会受 `movw/movt` 立即数变化影响；
> 可靠的下一步是**重定位归一化后的指令 / 基本块比较**，而非字符串比对（见 12.6）。

→ **当前判断**：换回 1.15.1 官方 aboot **暂无收益证据**（`fastboot boot` 命令串这一项已静态确认两版皆无）。
→ 该路线强度由「确认」降为**较强**；在完成归一化指令级比较前，不写「完全同源 / 正式关闭」。

### 12.5 当前 boot/recovery RSA 验签路径的 keystore 来源核查（`0x9185B080`）

**它不读任何分区。**

```asm
9185b080  push {r4,r5,r6,lr}; sub sp,#0x30
9185b0b8  mov r0, r6
9185b0cc  bl  0x9185A734        ; ← 唯一的实质调用
9185b0d0  … 只做返回值和栈保护比对，无任何 I/O
```

`0x9185A734` 是对**描述符首字节**做 switch 的分派器：

```asm
9185a780  ldrb r2, [r4]         ; 类型 tag
9185a790  cmp  r2, #6
9185a794  ldrls pc, [pc, r2, lsl #2]   ; 7 项跳表 @0x9185A79C
```

跳表解出：type0→`0x9185A86C`、type1/6→`0x9185A8E8`、type2→`0x9185AA90`、type3→`0x9185AB94`、type4→`0x9185AC0C`、type5→`0x9185A7B8`。
各分支进入的是加密原语（`0x91867244`、`0x91867368`、`0x9185BAAC`），不是存储驱动。

描述符指向的数据块全部在 `aboot` 的只读段：

| 地址 | 内容 |
|---|---|
| `0x91879B44` | `"VERIFIED_BOOT_SIG"` / `"algor"` / `"auth_attr"` —— 属性名表 |
| `0x91878F28` | DER 块 `30 82 06 27 02 01 00 30 82 01 1F …`，模数 `e1146086…` |

**分区维度的反证**：整个二进制约 `"keystore\0"` 独立字符串只有 4 处，被当作**分区名**引用的只有两处——`0x9183A6C8`（fastboot flash）与 `0x918378DC`（fastboot erase）。**启动路径一处都没有。**

→ **v7.4 限定结论范围（评审第四点）**：当前定位到的 **boot/recovery RSA 验签路径**使用 aboot 内嵌的静态密钥描述符；
**尚未发现该路径从独立 keystore 分区读取验签公钥的证据**。
→ 「换 keystore 分区能绕过**当前这条** boot 验签」不成立，该线索在当前路径上关闭。

> 但这与「整个启动过程中 keystore 分区完全不参与任何信任判断」**不是同一个命题**。
> `keystore` 是否用于 TZ / 账号 / 防盗等其他用途，仍为**待验证推断**（13.7 U8）；
> 12.5 的反证只覆盖 boot/recovery RSA 验签这一条路径。

### 12.6 两版 aboot 的字节级比对无效（方法说明）

用 64 字节窗口在 1.15.1 mbn 中匹配 7.13.15 的函数体，四个关键函数全部"未找到"。
原因不是代码不同，而是**两个镜像的装载基址不同**（`0x91800000` vs `0x91600000`），`movw/movt` 立即数随之改变。
可靠的比对方式是字符串集合比对（已做，8 项一一对应），字节比对在此场景无效。

### 12.7 ASN.1 入口的可利用性审计（最后一轮静态排查）

**结论：当前未发现可直接利用的边界缺陷；相关代码存在较广泛的栈保护，但这不代表所有类型的内存破坏都已被排除。**

(1) `verify_image` 里唯一的 `memcpy` 是安全的：

```asm
918116ac: bl   0x918107C4        ; 返回页大小（0x800 或 0x1000）
918116b0: bl   0x9184FB9C        ; calloc(页大小)
918116b4: subs r5, r0, #0
918116b8: beq  0x91811A84        ; 分配失败 → 报错退出
918116bc: ldr  sl, [sp, #0x1c]   ; sl = data + len（签名块起点）
918116c0: bl   0x918107C4        ; 再取页大小
918116c4: mov  r1, sl
918116c8: mov  r2, r0            ; len = 页大小
918116cc: mov  r0, r5            ; dst = calloc 缓冲区
918116d0: bl   0x9184FD8C        ; memcpy
```

源、目的、长度三者都等于「一页」，不存在由镜像内容决定的长度。

(2) DER 长度解析受双重约束：

```asm
91810bd8  cmp r3, #0x1000000 / bhs  → 报错    ; 长度值 < 16 MB
91810bbc  cmp r7, r4 / bls          → 报错    ; 长度字段本身不得越出缓冲
91810c40  mvn r2, r4 / cmp r2, r3 / bhi → 报错 ; 加法溢出
```

调用侧再补一刀：

```asm
9181183c  subs sl, r0, #0            ; r0 = 解析出的 DER 总长
91811844  bl   0x918107C4            ; 页大小
91811848  cmp  r0, sl
9181184c  bhs  0x918118A4            ; 页大小 >= DER 总长，否则报错
```

→ DER **必须完整落在一页之内**，越界读写窗口被压缩到 4096 字节以内。

(3) 栈保护**统计口径（v7.3 重新核对并收紧）**：

| 观测量 | 全局 | 验签核心区 `0x91810000–0x91812000` | 含义 |
|---|---|---|---|
| 全局 canary 地址 `0x91B951AC` 的构造点（`movw/movt` 对） | 1622 | 22 | 引用/加载指令计数 |
| `__stack_chk_fail`（`0x9184E70C`）调用点 | 1672 | 24 | 失败分支的校验点计数 |

> **必须区分**：以上两个都是**指令/引用点计数，不等于「受保护函数的唯一数量」**。
> 一个带 `-fstack-protector` 的函数通常同时包含「入口把全局 canary 存入栈帧」与「出口取回并比较」两处引用；
> 反之某些函数可能有多条失败路径。本轮**没有**建立函数边界表，因此无法给出「唯一受保护函数数」，
> 也不把 1622 / 1672 写成「1726 个受保护函数」。旧版「1726 处加载点」的统计口径也不同，v7.3 起统一采用上表。
>
> 栈金丝雀主要防御**栈上的特定越界写**：连续栈溢出会在 `__stack_chk_fail` 被拦下。
> 但它**不能自动排除**堆内存破坏、全局/静态数据变量被覆盖、函数指针被篡改等其他类型。
> 本轮审计范围是「ASN.1/DER 解析路径上的边界检查与可见拷贝」，**不是对全部内存破坏类型的排除性证明**。

(4) DER/X.509 解析用的是 **OpenSSL-LK**（`d2i_X509` 一系），不是 vivo 手写循环。
`Integer overflow`、`Signature length exceeds size signature buffer`、`Calloc failed` 等
字符串说明长度与分配失败都有显式检查。

**综合判定（v7.3 按评审收紧）**：当前未发现可直接利用的边界缺陷。相关代码存在较广泛的栈保护，
但这不代表所有类型的内存破坏都已被排除。若未来发现漏洞，还需要进一步判断**漏洞类型、可控程度、
保护机制及可利用条件**（栈溢出会先撞上金丝雀；堆破坏/数据覆盖/函数指针篡改则不受金丝雀直接约束）。
以现有观测条件（1 bit 预言机、无 UART、pstore 不可用、无符号），暂不具备继续利用的工程条件。

**关于哈希输入的后续方向（独立逆向问题，不因本结题而重开项目）**：不再穷举 SHA-256 组合，
而应追踪 `0x91839B78` 的真实输入寄存器 → `0x9181167C` 内部保存的 `data`/`len` →
`0x91810CB0` 到 SHA-256 `update` 的最终参数 → `update` 实际接收的地址与长度，
以判定是加载缓冲区被改写、哈希输入指针有偏移，还是中间存在其他数据处理。

**若要让这条路重新成立，需要下列任一条件**：
- 拆机引出 UART，能读 panic 输出；
- 拿到该 aboot 的调试版 / 带符号版本（可定位具体函数与栈布局）；
- 命中一个已公开、且确实存在于本 build 的 LK/OpenSSL-LK CVE。

## 13. 结语（研究暂停点）

### 13.1 这份报告最终证明了什么

按"能不能做"分层，结论是逐层收紧的：

| 层 | 命题 | 状态 |
|---|---|---|
| 1 | 设备能刷入任意镜像（devinfo 解锁有效） | **成立** |
| 2 | 自编译 boot 能否通过已识别的启动验证并被引导 | **当前没有可行路径**；验签失败后的最终装载结果**尚未完全闭合**（4.2、13.7 U1） |
| 3 | 存在"少验一次"的分支（缺签名 / 别的分区 / 老 aboot / fastboot boot） | **其余基本证伪；「缺签名」一项仍为较强推断**（5.2 未闭合） |
| 4 | 信任根可替换（keystore 分区 / 镜像自带证书） | **证伪**（钥匙编译在 aboot 里） |
| 5 | 用内存破坏绕过（ASN.1 / 解析器） | **本轮审计未发现可用缺陷**；存在广泛栈保护，但不排除其他类型内存破坏 |
| 6 | 换 system 也能得到类原生 | **不成立**（dm-verity enforcing；所需私钥不在手，归属为推断） |

一句话：**能写，不能启。** 缺的不是方法，是与设备内信任根匹配的签名/校验私钥；我们没有它，也无法生成有效签名。

> **v7.3 收紧**：旧版写「是 vivo 的私钥」把「私钥归属」当成了已确认事实。
> 严格表述应为「与该公钥匹配的私钥不可得」；归属 vivo 是合理推断（5.5）。
>
> **v7.4 收紧**：旧版把「验签失败 → 加载器失败出口 → 不装载内核」当作闭合链路。
> 实测 `0x91843B58` 为 getter，`skip_flag` 检查分支可能不可达；能确认的是失败会置标志并使**验签子过程 `0x91839B18` 提前返回**，
> 而调用者 `0x9183E05C` 仍继续执行；「必然阻止内核装载」仍为**尚未完全闭合**（4.2、13.7 U1）。
> **20:42 收敛**：「局部状态处理 + 子过程提前返回」与「整个启动流程停止」是两个命题，不作为同一结论使用。

### 13.2 这轮研究真正有价值的部分

不是"没做出来"，而是把一条条似是而非的路**逐条钉死**，并留下了可复核的指令级证据：

- 签名结构与长度模型解开：`DER{version, cert, alg, "/分区名", 数据长度, sig}`，签名在 DER 内 `+0x400`，长度字段与"页 + 对齐 kernel + 对齐 ramdisk"逐字节吻合（4 份镜像验证）；**哈希输入仍未重构**
- 验签链完整定位：`0x9181167C → 0x91810CB0 → 0x9182154C → 0x9186CC54`（密钥对象虚表 → RSA）
- 失败路径**部分闭合**：验签失败置 `skip_flag[0x91B92D08]=1` 与 `[0x9192BBF0]=0`，并使验签子过程 `0x91839B18` 提前返回（确认）；上层 `skip_flag` 检查分支可能不可达，调用者 `0x9183E05C` 后续流程未追通，「必然阻止内核装载」尚未完全闭合（4.2）
- 三个验证目标均验签：`/boot`、`/survival`、`/recovery`；对应**两个直接静态调用点**（`0x91839B78`、`0x91839C4C`，全二进制直接 BL 搜索确认）
- 密钥来源定死：aboot 内嵌 DER（`0x91878F28`，模数 `e1146086…`），经 `0x9185B080` 查表取用，**非镜像证书、非 keystore 分区**
- 边界审计：`verify_image` 唯一 memcpy 长度恒为一页；DER 总长强制 ≤ 一页；长度解析三重校验

附带纠正了若干流传甚广的错误做法（改 devinfo 解锁、TWRP 一把梭、poke 注入、换老 aboot、fastboot boot）。

### 13.3 设备当前状态与遗留事项

- 引导层、基带、IMEI、分区表**全程未改动**
- **设备最终状态（v7.4 更正内部矛盾）**：已执行「刷回 `boot_00_baseline.img`」的恢复操作，
  但**最后一次 `fastboot flash` 在 19:15 被中断，写入是否完成未确认**；设备最终启动状态**待实际开机或 EDL 只读回读核实**。
  报告不再把「已恢复至官方 1.15.1」写成既成事实（对应 13.7 U6）
- 拿到设备后第一步：开机看是否正常进系统
  - 正常 → 无需处理
  - 卡 logo → 按住 **音量下 + 电源** 进 fastboot，执行
    `fastboot flash boot C:/qfilx/boottest/boot_00_baseline.img`
- 备用恢复路径：9008（EDL）+ 1.15.1 官方固件包，已验证可用

### 13.4 什么情况下重启这个项目（区分「设备实验 / 漏洞利用」与「低风险离线收尾」）

> **归档前整理（21:02）**：本节四条指的是**需要重新操作设备或启动漏洞利用研究**才值得投入的条件；
> 13.7 中标为「纯离线可推进」的 U1 / U2 / U7 / U9 / U10 属于**不涉及设备操作的低风险证据收尾**，与本节不冲突——
> 「项目暂停」指暂停设备实验与漏洞研究，不排除将来做纯静态证据整理。
> 若只做离线复核，U1（`0x9183E398` 两分支 → 最终内核入口）是第一优先级，无需等待本节四条。

**只有下面四条之一出现，才值得重启设备实验或漏洞利用研究**（与第 10 节可证伪条件一致）：

1. 出现**能通过 SBL 认证**且关闭 boot 验签的 aboot（工程机版本 / vivo 签名）；
2. 拿到 vivo 的 boot 签名私钥，或可用的签名服务；
3. 拆机引出 **UART**，能读 panic / 寄存器 —— 这是让"漏洞研究"从盲狙变成工程的前提；
4. 命中一个**已公开且确认存在于本 build** 的 LK / OpenSSL-LK 内存破坏 CVE。

**另外保留的「补齐证据」待办，按是否需要设备分为两类（均不构成本次重启项目的理由）**：

*需要设备在手、先备份后进行：*

- **T3-A / T3-B**：按 5.2 拆分后的两个单变量实验（无效 RSA 签名 / 完全缺失认证结构），各自需回读确认；
- **EDL 只读回读**：读回 T1 之后 `L` 起始的分区内容 → 确认「旧签名残留」不是推断；同时核实设备最终 boot 分区状态（U6）。

*纯离线、不碰设备（低风险证据收尾，见 13.7）：*

- **U1（第一优先）**：从 `0x9183E398` 的两个分支出发，沿真实执行路径追到最终内核入口（4.2 C2、13.7 U1）；
- 其余：确认 `0x91B944B0` 无间接写入（U2）、两版 aboot 归一化指令比较（U7）、
  当前 boot ramdisk 的 `/verity_key` 指纹（U9）。

> 按评审要求，本轮**没有**为了补齐报告而刷入任何新实验镜像；上述各项仅登记为条件或待办，未执行。

在此之前，任何"刷机教程/一键工具"声称能让这台零售机跑自编译内核，都需要先解释它如何绕过上面第 2～4 层的同一组约束。

### 13.5 如果将来要重做，建议的顺序

1. 先读 `getvar secure`、`ro.boot.verifiedbootstate`、`ro.boot.veritymode` —— 作为**初步筛选**；
2. 再确认 `fastboot boot` 是否存在（命令表里有没有 `boot` 串）；
3. 再确认内核有没有 `CONFIG_KEXEC`；
4. 最后才谈编译 —— 前面三条任一不通过，编译内核都是白费。

> **v7.3 收紧**：这三项只是**初步筛选，不是完备判据**。不同厂商可能还有其它验证层
> （例如独立于 dm-verity 的分区签名、TZ/QSEE 侧校验、OEM 自定义 fastboot 命令），
> 三项全部通过也不能保证一定能引导自编译镜像；但三项任一不通过，基本可以据此止损。

**这三步大约 10 分钟，能省掉几个月。**

### 13.6 面向复核者的最终表述（v7.3 采纳评审措辞）

> PD1610 这套零售版启动链**具有实际工作的镜像认证机制**。
> 设备允许**写入**镜像，不代表允许**执行**任意镜像。
> 当前已确认 aboot 内嵌公钥验签、验签失败会设置加载状态标志、清零描述符字段并使验签子过程 `0x91839B18` 提前返回、以及 dm-verity 运行状态；
> **失败后的完整控制流、哈希输入构造和个别实验细节仍有未闭合之处**（4.2、第 6 节、5.2、13.7）。
> 因此本报告的定位是**阶段性研究终稿**，而非「所有结论完全闭合」的最终判决。

这轮研究把问题从「有没有一个神奇的刷机工具」，推进到了一个可以被其他逆向开发者**逐条复核**的技术结论：
每条断言都标注了证据强度与可证伪条件（第 10 节），推断与实测分开记录，未闭合项明确保留。
