# vivo Xplay6 (PD1610) 类原生移植研究总报告

> 设备：vivo Xplay6 / PD1610 / MSM8996 / UFS 6 LUN / 4096B 扇区
> 研究周期：2026-11-08 ~ 2026-11-09
> 研究方法：9008 刷写实验 + aboot/boot/recovery 静态反汇编 + 官方固件对比 + 社区线索核查
> 核心结论：**在公开可得材料范围内，类原生移植不可行；设备已稳定在 Android 6.0.1 + 解锁 BL 状态**

---

## 一、结论摘要

| 目标 | 结果 |
|---|---|
| BL 解锁 | ✅ 成功（devinfo `is_unlocked=1` + `is_unlock_critical=1`），但只放开"写分区"，不放开"启动未签名镜像" |
| 降级 Android 6.0.1 | ✅ 成功，现运行 `PD1610_D_1.15.1`，基带/IMEI/NV 完好 |
| 刷入类原生（LineageOS 等） | ❌ 不可行 |
| ROOT | ❌ 不可行（需改 boot，被签名拦截） |

**不可行的根本原因**：vivo 在启动链上部署了**三套彼此独立的 RSA 信任根**，且全部不是 AOSP 公开 testkey：

| 验证层 | 保护对象 | 公钥特征 | 可否自签 |
|---|---|---|---|
| aboot（MBN 证书链） | boot / recovery 镜像 | vivo beta CA，`SW_ID/HW_ID/OEM_ID` 齐全 | 否 |
| recovery `res/keys` | `update.zip` OTA 包 | 模数 `b96ada8b...`，仅 1 把 | 否 |
| boot 内 `/verity_key` | system / oem 的 dm-verity | 模数 `a704dbb9...`，7.x 与 8.x 同一把 | 否 |

三层任意一层被突破都还需要另外两层，而任何一层都缺乏可用私钥。

## 四、第一阶段：BL 解锁实验

### 4.1 devinfo 结构

位置：LUN4 / start_sector 882954 / 4096 字节

```
0x00–0x0C  "ANDROID-BOOT!" 魔数
0x10       is_unlocked          (32 位)
0x14       is_tampered          (32 位)
0x18       is_unlock_critical   (32 位)
0x1C       charger_screen_enabled
```

写入 `0x10=1` 与 `0x18=1` 后：

```
fastboot oem device-info → Device unlocked: true / critical unlocked: true
```

### 4.2 解锁的实际效果

| 操作 | 结果 |
|---|---|
| `fastboot flash` 写任意分区 | ✅ 放行 |
| `fastboot erase` / `format` | ✅ 放行（需 USB 链路正常） |
| `fastboot boot` 启动未签名镜像 | ❌ `unknown command or device is lock` |
| 启动被修改过的 boot | ❌ 卡 logo（签名校验失败） |

**关键证据**（aboot 反汇编）：解锁分支与锁定分支**汇入同一个验证函数**。

```
0x91839974: bl 0x91810E40     ; 某启动路径
0x918399C8: b  0x91810E40     ; 解锁/锁定分支在此汇合
0x9183E3C8: bl 0x91810E84     ; 常规启动路径
```

三处入口最终都进入 `0x91810E40 → 0x91810E84`，没有旁路。

## 五、第二阶段：降级 1.15.1（已成功）

### 5.1 分区兼容性验证

用 `gpt_compare.py` 逐条比对当前 GPT 与 1.15.1 刷写表：

```
6 个 LUN 全部比对，start_sector 差值全为 0，size 全部相等
冲突项：0
```

结论：布局完全兼容，**无需刷 GPT**，保留原分区表可随时回退。

### 5.2 刷写清单（阶段一：系统层，3.1 GB）

```
LUN0 cache      <- cache.img        6.1 MB
LUN0 oem        <- oem.img         17.6 MB
LUN0 apps       <- apps.img       398.1 MB
LUN4 boot       <- boot.img        50.3 MB
LUN4 system     <- system.img    2571.9 MB
LUN4 recovery   <- recovery.img    59.1 MB
```

**主动跳过**：

| 分区 | 原因 |
|---|---|
| `persist` `fsg` `fsc` `modemst1` `modemst2` `sec` | 保护 IMEI 与传感器校准 |
| `devinfo` | XML 中是**擦除**操作，会抹掉 BL 解锁状态 |
| `splash` `cdt` | 保留开机画面与硬件配置，便于判断启动阶段 |
| `PrimaryGPT` `BackupGPT` | 布局已一致，不动最安全 |

### 5.3 data 重建

6.0.1 的 recovery **无法格式化** 7.1.1 加密的 `/data`：

```
Formatting /data...
format_volume result=-1...     ← 失败
Formatting /cache...
format_volume result=0...      ← 成功
```

改用 fastboot 直接写原厂镜像：

```
fastboot erase userdata / misc / cache / keystore
fastboot flash userdata userdata.img     (1.36 GB sparse，3 段全部 OKAY)
```

### 5.4 踩坑记录

| 现象 | 原因 | 解决 |
|---|---|---|
| `Sahara protocol error` / `Could not find the file` | `-s 13:"路径"` 多包了一层引号 | 改为 `13:相对文件名`，`cwd` 设为工具目录 |
| `verbose=` is not recognized | 该版 fh_loader 的 `verbose` 是开关 | 去掉 `=1` |
| `fastboot erase` 全部 `Write to device failed` | USB 链路问题，非权限拒绝 | **换 USB 口** 后全部 `OKAY` |
| `fastboot oem edl` → `unknown command` | 7.13.15 未注册该命令 | 只能 `adb shell reboot edl` |
| recovery 反复循环 | `misc` 残留 recovery 指令 | `fastboot erase misc` |

## 六、第三阶段：aboot 静态分析

### 6.1 四版对比

| 版本 | 大小 | 入口地址 | SHA-256 |
|---|---|---|---|
| 7.13.15（7.1.1） | 16,777,216（分区 dump） | `0x91800000` | `b4d75a9b399a8d28b8bd7ff7c68994beadab708ed3d23d4c399095788efc3c5f` |
| 1.15.1（6.0.1） | 4,015,920 | `0x91600000` | `09990c24f63c5b6fb6ab32af65ad180fce8350d640f8a67b74ef35eb0d06e3c8` |
| 8.19.9（8.1 Beta） | 3,173,696 | `0x91D00000` | `7f21823d48ffab4aabbded6161000b8dbfd5839b5e2070446cef28fd5d0d5a0e` |
| 8.19.16（8.1.0） | 3,173,696 | `0x91D00000` | `fe535256b3e90cb6d4c3fd2f9b7ea734d87366b5af90d22acd1befde24c15c64` |

### 6.2 架构分水岭

| 特征 | 7.13.15 | 8.19.16 |
|---|---|---|
| `ANDROID!` 代码引用 | **0 处** | **7 处** |
| 读取 `kernel_addr` (hdr+0xC) | 无 | 有 |
| 读取 `ramdisk_addr` (hdr+0x14) | 无 | 有 |
| 读取 `tags_addr` (hdr+0x20) | 无 | 有 |
| 地址检查 | overlap 检查 | 完整 `check_addr` |

7.x 走 MBN hash + 证书链，完全不解析 Android boot header；8.x 保留了传统 LK 的 header 解析路径。

### 6.3 8.19.9 与 8.19.16：代码零差异

```
差异 784 字节，聚成 4 段：
  0x0010A8..0x0011A7   256 bytes   ← RSA-2048 签名块
  0x00125A..0x001272    25 bytes   ← 版本号/构建时间
  0x0013C8..0x0014C7   256 bytes   ← RSA-2048 签名块
  0x00155B..0x00165A   256 bytes   ← RSA-2048 签名块

check_addr    差异命中: False
loader        差异命中: False
verifier      差异命中: False
header_parse  差异命中: False
```

**代码段从 0x8000 起一字节未变**，只有重新签名和版本号更新。说明 8.19.x 全系列使用同一份 aboot 代码，不存在"更松的版本"。

## 七、第四阶段：CVE 排查（全部排除）

### 7.1 CVE-2013-2598（LK 地址覆盖）

**7.13.15：排除**

- 全镜像 927,062 条指令，`ANDROID!` 常量引用 **0 处**
- `kernel_addr / ramdisk_addr / tags_addr` 取用 **0 处**，无攻击面
- 地址重叠检查存在（`kernel/ramdisk addresses overlap` @0x9183DAB4 等 8 处引用）

**8.19.16：排除**

它保留了 header 解析：

```
91D3C490: bl   0x91D52E68    ; memcmp(buf, "ANDROID!", 8)
91D3CB00: ldr  r7, [r4, #0xc]  ; kernel_addr
91D3CB2C: bl   0x91D3BCC0      ; 带地址进入加载
```

但有完整的 `check_aboot_addr_range_overlap` 等价实现（`0x91D3C218`）：

```
91D3C230: cmp  ip, r1          ; 溢出检查
91D3C240: movt r2, #0x91cf     ; 0x91CFFFFF
91D3C250: movt r2, #0x922f     ; 0x922FFFFF
91D3C258: bls  0x91d3c28c      ; 落在 aboot 区间 → 返回 -1
```

且明确用于 `kernel_addr`（调用点 `0x91D454F0`）：

```
91D454E4: ldr  r0, [sb, #0xc]  ; kernel_addr
91D454F0: bl   0x91D3C218      ; 区间校验
```

任何落在 `0x91D00000–0x922FFFFF`（aboot 自身）的地址都被拒绝。

### 7.2 CVE-2014-0973（RSA 摘要长度）

**已修复**

DigestInfo 由 19 条 `strb` 逐字节构造（`0x91810CF8`–`0x91810D88`）：

```
30 31 30 0d 06 09 60 86 48 01 65 03 04 02 01 05 00 04 20
```

长度校验：

```
91810DC0: cmp r0, #0x33        ; 51 = 19 + 32，必须完整匹配
```

PKCS#1 v1.5 结构校验（`0x9186CDD4`）：

```
9186CDE0: sub  lr, r1, #0xb    ; modlen - 11
9186CE18: mov  r1, #0xff
9186CE1C: strb sb, [r5], #2    ; 00
9186CE24: strb r8, [r3, #1]    ; 01
9186CE2C: bl   memset          ; FF 填充
9186CE34: strb sb, [r5, r7]    ; 00 分隔符
```

无长度截断，无尾随数据可利用空间。

### 7.3 CVE-2014-0974（FDT 地址校验）

**不可利用**

- `Fdt addresses overlap`（0x9187B993）全镜像零引用，仅 `Tags addresses overlap` 被使用
- 但控制 FDT 地址必须改 boot header，而 header 受签名保护 → 无法构造输入

### 7.4 CVE-2014-4325（fastboot boot 绕过）

**排除**

命令表（字符串区 `0x08D300`–`0x08D460`）：

```
flash:  erase:  continue  reboot  reboot-bootloader
bbk lock_vivo  oem device-info  preflash
oem enable-charger-screen  oem disable-charger-screen
product  kernel  serialno  oem update- app  bbk unlock_vivo
partition-size:  partition-type:
oem reboot-edl          ← 实用：可从 fastboot 直进 9008
```

7.13.15 与 8.19.16 均**没有 `boot` 命令**。

### 7.5 状态机与"跳过验证"分支（死代码）

```
0x9189B89C  静态初值 = 0x00000003   （锁定态）
0x91B92D08  静态初值 = 0x00000000   （标志恒 0）
```

两条候选绕过分支：

```
91839C: ldr r3, [0x91B92D08]
9183AC: bne 0x9183e5b8       ; 恒不成立

9183B0: bl  0x91811ab0       ; 返回 0x9189B89C 的值
9183B4: cmp r0, #1
9183B8: beq 0x9183eac0       ; 状态 1 无任何写入源
```

状态升级逻辑双重封死：

```
91810C84: bics ip, r0, #2    ; state ∈ {0,2} → 改成 3
918115F0: sub  r1, r1, #1
918115F4: cmp  r1, #1
918115F8: movls r1, #3       ; state ∈ {1,2} → 改成 3
```

全镜像 10 个引用点中，**没有任何一处写入 1**。

### 7.6 `authorized_kernel` 的真相

```
androidboot.veritymode= / androidboot.keymaster=1 / androidboot.mode=
androidboot.authorized_kernel=true / androidboot.baseband=msm ...
```

这是 cmdline 模板中的**输出标志**（验证通过后告诉内核），不是 aboot 的判断开关。

## 八、第五阶段：三层密钥体系

### 8.1 dm-verity 公钥（boot 内 `/verity_key`）

从 7.1.1 与 8.19.16 的 boot ramdisk 中提取，**字节级完全相同**：

```
7.1.1   sha256 = f16f3691ce1e667856add1ddb651b24a023de88cb75b686d45309f6dd88cad5c
8.19.16 sha256 = f16f3691ce1e667856add1ddb651b24a023de88cb75b686d45309f6dd88cad5c
```

容器结构（vivo 自定义，非 DER）：

```
[0x000:0x004]  40 00 00 00
[0x004:0x104]  a704dbb9 e99cf54b ...   ← 模数 n
[0x104:0x204]  94a70faf 7943dee7 ...
[0x204:0x208]  8c6c6086
[0x208:0x20C]  01 00 01 00             ← 指数 65537
```

与 AOSP testkey 对比：

```
verity_key n = a704dbb9e99cf54b...
testkey    n = e8eb784d2f4d5491...
正序包含 False / 逆序包含 False / 完全相同 False
```

**结论**：vivo 从 Android 7 到 8.1 未更换 verity 公钥，且不是公开密钥。

### 8.2 对应的 fstab 配置（7.1.1）

```
/system   ext4  ro,barrier=1,discard  wait,verify
/oem      ext4  ro,barrier=1,discard  wait,verify
/apps     ext4  ro,barrier=1,discard  wait
```

配合实测 `ro.boot.veritymode=enforcing`：**签名验证失败即中止启动**，不进入 EIO。

### 8.3 recovery OTA 公钥（`res/keys`）

从 1.15.1 的 `recovery.img` ramdisk 提取，mincrypt 格式：

```
v2 {64,0xc8a9f331,{64 字模数},{64 字 rr}}
共 1 把公钥
模数 = b96ada8b7d702096bef6e03d7b2eae6b...
sha256 = 2f8e80ae3dad1ac490edb59e712502d8...
```

recovery 自身属性：

```
ro.secure=1
ro.debuggable=0
ro.adb.secure=1
```

与 testkey 对比：**不匹配**。因此原厂 recovery **不接受** AOSP testkey 签名的 `update.zip`。

**这直接否定了"unsigned_twrp_temp.zip → 原厂 recovery → 临时 TWRP"的教程流程。**

### 8.4 EIO 状态转换

aboot 里存在 boot state 枚举字符串表：

```
...sbl.sdi.xbl.hyp.pmic....green...orange..yellow..red.eio.enforcing...
```

说明有"按状态选 eio/enforcing"的逻辑。但同时：

```
restart_reason   0 处
bootreason       0 处
boot_reason      0 处
```

**没有持久化失败计数的机制**，因此不存在"首次失败 → 下次切 EIO"的状态机。且实测 devinfo ULC 状态下仍为 `enforcing`，说明选择依据是更底层的 fuse/SBL 状态，不可通过分区写入控制。

## 九、第六阶段：工具与社区线索

### 9.1 `bbk unlock_vivo` 的真实实现

字符串引用点：7.13.15 @ `0x9183C5B0`（命令注册），handler @ `0x91838894`：

```
918388A8: ldr  r2, [0x9192BBDC + 0x10]   ; 读全局状态
918388B4: cmp  r2, #1
918388BC: beq  0x918388E4                ; 状态==1 → 继续
918388C0: ...                            ; 否则返回错误
918388E4: movw r0, #0xf600
918388EC: bl   0x91840618                ; 打印提示
91838900: mov  r0, #2
9183890C: b    0x91833068                ; 复位
```

**没有 HTTP 请求、没有 crypto 调用、没有 devinfo 写入、没有 SCM/QFuse 调用。**

它只是"解锁已完成，请重启"的确认命令。维修工具（TR Tools Pro / UnlockTool / Hydra / Chimera）的 vivo 解锁走售后服务器认证，最终结果仍然是写 devinfo——**与手动修改等效，不改变 secure boot 状态**。

### 9.2 酷安 Y66 案例（firehose peek/poke）

社区帖子（vivo Y66，2025-07）提出：aboot 里有一个函数恒返回 1，返回 1 时启用校验，改内存为 0 可禁用校验。

**Xplay6 的 firehose 确实支持 peek/poke**：

```
read..............................!.....
getstorageinfo....................!.....
getsha256digest...................!.....
erase.............................!.....
peek..............................!.....
poke..............................!.....
<log value="Supported Functions: ...
```

但该路线不可行：

- 需要构造 ROP 链（帖子作者原话："难度太大了，我做不到"）
- **重启后失效**，每次开机都要重新注入
- 时序矛盾：EDL 模式下 firehose 在跑时 aboot 尚未加载；aboot 加载后 firehose 已退出
- 作者明确说"y66 和其他机型的安全机制差别非常巨大，不太通用"

### 9.5 Treble 判定

当前 GPT 共 33 个分区（LUN0 14 + LUN1 1 + LUN2 1 + LUN3 3 + LUN4 33 + LUN5 3）：

```
含 vendor  : False
含 product : False
含 odm     : False
```

**没有 Treble 的分区基础，GSI 路线不成立。**

## 十、最终结论

### 10.1 为什么类原生移植不可行

需要同时突破三层，而每层都缺私钥：

1. **aboot 验 boot**：MBN 证书链，改一字节即卡 logo / 黑屏
2. **recovery 验 OTA**：单把 vivo 公钥，不认 testkey
3. **dm-verity 验 system**：vivo 公钥，且 `enforcing` 模式下失败即中止启动

即便解决了签名，还有：
- 无 Treble 分区，无法用 GSI
- 3.18 内核与 Android 10 的 HAL 需求差距过大
- `system.new.dat` 内 vendor 与 system 强耦合，需整体移植

### 10.2 那些"成功案例"是什么

`lineage_pd1610-eng 10 ... eng.root.20261014.103120 test-keys`

- `eng` = 工程构建，非 user/userdebug
- `test-keys` = AOSP 测试密钥签名

零售机官方系统**不可能**使用 test-keys。因此该案例只能是：
- 工程机（bootloader 不验签），或
- aboot 被替换为不验签版本

两者均无公开流出。案例作者拒绝提供启动链文件，也从侧面印证了这一点。

### 10.3 当前状态的价值

```
系统      Android 6.0.1 / 1.15.1（发烧友公认音质最好的出厂版）
BL        已解锁，fastboot 可写
基带      IMEI 完好，NV 全保留
恢复      9008 可用，两套完整固件在手
引导层    原厂，未被污染
```

这是公开条件下能达到的最优结果。
