# 零基础接续指南：只会刷机，也能用 Codex / WorkBuddy 接着修

日期：2026-11-15 · 适用对象：**刷过机、会进 fastboot、但没写过代码、没做过实验的人** · 默认语言：简体中文

> 读完这一份，你应该能做到：把项目恢复到电脑上 → 打开 AI 工具 → 说出第一句正确的话 → 完成一轮「不冒险」的协作 → 出问题知道怎么救回来。
> 你**不需要**会 C 语言、不需要懂 Linux 内核、不需要自己敲编译命令。那些是 AI 的活。
> 想直接看最深处的方法论，读 `offline/13_continuation_playbook.md`；本文件是它的白话版前导。

## 0. 先用大白话说清这是个什么项目

### 0.1 刷机 和 这里做的事，不是一回事

| | 你熟悉的刷机 | 这个项目在做的事 |
|---|---|---|
| 拿到什么 | 别人做好的 `ROM.zip` / `boot.img` | 一堆**调查记录 + 改到一半的源码** |
| 你要做 | 进 recovery / fastboot，选包，刷，开机 | 让 AI 改代码 → 重新编译出新的 `boot.img` → 刷 → 看日志 → 判断哪里错 → 再改 |
| 失败时 | 换包重刷 | **不能换包**，要靠日志找出「为什么起不来」，一次只改一个地方再试 |
| 成功长什么样 | 进桌面 | 进桌面**并且**触摸、按键、各个硬件都能用，还要留下一份能复现的证据 |
| 花的时间 | 十几分钟 | 一轮约 10–20 分钟，可能要几轮 |

一句话：**刷机是把成品装进手机；这里是「做成品的过程」被中途按下暂停，你要接着做下去。**

### 0.2 项目里有两条完全不同的路线，别搞混

```
项目
├─【路线 A】prebuilt 路线 —— 「拿原厂内核，做一个能用的 LOS16 ROM」
│    内核：原厂 3.18.71，**不自己编译内核**
│    成果：已经有一个可刷的 ROM zip（网盘 15_ 分类）
│    WiFi 已修通；还剩相机、libcurl、清诊断代码、sepolicy 四项没修好
│    接着做 = 改 ROM 里的配置/源码 → 重新编译 system.img → 刷 system → 测功能
│
└─【路线 B】自编译内核路线 —— 「自己编译 3.18.120 内核，替换原厂内核」
     内核：自己从源码编出来的 3.18.120
     成果：能开机进桌面、触摸锁屏唤醒后可用；仍有 4 项没达标
     接着做 = 改内核源码/config → 编译 boot.img → 只刷 boot → 抓日志 → 判定
```

**两条线的镜像绝对不能互相刷。** `02_/images/boot.img`（原厂回滚用）和 `03_/sys13_system.img`（WiFi 修通的系统）都不是同一版本的东西。刷之前一定让 AI 说清「这次刷的是哪个文件、进哪个分区」。

### 0.3 现在的真实状态（别被旧报告误导）

- 手机**已经回滚到原厂系统**，能正常开机、触摸和按键都好，**不在 fastboot**。这是安全的起点。
- 仓库里的 `ROUND*.md` 是**调查日记**，不是教程，也不表示「现在手机正跑着那一版」。
- 完成度 `50/50` 是「证据齐不齐」的分数，**不是**「手机做好了一半」。别被数字吓到。
- 详见 `offline/12_ai_handoff_index.md` **§9 当前准确状态**（旧章节的数字已过期，以 §9 为准）。

## 1. 你只需要会做三件事，其余全交给 AI

| 只有你能做 | AI 会替你做 |
|---|---|
| ① 把手机**手动弄进 fastboot**，然后回一句「好了」 | 读日志、查报错、比对源码、反汇编 |
| ② 按 AI 的要求**点屏幕 / 按导航键**，然后如实说「有反应 / 没反应」 | 改配置、写补丁、跑编译、生成 boot.img |
| ③ 决定「继续 / 暂停 / 回滚」，并在清空文件前点头 | 跑预检、发刷机命令、等手机上线、抓全量证据、写报告 |

**为什么进 fastboot 一定要你动手**：这台手机在自编译内核里，`adb reboot bootloader` 会退化成普通重启（这是项目里一个**没修好**的问题）。所以 AI 不能自己把手机切过去，它必须明确说「**请进 fastboot**」，你操作完回复，它才继续。**AI 如果没说这句话就自己刷，是违规的，你可以直接叫停。**

### 「请进 fastboot」到底怎么进

1. 手机关机（或让 AI 先执行 `adb reboot` 后等它亮屏再关机）。
2. 按住 **音量下** 不放，再按 **电源键**，感到震动后松电源、继续按住音量下，直到出现 fastboot 界面（不同机器组合可能不同，以你之前成功的方式为准）。
3. 用 USB 线连电脑。
4. 回 AI 一句：**「已进 fastboot」**。
5. 剩下的（确认端口、刷入、重启、验证）AI 来做。

> 项目历史上吃过亏：AI 曾经看到端口在线就写「设备自动进了 fastboot」，其实是你手动按的。所以现在的约定是——**不推断，等你亲口确认**。

## 2. 开工前，一次性把东西准备好

### 2.1 电脑上装什么

| 工具 | 干什么 | 从哪拿 |
|---|---|---|
| **WorkBuddy** 或 **Codex** | 让 AI 读文件、跑命令、改代码 | 你已在用的那个就行，二选一 |
| **Git** | 把仓库拉到本地 | 官网安装；或用 GitHub Desktop |
| **platform-tools**（adb / fastboot） | 电脑和手机说话 | 网盘 `04_9008与刷机工具/platform-tools/`，11 MiB |
| **WSL / Ubuntu 20.04**（只有路线 B 且要重新编译时才需要） | 编译内核 | 网盘 `06_WSL重建集/`，1.6 GiB，按 `offline/11_wsl_rebuild_guide.md` 路线 B |
| 压缩/校验工具 | 解开分卷、验哈希 | 7-Zip 或 Python 3.14+；`sha256sum` |

### 2.2 从百度网盘下哪些（不用全下 76 GiB）

云端目录 `PD1610_Xplay6/`，分享链接见 README「百度网盘冷备索引」。**最小开工集**：

```
00_必读_恢复说明/       ← 先下这个，里面有清单、RESTORE、索引、操作卡
01_全量冷备分卷/        ← 两卷 973 MiB + manifest.json + SHA256SUMS（权威冷备）
02_原厂回滚与发布包/     ← 出事时救砖用的原厂 boot.img
04_9008与刷机工具/       ← adb / fastboot / 9008 programmer
06_WSL重建集/            ← 只有要重编内核才需要
```

按路线再加：
- **路线 A（修 ROM）**：`03_prebuilt_续修基线/`（sys13 基线）、`15_LOS16_ROM刷机包/`（可刷 ROM）。
- **路线 B（修内核）**：`01_` 解开后就有完整工程；要原样环境再加 `06_`。

`10_` / `11_` 是 40 GiB / 11 GiB 的「原貌全量分卷」，只有想翻旧文件才需要，**不用下**。

### 2.3 两个必须照做的规矩

1. **路径原样**：构建脚本里写死了 `D:/xplay6/...`、`/home/builder/...` 这些位置。恢复时放回同样的盘符和目录，别改名字，否则编译会报「找不到文件」。`offline/11_wsl_rebuild_guide.md` 有完整对照表。
2. **先校验再动手**：把 `SHA256SUMS`、`manifest.json`、两个分卷放同一目录，让 AI 跑 `sha256sum -c SHA256SUMS`，必须显示 **3 行全 OK**。不 OK 就是下载坏了，重新下，别拿坏包开工。

## 3. 第一次跟 AI 说话：直接复制下面这段

### 3.1 用 WorkBuddy

1. 打开 WorkBuddy，把工作区/项目目录设成仓库所在文件夹（例如 `D:/xplay6/github_pd1610`，或从分卷恢复出的工程根）。
2. 新建对话，把下面整段贴进去发送：

```
我在接手 PD1610 / Xplay6 的内核项目。我是刷机用户，不会写代码、不会做实验，
请你用大白话带我，命令由你来跑，只告诉我需要我手动做的动作。

开工前请按顺序读：
1) AGENTS.md（仓库根，给你的硬规则）
2) docs/BEGINNER_GUIDE_CN.md（给我的白话手册）
3) offline/12_ai_handoff_index.md 的 §9（当前准确状态）
4) offline/13_continuation_playbook.md（单变量循环与 8 步 SOP）

读完先别动手机，也不要编译。先回答我三件事：
① 现在手机应该是什么状态、我该怎么确认；
② 我这次要接的是路线 A（修 ROM）还是路线 B（修自编译内核），你建议先做哪一轮、为什么；
③ 这一轮里，哪些动作必须我本人做，你会在什么时候明确提醒我。

规则：只写你真实跑过的命令和结果；没跑的写「未执行」并给可复现命令；
不要推断设备自动进了 fastboot；一轮只改一个变量；刷机前必须跑预检。
```

### 3.2 用 Codex

Codex（CLI 或 IDE 版）在仓库根目录启动时会自动读取 `AGENTS.md`。所以：

```bash
cd D:/xplay6/github_pd1610      # 换成你实际 clone / 解压出来的路径

```

进去后贴同一段开场白（把「WorkBuddy」换成「Codex」即可）。`AGENTS.md` 里已经写好了「先读哪几份、单变量、不虚构、请进 fastboot、只刷 boot、预检门禁」，Codex 会自动遵守，不用你再背一遍。

> 如果 Codex 是云端/沙盒环境、碰不到你电脑上的手机，就把「实机操作」单独留给本机 WorkBuddy：让 Codex 做离线分析和改代码，把生成的补丁/命令贴回本机跑。第 4 节的表照样适用。

```
我选路线 B：自编译 3.18.120 内核。请先读 offline/05_experiment_queue.md

以及为什么「先抓证据」比「先改代码」划算。第一轮只做零风险的状态核对与取证。
```

### 3.4 每轮结束时，固定问这三句（防止 AI 编结果）

```
请按下面三条复核本轮，逐条给证据，不要只给结论：
1) 本轮输入镜像的 sha256 和预检结果是什么？文件路径在哪？
2) 你说「成功/失败」依据的是哪个文件里的哪几行？
3) 有哪些步骤你其实没执行？请写「未执行」并给出可复现命令。
```

历史教训：曾经把「设备注册成功」当成「触摸能用」，实际点击时一个事件都没有。所以**一定要它拿 `getevent` 的行数、IRQ 计数这类真实数字说话**。

## 4. 一轮实验长什么样（真人视角剧本）

下面是一轮标准流程。**左列是 AI 会说的话，中列是你的动作，右列是你回什么**。照着走就行：

| AI 说 | 你做 | 你回 |
|---|---|---|
| 「我先离线核对，不动手机」 | 什么都不用做，等 | （不用回） |
| 「我改了一处配置，正在编译」 | 等 | （不用回） |
| 「预检通过，镜像 sha 是 `xxxx…`。**请进 fastboot**」 | 关机 → 音量下 + 电源 → 插线 → 看到 fastboot 界面 | **「已进 fastboot」** |
| 「刷入完成，正在重启，我等它上线」 | 别拔线，别按电源，让它开机 | （不用回） |
| 「设备可能掉线一次，我在重新枚举」 | 别动；若超过 2 分钟没反应，重新插一下 USB 并说明 | **「我重插了」**（如做了） |
| 「进桌面了。请点几下屏幕、滑一下，然后按返回键和任务键」 | 实际去点、去滑、去按 | **「触摸：有反应 / 没反应；返回键：没反应；任务键：没反应」** |
| 「我抓到 0 个事件，本轮判 FAIL」 | 不用自责，这是有效结果 | （不用回） |
| 「按约定回滚原厂。**请进 fastboot**」 | 再进一次 fastboot | **「已进 fastboot」** |
| 「回滚完成：原厂 3.18.71、能开机、fastboot 已退出」 | 拿起来确认能正常用 | **「确认可用」** |

一轮大概 10–20 分钟。中间**最常出现的插曲**是 USB 瞬时掉线：adb 会先连上重启前的旧会话再断开。这不是刷坏了，等 AI 重新枚举即可，别自己重启手机。

## 5. 黑话对照表（按刷机用户的理解来翻译）

| 文档里的词 | 大白话 |
|---|---|
| `boot.img` | 只装「内核 + 启动盘」的小包，刷它风险最小，本项目每轮**只刷这个** |
| `system.img` | 整个系统分区。路线 A 修 ROM 才会刷它；别和 `boot.img` 混 |
| `fastboot` | 手机上的一个刷机模式，电脑上用 `fastboot` 命令往里写文件 |
| 9008 / EDL | 高通的「急救模式」，手机黑屏也能连电脑读内存。bootloop 时靠它看死在哪一步 |
| `adb` | 手机开机后，电脑用 USB 远程下命令/看日志的通道 |
| `dmesg` | 内核自己的开机日记，看驱动有没有报错全靠它 |
| `getevent` | 把屏幕上每一次触摸、每一次按键原样打印出来。**「能不能点」以它为准，不靠肉眼感觉** |
| input 设备 | 系统认出来的「触摸屏 / 按键」等输入硬件。少一个就说明那个功能没驱动 |
| I²C / 驱动绑定 | 主板上的芯片要配上对应驱动才能工作。「绑定成功」= 配对上了 |
| 预检（preflight） | 刷机前 AI 自己跑的一套检查，防止把明显会卡死的镜像刷进去。**硬门槛，不许跳过** |
| 单变量 | 一轮只改一个地方。改两处就分不清是谁修好的 / 谁弄坏的 |
| 冷启动 | 完全关机再开机（不是重启）。有些问题只在冷启动后复现 |
| 回滚 | 把原厂 `boot.img` 刷回去，手机恢复成能正常用的状态。每轮收尾都做 |
| sha256 / 哈希 | 文件的数字指纹。用来确认「你下的包」和「AI 生成的包」没坏、没被换 |
| 实验队列 | 一张待办表（`offline/05`），写死每一轮要验证什么、什么算成功、失败了往哪走 |
| A 轮结果 | 一次「不改任何东西、只把证据抓齐」的实机记录（`offline/08`）。它让完成度从模糊区间变成确定值 |
| 完成度 / gate | 8 项验收打分。`UNVERIFIED` = 「这事可能做了但没留证据」，不是「没做」 |
| WSL | Windows 里的 Linux 子系统。编译安卓内核要用它 |
| 交叉编译 | 在电脑上编译出「给手机 CPU 用的」内核，编完生成 `boot.img` |
| 补丁 / diff | 「改了哪几行」的记录。发补丁集比重发整个源码树安全 |
| `AGENTS.md` | 放在仓库根、专门写给 AI 看的规则文件，Codex 一打开就会读 |

## 6. 保命：什么时候必须停，怎么救回来

### 6.1 出现这些，立刻对 AI 说「停止并回滚原厂」

- 卡在开机第一屏 / 第二屏超过 5 分钟（bootloop）。
- 屏幕一直黑、按电源没反应。
- 刷机命令报错后，AI 想再试第三次以上。
- AI 说「我推断设备已经在 fastboot 了」——它不该推断。
- AI 想刷 `system` / `vendor` / `userdata`，或想执行「双清 / 恢复出厂」。

### 6.2 回滚怎么做（命令让 AI 跑，你只负责进 fastboot）

原厂镜像在网盘 `02_原厂回滚与发布包/images/boot.img`，sha256 以 `929fda99` 开头。流程固定：

```
你：关机 → 音量下+电源 → 进 fastboot → 回「已进 fastboot」
AI：确认端口 → 刷入原厂 boot → 重启 → 等开机 → 报告「3.18.71 / 能开机」
你：拿起来确认触摸、按键正常 → 回「确认可用」
```

回滚成功后，手机又回到安全起点，本次实验的白做也不会有损失。

### 6.3 绝对不要做的 8 件事

1. 别刷 `system` / `vendor` / `userdata`（除非路线 A 且 AI 明确说明并已被你确认）。
2. 别双清 / 恢复出厂 / 格式化 data。
3. 别把百度网盘设成**双向同步**——以后清空电脑会把云端一起删掉，必须是单向「备份」。
4. 别删 `.workbuddy/` 文件夹（项目记忆在里面）。
5. 别在手机启动过程中拔 USB 线或按电源键。
6. 别改名 / 解压 / 编辑 `01_` 里的两个分卷文件。
7. 别凭感觉替 AI 判断「应该成功了吧」——点不动就是点不动，如实说。
8. 别让 AI 一次改好几个地方「顺便一起修」，十有八九会回到查不出原因的状态。

## 7. 怎么判断 AI 有没有在瞎编

这个项目的历史里，**最贵的错误不是刷坏手机，而是把假设写成结论**（Round14/15 曾误判 `usb_bam`，Round16 才推翻）。所以留了三条硬规矩，你也可以拿来检查：

| 检查 | 正确回答长这样 | 危险信号 |
|---|---|---|
| 「哈希多少？」 | 给出完整 sha256 + 对应文件路径 | 「应该和上一版差不多」「没记」 |
| 「证据在哪？」 | `flash_log/roundXX_dmesg.txt` 第 N 行，`getevent` 抓到 1266 行 | 「日志显示正常」但不给文件 |
| 「哪些没跑？」 | 明确列出「未执行：X，命令是 `...`」 | 「都完成了」却没有任何命令输出 |

**区分 [O] 和 [H]**：`[O]` = 观察到的事实（日志、计数、哈希）；`[H]` = AI 的猜测，必须标注「未验证」。看到 `[H]` 被当成结论用，直接让它改回去。

另外：AI 说「触摸已修好」时，标准追问是「`getevent` 抓到几行？IRQ 从多少涨到多少？」——**设备注册成功 ≠ 有触摸事件**，这条坑项目里踩过。

## 8. 建议的第一轮：不编译、不刷机、零风险

第一次接手别急着改代码。建议让 AI 做这一轮，把协作流程跑通：

```
本轮只做零风险状态核对，不编译、不刷机、不改任何文件：
1) 确认手机在线，读内核版本、开机完成标志、input 设备清单；
2) 抓一份基线日志（dmesg / getprop / input / I2C 绑定）；
3) 核对本地文件：仓库文件数、分卷 sha256sum -c 是否 3/3 OK；
4) 给我一份「当前状态报告」，用大白话写：手机现在跑的是什么、
   仓库里两条路线各做到哪、下一轮建议做什么、需要我做什么。
未执行的步骤写「未执行」。不碰任何分区。
```

这一轮做完，你就知道 AI 会不会按规矩说话、你的 USB 连得稳不稳、网盘文件有没有下坏。**然后再决定要不要进真正的实验轮。**

## 9. 常见问题

**Q：我完全不会 Linux 命令怎么办？**
A：不用会。所有命令 AI 会自己跑并贴结果给你。你只要会复制它的开场白、按它说的进 fastboot、点屏幕并如实反馈。

**Q：我不会 C 语言，能修内核吗？**
A：能，因为改代码的是 AI。你的价值是「真机操作」和「如实反馈」——这两件事 AI 做不了。项目前 26 轮就是这么配合下来的。

**Q：手机变砖了？**
A：先别慌，按 §6.2 回滚原厂 boot。真进不去 fastboot，还有 9008 急救模式（工具在网盘 `04_`），让 AI 带你走。项目全程有回滚基线，没有做过不可逆的分区写入。

**Q：网盘链接失效 / 要提取码？**
A：找项目维护者要新链接或提取码。仓库 README 的「百度网盘冷备索引」里写了目录结构，用来核对内容有没有下全。

**Q：AI 说要刷 `system`，是不是很危险？**
A：路线 A（修 ROM）确实会刷 `system`，但那是**另一条路线**的常规操作，和第 2 节说的「只刷 boot」不冲突——后者是路线 B 的规矩。让它先说清「这次刷哪个文件、进哪个分区、回滚副本在哪」，你确认了再让它动手。

**Q：README 里 `50/50` 是不是说只做了一半？**
A：不是。那是「证据齐不齐」的分数，`UNVERIFIED` 归零后的确定值。剩下的 4 项 FAIL 是具体功能没达标（冷启动触摸、导航键、input 5/9、I²C 4/9），不是「一半代码没写」。

**Q：XDA 上能不能直接发这个 ROM？**
A：路线 A 有可刷 ROM，但仍有 4 项 TODO；路线 B 的自编译内核还只是研究快照。写帖前先看 `D:/xplay6/XDA_POST_PD1610.md`（本机文档，未进仓库），别把它包装成日常可用版。
